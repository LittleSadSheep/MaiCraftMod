# 架构总览

`docs/dev/` 是**横向的能力文档**：取物、烹饪、聊天、等待，每个能力一篇，讲得很深
（参数、分支、完成证据、验证范围）。

这里补的是**纵向的地图**：一条指令怎么穿过整个系统。

两者不重复。能力文档假设你已经知道"这句话落在哪个部分"；这份文档就是回答那个问题的。

## 第一次读代码，从哪开始

**先读文档，再读代码。代码从上往下读，不要从最下面开始。**

### 第 0 步：先把这四篇看完（不看代码）

[结构地图](01-structure.md) → [一条指令的旅程](02-data-flow.md) →
[四个公开工具](06-tools.md) → [核心类型与数量关系](03-core-types.md)

先读完再碰代码。否则你会像没带地图进城。

### 第 1 步：挑一条**最短的能力**，从上往下走

推荐 **`maicraft:remember_place`**（记一个地点）。它是全项目最短的一条链：

```text
入口   perceive(view=abilities, focus="maicraft:remember_place") 看它要什么参数
翻译   AbilityAdapter.remember         ← 只有几十行
语义   它返回 IntentAction.Remember → 直接记账
```

**它没有任务单、没有身体操作**——所以你能在十分钟里看懂"一个目标怎么变成动作"。

### 第 2 步：挑一条**有身体操作**的，还是从上往下

推荐 **`maicraft:sleep`**（睡觉）。这次走完整条链，**顺序不变，仍然从上面开始**：

```text
入口   在 abilities 里读 sleep 的契约（它不需要参数）
翻译   AbilityAdapter.sleep  ← 看它怎么判断"有没有床"
任务   它拼出的 Chain([build, goto, sleep])，最后一环 SleepCompanionTask.onTick()
身体   它调用的 context.actions().useBlock(...)
```

**走到最后一站（`useBlock`），你才第一次遇到"提交"。** 这时你已经知道它为什么存在了。

### 第 3 步：最后才看"提交 / 对账"

回头读[关键机制](04-mechanisms.md)第 3 节，再按顺序看：

```text
NativeConfirmation       ← "怎么算成功"
NativeActionReceipt      ← "小票上记什么"
DefaultNativeActionPort  ← 实现（最后才看）
```

### ❌ 不要这样做

| 不要 | 为什么 |
| --- | --- |
| 一上来就读 `DefaultNativeActionPort`（560 行） | 你还不知道它服务谁 |
| 一上来就读"提交 / 对账" | 它是最微妙的机制，**不是入口** |
| 按包名顺序读 | 包名是整理结果，不是学习路径 |

## 贯穿全局的一条信条

> **发出 ≠ 成功。**

请求发出去了、客户端画面变了、背包里本来有这件物品、库存数字增加了——
**都不自动等于任务成功。**

这条信条在每个部分都有具体落实，读的时候可以顺着它看：

| 部分 | 信条怎么落实 |
| --- | --- |
| 入口 | `execute` 返回 `accepted: true` 只表示**已登记** |
| 语义 | 步骤完成要看子任务拿回的真实证据，不是"动作发了" |
| 翻译 | 只读现场、不写世界；信息不全就 `Pending` 或提问 |
| 调度 | 被抢占不等于丢失，进度保留 |
| 任务 | `start` 是一次性准备；`result` 会收尾；到达要按身体再验 |
| 身体操作 | 提交后才对账；要**连续稳定刻**满足才算确认 |
