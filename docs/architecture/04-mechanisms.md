# 关键机制

这一节讲几处**别处没说、但读代码一定会撞上**的设计。
每一节都是独立的，可以按需跳读。

---

## 1. `Native` 和 `Tool`：两条路，一个出口

翻译产出动作时，有两条路：

```text
① Native：翻译自己造好了任务单
   AbilityAdapter.adapt(...) ──► new IntentAction.Native(record)

② Tool：翻译只给"工具名 + 参数"，让工具去造
   AbilityAdapter.adapt(...) ──► new IntentAction.Tool("goto", json)
        └─► 工具内部：new MoveToTaskRecord(...) 然后 setTask(...)
```

**两条路最终都进同一个方法 `beginNative(TaskRecord)`。**

### `Native` 的执行：父任务把子任务"揣在兜里"

```text
beginNative(record)
  ├─ childRecord = record
  ├─ child = TaskFactory.create(player, record)   ★ 记录 → 执行器
  └─ child.start(player)                          一次性准备

之后每刻：
tickChild() ──► child.tick(player)
```

关键点：**子任务不在任何任务槽里**，它只是 `IntentTask` 的一个私有字段。

| | 谁在任务槽 | 谁驱动 |
| --- | --- | --- |
| `current` 槽 | 父任务 `IntentTask` | `CompanionBrain` |
| 子任务 `child` | **不在槽里** | **父任务亲自 `tick`** |

**所以子任务不会被别的任务挤掉。**

### `Tool` 为什么需要 `captureNext`

工具是按照**独立工具**的契约写的：它只管把任务单**提交给调度器**。两个入口：

| 工具调 | 会走到哪 | 没有拦截时的后果 |
| --- | --- | --- |
| `setTask(...)` | `current` 槽 | **顶掉父任务** |
| `runSync(...)` | `sync` 槽 | 变成父任务的**平级**，抢身体 |

两种都不行：

- 前者把父任务挤走；
- 后者让父任务被挂起，等 sync 那件事回来，发现"子任务还没建"，
  于是重新翻译、**再次提交** → 循环。

所以父任务在调用工具**之前**，先摆一张网：

```text
beginTool
  ├─ captureNext 摆网（设一个"正在接收"的标记）
  ├─ 调用 tool.onGameCall(...)
  │      └─ 工具调 setTask / runSync
  │            └─ 被网接住 → 交回父任务（没有走到调度器）
  └─ 取下网，看接到了什么
```

**这张网的约束**（来自 `TaskDispatch`）：

| 约束 | 原因 |
| --- | --- |
| 一次只能接住**一个**任务单 | 接住两个说不清用哪个，直接报错 |
| **不能嵌套** | 父任务已在张网，里面不能再张一张 |

### `beginTool` 拿到的东西：**三种可能**

```text
① 接住了一张任务单   → beginNative(record)        ← 最常见
② 工具只回了即时结果  → 解析结果，直接完成这一步     ← 查询类工具
③ 两样都没有         → 失败（"既没任务单也没结果"）
```

> ⚠️ **不是"一定产出任务单"。** 有些工具是"查一下、立刻回答"，
> 它们走 `reply` 而不是 `submit`——网接不到东西，但工具给了答案。

**因果链**：`captureNext` 接住 → 子任务变成私有 → 于是不会被挤掉。
不能倒过来读成"因为不会被挤掉，所以 captureNext 多余"。

**它也是 `Tool` 层的历史证据**：`Tool` 的契约是"提交"，`Native` 的契约是"返回"。
`captureNext` 存在的全部理由，就是把前者掰成后者。

## 2. 两个槽 + 三档优先级

身体只有一个，所以要有"谁先来"的规则。

```text
TaskSelector 每个游戏刻按顺序问"你能跑吗"，第一个说能的拿走身体：

  1. 反射（自救）    多个，按注册顺序    等模型决定就晚了
  2. 同步槽 sync     0 或 1 个          临时动作，调用方在等结果
  3. 当前槽 current ★ 0 或 1 个          主人交代的任务
  4. 空闲姿态        通常不用
```

| 槽 | 装什么 | 典型 |
| --- | --- | --- |
| `sync` | 临时动作：短、有界、**调用方在等结果** | 换装备、关菜单、合成 |
| `current` | 当前任务：可能很长 | 盖房子、打龙 |

**抢占三档：**

| 原因 | 什么时候 | 后果 |
| --- | --- | --- |
| `PREEMPTED` | 自救或临时动作插进来 | **进度留着**，回来接着干 |
| `REPLACED` | 主人改主意 / 派了新活 | 换掉 |
| `BODY_GONE` | 死亡、下线、换世界 | 身体没了 |

**没轮到的任务会延后自己的截止时间**——等别人干活不该花掉自己的执行时间。

## 3. 原生操作：提交 → 对账

这是全项目最硬的一块。核心信条：

> **「我屏幕上看到变了」 ≠ 「世界真的变了」。**

因为客户端会**预测**：你一点，画面立刻变；但服务器才是权威，
它可能说"不行"，于是方块回来。

所以要**两阶段**：

```text
① 提交：useBlock(...) ──► 拿到一张回执（状态 PENDING）
② 对账：之后每刻 poll(receipt)
          └─► 用「判定条件」读客户端事实
```

### 回执 `NativeActionReceipt`

记着：操作类型、提交时的**身体版本**和**控制版本**、截止时刻、
要连续几刻稳定、**判定条件**、当前状态。

状态有六种：

| 状态 | 意思 |
| --- | --- |
| `PENDING` | 还在等 |
| `CONFIRMED_APPLIED` | ✅ 确认成功 |
| `CONFIRMED_NOT_APPLIED` | ❌ 确认没发生 |
| `DIVERGED` | ⚠️ 出现了**第三种状态**（不是没变，是变成了别的） |
| `CANCELLED` | 已取消 |
| `UNCERTAIN` | 已提交但没等到确认 |

### 判定条件 `NativeConfirmation`

就是一个函数：读当前客户端事实，返回四种判定之一：

| 判定 | 意思 |
| --- | --- |
| `PENDING` | 还没发生，继续等 |
| `APPLIED` | 成功了 |
| `NOT_APPLIED` | 没有生效 |
| `DIVERGED` | 出现了预期之外的状态 |

项目自带的例子：`blockBecomesAir`（挖掉变空气）、`blockState`（变成期望状态）、
`menuChanged`（菜单换了）、`heldItemChanged`（手上物品变了）、`entityHurt`（实体掉血）……

> **判定条件只读事实，不会自己再点一次，也不自动证明服务器已确认。**

### 为什么要"连续稳定刻"

因为客户端有预测。要求**连续 2 个客户端刻**都满足，才排除"服务器马上要回滚"。
只数不同的客户端刻，同一刻重复查询不重复计数。

### `poll`：每刻对账一次

任务**每个游戏刻**调用一次 `poll(context, receipt)`。**它只读，不发新点击。**

```text
poll(context, receipt)
  ├─ 1. 这仍是"本刻"的身体吗？（过期的入口直接拒绝）
  ├─ 2. 已经是终态？ → 直接返回（终态是冻结的历史，不会重开）
  ├─ 3. 身体 / 控制版本变了，或本刻不许动手？ → UNCERTAIN（不谎报）
  ├─ 4. 跑判定条件，按四种判定处理：
  │        APPLIED     → 稳定计数 +1；够了 → CONFIRMED_APPLIED
  │        NOT_APPLIED → CONFIRMED_NOT_APPLIED
  │        DIVERGED    → DIVERGED
  │        PENDING     → 稳定计数【清零】
  ├─ 5. 还没结论，但已过截止时刻？ → UNCERTAIN（确认窗口到期）
  └─ 6. 返回 receipt（可能仍是 PENDING）
```

**三个关键点：**

| 点 | 说明 |
| --- | --- |
| `PENDING` 会**清零** | 判定条件来回变时，连续计数重置——**凑不过去** |
| 版本变了 → 直接 `UNCERTAIN` | 不是失败，是**不谎报**：身体都换了，结果不可信 |
| 超时 → `UNCERTAIN` 而不是 `FAILED` | 同上：没确认就是没确认 |

**任务怎么用它（每刻一次）：**

```java
receipt = context.actions().poll(context, receipt);   // 对账
if (!receipt.terminal()) return RUNNING;              // 还没结论 → 下一刻继续
if (receipt.status() == CONFIRMED_APPLIED) { 成功 }
else                                       { 失败 / 报告不确定 }
```

⚠️ **对账期间绝不要再点一次。** `poll` 只读；重复提交会让"这到底是第几次操作"说不清。

**一个具体轨迹（挖一个方块）：**

```text
刻 1  提交 startBreaking ──► PENDING
刻 2  poll → 还是原方块    → PENDING（稳定计数 0）
刻 3  poll → 还是原方块    → PENDING（稳定计数 0）
刻 4  poll → 变空气了      → APPLIED（稳定计数 1）
刻 5  poll → 还是空气      → APPLIED（稳定计数 2）→ CONFIRMED_APPLIED ✅
```

如果刻 4 变空气、刻 5 又变回方块 → **计数清零**，重新等够 2 刻。

> **任务结束但回执还没确认时**，要调用 `retireOneShotForTaskBoundary` 把这个
> 操作槽还回去（见 `SleepCompanionTask.cleanup`）。不清会占着"本刻操作额度"。

### 每刻只能提交一次

`LocalPlayerContext.mutationAvailable()` 表示"本刻还可不可以再提交一次操作"。

**这就是为什么所有任务都是"每刻做一点"**——不是愿意慢，
是**身体每刻只准动一次手**。

## 4. 世界身份绑定与检查点

### 世界身份

`StateIdentity` 回答"这份任务属于哪个存档"：

| 情况 | 用什么算 |
| --- | --- |
| 单人存档 | 存档目录的绝对路径（Windows 转小写） |
| 多人服务器 | 服务器地址 |

再取哈希，得到身份键。**每个任务在创建时记下这个键**（`bindingKey`）。

用途：换世界、换连接、换玩家后，旧任务**不能被误用**。

### 检查点

```text
<游戏目录>/config/maicraft/memory.sqlite
```

任务检查点保存计划、**总任务单**、请求键、地标和容器记忆。机器档案、完整蓝图、玩家施工归属、作者模型、续建项目、支撑账、原生预约和服务端未决请求也使用这一个 SQLite 文件。

`MemoryDatabase` 的 `memory_records` 表以 `scope`、`identity_key`、`document_key` 为联合主键。复杂任务、项目和机器内容沿用已有编码及校验，数据库负责隔离、事务与持久化；当前不拆分任务内部步骤为独立 SQL 表。

| 分区 | 记录与编号 |
| --- | --- |
| `state` | 世界检查点，空文档键 |
| `state/owned-construction/<玩家 UUID>` | 该玩家在当前世界的施工归属 |
| `machines` | 世界与玩家机器索引，空文档键；独立图纸使用内容指纹 |
| `state/build-scenes` | 作者模型版本，原 `scene_id` |
| `state/build-projects` | 冻结施工目标，原 `project_id` |
| `state/build-scaffolds` | 原生确认支撑账，原 `project_id`；轻量更新不改写冻结目标 |
| `state/native-submissions/<机制>` | 附魔、聊天和其他原生提交预约，原操作 UUID |
| `server-mutations` | 客户端服务端未决请求，按旧日志名称区分 |

`MemoryDocuments` 只在库中缺少该编号时读取旧文件，领域校验通过后唯一插入；源文件保留。`MutationJournal` 先合并旧正式文件和 `.pending` 的未决身份，再一次入库。旧原生预约即使为空或截断也保留原文并阻止再次提交；数据库中的空未决集合和空支撑账同样是有效记录，不能被旧文件重新填回。

| 特性 | 说明 |
| --- | --- |
| 写入 | 游戏线程留文本，后台提交 SQLite 事务；机器索引与引用蓝图一起提交 |
| 节流 | 平时约 5 秒一次；关键点（消费前、死亡、断线、关机）强制写 |
| 耐久性 | WAL + `synchronous=FULL`；提交完成后才兑现保存回执，消费屏障继续等待该回执 |
| 迁移 | 按世界首次读取旧 JSON，完整校验后导入；已有数据库记录优先，旧文件保留 |
| 损坏 | 旧 JSON 语法损坏仍加 `.corrupt` 保留；数据库不可读或库内检查点损坏时保留原记录并阻止覆盖 |
| 超容量 | 不加载，也**不覆盖**旧记录；预算按每份检查点或图纸的 UTF-8 内容计算 |

正常退出游戏后备份整个 `config/maicraft/`。运行期间 SQLite 可能存在 `memory.sqlite-wal` 与 `memory.sqlite-shm`，不能只拷贝主文件作为一致备份。旧目录用于兼容导入和保留迁移源，不再写入新的内部状态 JSON。

`ResponseArchive` 把大回执压缩后存入本服务创建的临时 SQLite，保留原来的 URI、份数、压缩字节预算和未使用三十分钟失效规则。停止服务时删除临时库；这种会话引用从来不承担跨进程恢复。配置、外部蓝图文件以及 JSON/NBT 导出是文件接口，继续按其格式读写。

### 恢复的纪律

**恢复 ≠ 重新批准。**

未完成任务从磁盘回来时：

- 先以**暂停**状态恢复
- 丢掉旧的路线、菜单、按键（只保留目标和已确认的结果）
- 要明确要求继续，它才动

理由：旧世界的路线和菜单在新世界不成立；而且已经提交、结果不确定的操作，
不能因为"重试"再点一次。

## 5. 翻译为什么每刻重跑

翻译（`AbilityAdapter`）在"没有子任务在跑"时**每个游戏刻都会被调用一次**。

因为**世界会变**：

- 床可能被怪打掉了
- 天可能黑了
- 材料可能到手了
- 上一个动作可能刚做完

所以它每次都**重新看当前现场**，重新决定下一步。

这带来两个约束：

1. **必须便宜、幂等**（不能有副作用）
2. **信息不全时返回 `Pending`**，而不是猜

> 这也是"Mod 补齐前置条件"的实现方式：LLM 只说"睡觉"，
> 翻译自己判断"找床 / 放床 / 走过去 / 躺下"，或者提出问题。

## 6. `Chain` 的动作是"到点才构造"的

`Chain` 代表"一组动作按顺序做"。例如睡觉可能变成：

```text
Chain([ build(放床), goto(走过去), sleep(躺下) ])
```

**它装的不是"预先造好的任务单"，而是"到点才构造的动作"。**

为什么不能一次造好？两个原因：

| 问题 | 说明 |
| --- | --- |
| **截止时间锚点会错** | 任务单的截止时间是"构造那一刻 + 时限"。同一刻造三张，第一步一耗时，后面几步的时限就被吃掉了 |
| **副作用顺序会错** | 造任务单可能读实时状态、写施工账；这些应该按动作顺序发生，不是一次全发生 |

所以 `Chain` 的元素是**延迟动作**：

```text
begin(Chain)
  └─ 记下动作列表 + 下标
之后每刻：
  当前动作完成 → 下标 +1 → 轮到下一个才构造它
```

**这和 `Tool` 的"延迟"是同一回事**：`Tool(name, json)` 也是到点才解析、才造任务单。

## 7. `request_key`：一个"约定"，不是"强制"

`request_key` 是**幂等键**（"幂等" = 同一件事只做一次）。
它就是"这件事的身份证"。

系统只保证一件事：

> **同一个 key，绝不会开出第二张任务单。**
> 重复发来，就把原来那张还给你。

**谁填？**

| 情况 | 谁填 |
| --- | --- |
| 调用方给了 | 按它去重 |
| 谁都没给 | 服务端**自动生成**（连接号 + 请求号 + 参数的哈希） |

**那"正确"谁负责？**

服务端**不检查内容**——它只做去重，不比较两次请求是否真的相同。

| 谁 | 责任 |
| --- | --- |
| 调用方 | 同一件事重试**复用同一个 key**；新的事**用新 key** |
| 服务端 | 同一 key 绝不开第二张；没给就自动兜底 |
| 服务端**不做** | 不判断你是不是"发错了" |

> 它防的是"网络抖动把同一个请求发了两遍"，**不防"你发错了"**。

**补救办法**：`execute` 的返回里有 `task_id`。就算网络不确定、任务开没开你不知道，
也可以用 `task(action="list", request_key=...)` **按 key 把任务找回来**。
