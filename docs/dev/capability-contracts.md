# 能力契约与贡献者文档怎么写

能力说明有两个读者：LLM 要据此正确提交目标并理解结果，贡献者要据此定位实现、修改行为和排查问题。两者共用真实语义，按各自用途组织内容。

## 模型可见契约

从 `perceive(view="abilities",focus=...)` 能读到的契约开始，沿请求校验、适配器、任务与结果逐层核对。

发现列表的 `summary` 用一句清楚的业务用途帮助选择能力，完整契约的 `usage` 保留操作说明，`parameters` 解释逐项参数。`usage` 不是请求参数。复盘过的能力由 [AbilitySummaries](../../common/src/main/java/org/maiwithu/maicraft/intent/AbilitySummaries.java) 提供发现摘要，[SemanticAbilityCatalog.describe](../../common/src/main/java/org/maiwithu/maicraft/intent/SemanticAbilityCatalog.java) 将原完整说明原样放入 `usage`；没有按字符数删节。未复盘的能力继续沿用原契约。

1. **用途和边界**：何时使用，角色会做什么，什么情况应选择另一能力；同名操作或子模式逐项说明。
2. **参数位置**：说明完整层级，例如 `goal.parameters`，明确它与 `target`、`preferences`、嵌套对象的关系。
3. **每个字段的语义**：类型、单位、默认值、范围、枚举、必填条件、互斥项；省略、零、空值和 `false` 有不同含义时分别解释。
4. **动作与确认**：先做什么、后做什么，依赖哪些真实观察，哪些操作会产生副作用，用什么原生证据确认成功。
5. **回执与恢复**：接单、动作完成、目标满足和结果未知分别意味着什么；说明失败、待决策、暂停和恢复的入口与依据。
6. **有效示例**：提供可解析的完整 `plan` 请求，覆盖普通情况和最容易误用的边界；引用必须来自真实观察，不编造 UUID、配方或注册 ID。

字段的声明类型（`integer`、`number`、`boolean`、`array<…>`、`object` 等）同时决定公开入口的编码还原。部分宿主会把 `-86` 写成 `"-86"`、把 `true` 写成 `"true"`、把数组包成 `{"item": [...]}`，或把已声明参数写在 `goal` 顶层。[ParameterNormalizer](../../common/src/main/java/org/maiwithu/maicraft/intent/ParameterNormalizer.java) 在 `PublicToolCatalog.validateAndNormalize` 和决策应答合并 `details.parameters` 前，按声明类型还原这些语义唯一的写法：对象字段只还原 `x/y/z` 与 `schema_version`，字符串字段一律不动；`"8.5"`、`"yes"` 这类无法唯一还原的值原样交给契约拒绝。成功回执以 `normalized_arguments` 列出每处还原。被拒的请求随错误附 `ability_signature`，内容是该能力的字段名、声明类型和可接受的地点种类，宿主据此改正即可，不必再读一轮完整契约。顶层工具字段已有逐项类型的输入 Schema，保持严格校验，不做还原。

自然语言的 `outcome` 不替代结构化参数。例如“精确到这一层”必须对应实际可用的精度参数，不能只在一句描述中承诺执行器没有收到的限制。

不设置说明字数上限，不通过截短描述、缩写堆砌或隐藏参数来满足长度回归。保留判断和调用所需事实，去除重复包装；真实网络报文限制和游戏输入限制须按各自协议处理。

契约应和当前实现一致。发现参数未接通、输入被忽略、回退偷偷放宽或成功条件不足时，明确记录差异，不能只把期望行为写成“已经支持”。改变游戏操作行为仍按仓库授权规则处理。

## `docs/dev` 中的能力说明

正式能力文档放在 `docs/dev`，相近能力可以合写；优先扩充已有文档。临时分析、历史归属和协作记录放在 `docs/tmp`，不进入提交。

推荐按照贡献者查问题的顺序组织：

| 内容 | 要回答的问题 |
| --- | --- |
| 用途和玩家场景 | 玩家想做什么，角色最终做了什么 |
| 参数与示例 | 字段放在哪里，怎样提交一份有效请求 |
| 主流程 | 从观察、准备到动作、确认和收尾，按游戏中的先后顺序解释 |
| 代码导航 | 想看某一步应打开哪个文件、哪个类或方法；使用有效相对链接 |
| 分支与副作用 | 缺材料、模组差异、菜单变化、原生拒绝时怎样处理，已经完成哪些效果 |
| 结果与控制 | 如何判断完成，暂停、取消、死亡、换世界和重启分别保留什么 |
| 已知边界与验证 | 哪些行为未接通或未验收，现有回归入口在哪里，不能把离线检查冒充实机验收 |

避免只有类名清单、历史修改流水账或“支持某功能”的口号。先说明玩家行为，再给实现入口；首次出现的项目术语必须能从上下文读懂。

公共索引由 [能力表](capabilities.md) 和 [开发文档入口](README.md) 维护。能力数量以 `IntentRuntime.KNOWN_ABILITIES` 为准；兼容入口、默认发现项以及 MCP 的四个工具分别统计。

## 中文业务注释

遵守仓库 `AGENTS.md`：所有新写或修改的代码配中文业务行为注释，使用简短类型名与导入，不新增全限定名调用。

- 流程入口先说明触发条件、角色目标与整体顺序。
- 在关键状态切换处说明角色此刻在做什么、为什么等待、继续或收场。
- 解释观察事实、原生提交和确认结果之间的关系；说明保留已发生效果的原因。
- 注释不只把 `if`、循环或变量名翻译成中文，不把未来设想写成当前保证。

例如：

```java
// 确认本次产物已入包后再结算收获；物品实体暂时消失时继续等同步，避免重复投料。
```

本轮仅整理说明时，沿公开入口和关键状态转换补注释，保持执行条件、返回值和原生动作次序。需要改变行为的缺陷单独说明触发场景和拟议修复。

## 协作与交付

多个会话同时工作时，每项能力只有一个本轮维护者。共享目录、总适配器和索引由协调会话统一整合，其他会话提交限定范围的文字提案；专属实现和文档可按分工编辑。

交付应列出能力 ID、完成的契约与文档、注释入口、发现的行为差异以及实际做过的检查。文档 JSON 和链接可做静态检查；是否执行回归及实机验证遵从本次用户要求，未经执行不得写“通过”。

所有开发和提交保留在 `dev`，只有用户明确要求才更新 `main`。提交使用配置身份并签名，中文 Conventional Commits 描述，每笔少于 325 个增删行。
