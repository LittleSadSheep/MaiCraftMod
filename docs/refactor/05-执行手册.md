# 05 执行手册（给执行 Agent）

**每次开工前读一遍。** 本手册优先于你自己的习惯；与本手册冲突的指令，以人类在对话里的明确要求为准。

背景：v2 在新仓库从零建设，v1（`MaiCraftMod`）冻结维护。你大部分时间在 v2 仓库工作；读 v1 只为两件事：清点领域旧逻辑（清册），以及按移植清单搬运底座文件。

## 一、十条铁律

1. **先认领，再动手。** 在看板上认领工作包；别人认领中的工作包不碰。
2. **一个提交只做一件事。** 移植、改名、改逻辑分开提交。
3. **只按批准的规格写行为。** 规格没写的行为不擅自加；规格写得不清楚，就停下来提问，不要自己猜。
4. **v2 不放旧代码。** 需要 v1 的东西，只能按移植清单搬，并登记 v1 路径、提交号和做了哪些整理。不登记的"顺手复制一段"一律不允许。
5. **v1 只读。** 除非工作包明确是 v1 的直播修复，否则不在 v1 提交任何东西。
6. **护栏只能收紧。** 不得放宽 ArchUnit 规则和源码扫描规则，不得往例外清单里加条目，除非工作包卡片明确要求。
7. **不就地打补丁。** 实机或测试暴露的问题，按第四节 4.3 的规程处理：找到它归属的模型或规格去修，不在出问题的地方加特判。
8. **决策代码要能离线测试。** 读接口、出结论的部分写成纯函数，用替身测试；测试不用 `Unsafe`，不用反射改私有成员。
9. **只跑相关回归。** 按工作包卡片写的回归组跑，不顺手跑全量；全量由 CI 负责。汇报时写明实际跑了哪些组。
10. **做完就停。** 工作包验收通过就提交、汇报，然后停下来，不顺手开始下一个，也不"再优化一下"。

## 二、仓库规则（两个仓库通用；转述自本机 `AGENTS.md`，该文件不进 Git）

### 分支与提交

- 只在 `dev` 分支开发、验证、提交。**绝不**对 `main` 做合并、快进、cherry-pick、update-ref 或推送；合入 `main` 只能由 LittleSadSheep 明确要求后进行。
- 不创建、不使用 `codex/*` 分支，不加自动分支前缀。
- 使用你配置好的 Git 身份，**每个提交都要签名**。
- 提交信息用 Conventional Commits：类型和可选作用域保持英文约定写法，冒号后面的说明和正文**一律中文**。例如 `feat(kernel): 加入子任务监护，所有执行器共用同一套子任务生命周期`。
- **提交行数**：v2 的重构建设工作不受 799 行限制（LittleSadSheep 2026-10-08 授权），但仍然一个提交只做一件事。v1 的直播修复仍要求单个提交少于 799 行。
- `dev` 上可能有多个会话同时提交：只暂存你自己的改动；提交前后核对 `HEAD`；不强制推送。

### 代码风格

- **禁止全限定名。** 类型写在 `import` 里，正文只用短名。同名冲突时才例外；反射类名、Mixin 目标、协议字符串这类必须写全名的不受此限。
- **新写或修改的每段代码都要加中文游戏逻辑注释**：写清触发条件、角色动作、执行顺序和原因。例如：
  ```java
  // 床被墙挡住看不见时，先换到下一个能看见床头的站位再点，不把一次坏站位当成整夜睡不了。
  // 靠近 -> 瞄准 -> 右键 -> 等确认入睡
  ```
  原样移植的文件不要求补注释；移植时改过的地方必须有。
- 其余写法以 [08-实现规范](08-实现规范.md) 为准。

### 文档与日志

- 设计文档、领域清册与规格、移植清单放在 v2 仓库的 `docs/design/`，进 Git。临时计划、日志、草稿放 `docs/tmp/`，不进 Git，**不要对被忽略的文件强制添加**。
- v2 每实现一个领域，在同一个提交里于根目录 `CHANGELOG.md` 的 `## [未发布]` 下按领域加一条：写游戏里变了什么，不写改了哪个类。
- 改了某个能力的实现或契约，同步更新对应的能力文档。

### 原生操作的原则（所有行为模型和能力都必须遵守）

- **LLM 负责设计、观察、纠正；Mod 负责执行已授权的原生操作，并如实报告实际效果。** 不要用代码替 LLM 判断一个设计聪不聪明、能不能工作。
- **不得用"预测会失败"提前拒绝本来可以尝试的原生操作。** 让原版和模组自己结算，再如实回报。
- **原生动作成功了没有，和目标达成了没有，分开判断。** 已确认的消耗和世界变化不能因为结果不合预期就记成"未知"；动作成功也不能冒充目标达成。
- **身体维护（吃饭、备餐、回血、睡觉）没达成，不能把仍可执行的主任务判失败。** 结清这次维护，记下事实，然后继续主任务。
- 原生拒绝要如实返回，不得通过直接改世界、改背包或伪造回执来强行成功。服务端只作证，不替角色动手。

### Amaidesu

- 只改 `Amaidesu` 里的 Minecraft 游戏 Agent。Harness 的通用编排和其他游戏目录不动；确实需要改，先说明范围、原因和影响，等同意。
- `Amaidesu` 的 `dev` **绝不推** `main`。

## 三、验证命令

```bash
./gradlew :common:<回归组名>              # 只跑一个回归组
./gradlew :common:architectureRegression   # 架构护栏
./gradlew :common:contractSnapshotRegression    # 契约快照
./gradlew :fabric:build :neoforge:build    # 只出安装包
```

Windows 下用 `.\gradlew.bat`。长时间的回归和打包放到后台运行，中途只报关键进度。

## 四、标准做法

### 4.1 移植一个文件（阶段 1 及之后）

1. 在移植清单里先登记一行：v1 路径、v1 提交号、目标路径、计划做的整理。
2. 原样复制，只改 `package` 与 `import` → 提交（"移植：……，无逻辑变化"）。
3. 按清单做整理（删掉领域特判、改用注入的服务、补 `Reach` 等）→ 单独提交，改过的地方补中文注释。
4. 架构护栏通过后才算完成。

### 4.2 写领域清册（阶段 4 的卡片 a，读 v1）

只清点，不评价，不修改 v1。模板：

```markdown
# <领域> 旧逻辑清册（v1 提交 <哈希>）

## 1 范围
| 文件 | 行数 | 角色（翻译 / 执行器 / 任务单 / 钩子 / 反射 / 提醒 / 测试） |

## 2 主流程
从公开能力到原生操作的实际调用链，按代码写，不按文档写。

## 3 规则条目
| 编号 | 位置（文件:行） | 触发条件 | 效果（拒绝 / 失败 / 提问 / 重试 / 特例 / 常量） | 注释里给出的理由（摘要） | 来源提交（git log -L 或 blame） | 覆盖它的测试 | 实机事故编号 | 建议类别（可选，写明把握程度） |

## 4 向 LLM 提问的出口（逐个列出问题和选项）
## 5 失败出口（按失败类型统计，并列出位置）
## 6 常量与阈值
## 7 跨领域依赖（引用了哪些其他领域的类，各用来做什么）
## 8 当前对外契约（参数表摘要）
## 9 现有测试（测试类 → 它断言的行为要点）
## 10 v1 直播中在这个领域出过的问题（来自 v1 维护记录）
```

规则条目要**全**：所有会让角色"不做、换做、等一等、问一下、失败"的分支都算。宁可多列，不可漏。完整的样板见 [06-试点规格-睡觉](06-试点规格-睡觉.md) 第 5 节。

### 4.3 实机问题处理规程（最重要的一条）

实机或测试暴露问题时，**先归类，再动手**：

| 问题属于 | 在哪里修 | 例子 |
| --- | --- | --- |
| 缺了一条游戏事实 | 把事实加到它归属的模型或平台层（只加一次），并在常量注释里写明类别 F 与来源 | 醒来的实体包和时间包不同刻到达 |
| 某个行为模型有缺陷 | 改那个模型；所有用到它的能力一起受益 | 遮挡时换工位的候选不够 |
| 规格没想到这种情况 | 停下来，补规格，经批准后再改实现 | 床被别的玩家占了怎么办 |
| 实现没按规格写 | 按规格改实现 | — |

每一类都要补一个能重现该场景的离线测试或实机验收项。**不允许**在出问题的执行器里加一条只为这次场景服务的特判。

### 4.4 实现一个领域（阶段 4 的卡片 c）

1. 读批准后的规格，列出要建的类（08 第 1 节的标准结构）。
2. 先写决策类和它们的离线测试，再写执行器和子步骤替身测试，最后写模块注册、契约资源。
3. 更新契约快照（显式更新，并在提交说明里写清变化）、`CHANGELOG.md`、能力文档。
4. 交给两位做实机验收；验收中发现的问题按 4.3 处理。

## 五、遇到问题怎么办

| 情况 | 做法 |
| --- | --- |
| 规格与游戏现实对不上 | 停下来，把具体出入写清楚，交给 Claude 或两位决定 |
| 想复制 v1 的一段代码 | 先登记进移植清单；不属于底座的代码不移植，按规格重写 |
| 护栏挡住了你认为合理的写法 | 不要绕过，提出来讨论 |
| 和别人的提交冲突 | `rebase` 解决；不确定该保留哪边就问；不强制推送 |
| v1 直播出了问题 | 只有接到明确的 v1 修复工作包才动 v1；修法以最小改动为准，并在对应领域清册里记一笔 |
