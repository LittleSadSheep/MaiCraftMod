# 文件职责与收敛清单

当前重点：让一个功能从哪里进入、在哪里执行、在哪里判断成功变得容易看懂，并找出可以退役或合并的文件。本轮只给判断依据和注释，不执行删除、合并或逻辑调整。

这份清单随全项目审计继续补充；“建议合并”不等于已经证明所有关联改动都可以直接落地。

## 更大的职责收敛点

**F22：整套旧移动执行层可以成组评估退役。** 项目自己的 Moves 表没有当前调用者，Movement.setExecutionDelegate 也没有绑定调用；现用搜索与执行使用内嵌 Baritone 的另一套类型。候选是 Moves、Input、MovementState、MovementStatus、MutableMoveResult，八个 MovementAscend／Descend／Diagonal／Downward／Fall／Parkour／Pillar／Traverse，MovementPlacement，以及 core/pathing/execute/AimProcessor。这十五个文件在本次改注释前合计 3262 行，均位于项目自己的 core/pathing 下；baritone 目录及 LookBehavior 内部的同名类仍在使用。

这里需要先收回少量现用帮助方法：Movement.feet/pathStart 仍被移动入口调用，AimGeometry 的角度与碰撞中心仍用于挖掘，BuildPlacementRegistry 的 Provider 和确认回调仍连接着现用施工。建议把这些现用部分归到已有帮助代码，删去它们为旧执行器保留的分支，再退役整组旧文件。这样可以直接减少整套重复的动作概念，而非只合并几个小记录。

**F23：旧搜索快照与当前性能计时拆清归属。** CachedNavView、LoadedChunks 和 PathCaches 的快照生成只通向旧 forSearch 接口；当前每次更新调用 PathCaches.clientTick，实际负责性能计时通知和清掉失效条目，并不在每次更新复制区块。若退役旧搜索接口，可以一起退役这些快照；现用的 NavProfiler.clientTickPulse 直接放回已有客户端更新入口。ContextFactory.forExecution 和 LoadedOnlyView 仍用于挖矿、找方块和施工，应保留其现用职责。

**F09：明确两套建筑设计入口的产品定位。** 当前 AbilityAdapter.build 依次分到固定工程续建、显式模型／蓝图、旧 SemanticBuildPlanner 房屋模板。它们共享底层施工，但前面的设计生成与准备仍分两套。旧规划器约 1622 行，新建模也有一组对象、编译、保存与导出代码。建议决定以哪条为主要入口：如果让 LLM 负责具体设计，Mod 可以集中负责模型检查、选址约束与执行；若还需要一键模板，明确保留少量模板能力，避免两套都不断扩成通用设计系统。本轮不擅自删掉任何现有能力。

**F10：加工任务不应重新实现一套获取材料规划。** 已审过的 SemanticCookCompanionTask 约 1804 行，包含配方路径索引、递归取材估价和来源推断；实际取材又交给 SemanticAcquire。对应语义审计 D19，已有 nearby 来源缺失、库存被重复计入等具体后果。建议把获取规则收回共用的获取材料层，加工任务集中处理设备、批次和完成条件。优先复用现有代码；需要新增共享单元时，应同时删掉重复实现，避免整理过程中继续叠加外壳。

**F15：任务准备可以沿用已有的直接返回方式。** 当前通用工具路径是“准备派发任务 → TaskDispatch 的临时捕获器拦住 → IntentTask 取回任务单再执行”。机器与电梯已经直接返回现有的 IntentAction.Native；即时查询也已有 Report。建议其他合适能力逐步复用这种明确返回方式，保留参数解析，减少旧工具包装和隐式捕获。可直接收敛到项目已经有的表达。例如勘察已有 Goal，当前先 toJson，再由 SemanticBuildSiteInvestigationTool.fromJson 重建 Goal，生成任务单后又被 capture 接回；直接返回现有 Native 任务单即可作为明确的重构候选。

**F16：共有字段直接依赖共有数据。** 打开菜单现在会构造一份“拉杆控制请求”来校验位置，还填了一个没有业务用途的 false。共同的观察范围与身份应由共同的已有观察数据／校验负责，避免改拉杆规则时连菜单打开也受影响。

**F17：兼容加载器的规则集中处理。** 构建交互识别已经用与方法名无关的签名检查，机器槽位识别却写死开发名 getItem，实际 Fabric 包中已验证失败（A84）。整理应让这种跨加载器约束有明确归属，而不是每个业务各猜一套反射规则。

**F18：模组规则回到对应集成，退役仅剩测试的普通安装帮助代码。** MachineInstallation 的现用部分集中在 AE2 电缆、面板、宿主和落点预测，调用者是机器计划、勘察、装配和验收；普通 block/BlockSpec 仅剩测试调用。建议把现用 AE2 规则与已有 Ae2ReflectionBridge 的职责一起整理，删掉没有生产入口的普通安装分支，让机器主流程只表达装什么、按什么顺序装，不再让读者以为这里还有一套通用方块安装器。该整理需要核对现有 AE2 桥的接口，不能只搬名字。

**F19：工具方法不应让每项配置都绕到验收类。** 多个 Mekanism 帮助类仅为调用一个无参反射方法，就依赖 MachineCommissioning.call。MachineCommissioning 同时收集三种模组的观察数据。建议整理时把各模组访问规则收回现有对应桥接类，验收层组合这些读取结果；不为这一个反射方法再增加新的“通用框架”文件。

**F20：空手准备沿用现有装备动作。** 打开菜单／拉杆控制各自寻找空快捷栏，而装机器时使用既有 UnequipCompanionTask，可以腾出主手。它们解决的是同一件事，已有实现能力也不一致（D40）。可以统一到现有装备任务，减少业务执行器里重复的物品切换分支。 新增的 BuildDoorStateRepair 又自行选择空副手，而原版开门只接受主手（A88）；这不只是代码重复，已经产生实际行为差异。

**F21：设备展开只做一次，当前已由另一任务处理。** 原来两个布局文件各自按“名称[编号]”展开，会与用户名称冲突（A87）。已复核 7921abb3：现由 SemanticMachineLayout 一次生成独立实例编号和分组，MachineLayoutAeNetworks 复用它们，显示名称保留作报告。这项无需再作为待合并任务重复做。

**F25：导航和换气自救共用“能不能浮到空气”的空间判断。** 两边分别向上找水面、找透气口，却都把含水实体当作可穿过的水（A92）。可把完整上浮通道的碰撞检查收在现有水中空间帮助代码中；游泳路线的阶段和自救任务的抢占仍各自负责。不要为了共享三段重复规则再增加一套控制框架。

**F26：真实加载判断应在现场读取入口统一说明和选用。** 当前多个业务各自把 hasChunkAt 当成加载验证，但原版客户端的含义不符合预期（A104）。通用几何函数接受 loaded 谓词的接口本身有用，问题在现场调用者传入了错误依据。可复用原有的实际缓存检查，不需要再给每个业务新建一个“安全检查器”；测试也应验证一次真实客户端入口。

**F27：机械接线删减失去来源的旧分支，保留实际三段流程。** 当前生产计划全部来自 CreateProgressiveSurvey；CreateMechanicalPlanner 的同步入口不产生成功计划。建议整理为已有前置检查、渐进调查、实际施工三段，退役 D57 所列旧成功分支与无人调用的旧单格调查方法。Planner 内的现用搜索和站位帮助不能连带删除。栏位恢复的共同校验应落在实际 restore，而不只放在续接入口（A107）。

## 应保留清楚边界的地方

**F24：移动目标的筛选由移动负责。** NearestBlockFinder 为了找“可以走到旁边的方块”，调用 MineCompanionTask.plausibleToBreak；因此连走近冰块也会被“不要挖冰”挡住（A89，实际内存对照已确认）。共用方块读取和位置数据即可，挖矿的破坏条件不应接管移动目的地是否有效的判断。这可以直接修改已有筛选逻辑，无需再增加一层通用协调器。

- 服务器是否处理了这次右键，与方块是否变成期望结果，是两个检查。`BlockUseConfirmation` 和 `BuildPlacementConfirmation` 的分工有实际作用，不能仅因名字都带 Confirmation 就合并。
- 输入控制与路径规划分别决定“现在按什么键”和“应该走哪里”，还会被多种任务复用。它们需要明确接口，整理重点是接口是否真正被调用。
- 现用导航的三处分工有实际用途：EmbeddedBaritoneNavigator 保存“这一趟路”的目标和结果，EmbeddedBaritoneRuntime 决定当前哪趟导航操纵玩家，EmbeddedBaritoneActionBridge 把挖掘、点击和选栏请求交给原生操作。它们与 F22 那套无执行入口的旧代码不同。
- 地图里的方块、保存的建模对象和固定施工单，是不同数据。可以共用状态解析，保留各自的存储含义；先解决重复编译和重复校验，不通过硬合并文件混淆它们。
- Mod 适配需要隔离可选依赖；不把所有反射代码混到通用任务里。应把某个 Mod 的规则集中放好，避免普通任务重新猜一遍。

引用分析不能只扫项目自己的包。GroundPathSmoothing、GroundJumpContinuation 和 WaterLandingWindow 在自己的包里看似无人调用，实际由内嵌 Baritone 调用；Fabric 入口由资源配置加载。它们已从无调用候选中排除。

F04 的范围是 PlayerNav 保留的旧成本接口和 BuildCalculationContext。ContextFactory.forExecution 仍被挖矿与邻近方块搜索直接调用，LoadedOnlyView 仍用于施工读取已加载方块；不能把这些现用帮助代码一起删掉。PathPlannerPool 虽然放在旧计算目录，也仍在给内嵌 Baritone 和地形检查提供后台线程。

现用 BoatNav 有独立的划船入口，不能因为另有步行导航就判为多余；但一格宽水道漏检船身、短段结束即转步行等问题应先明确（A94、D51）。NavProfiler 则是部分接入：卡顿采样仍用，五秒汇总和搜索完成记录没有调用（D50），可按实际需要缩减旧部分。

喷气背包这组文件目前有真实分工：JetpackFlightSession 管一趟飞行的阶段，JetpackNativeAdapter 负责模组状态和开关，JetpackRoute 找路线，JetpackFastDescent 管加速下降。其余文件分别处理估计运动、按键、镜头、平台和故障说明。可以把很短的按键／镜头帮助方法整理到同一现有控制帮助类，但不能仅按文件短就把运动计算和模组协议混在一起。总控中的完全重复行已列 D52，可先直接清理。

移动结构的坐标、碰撞、甲板候选与展示有不同职责：StructurePose 转坐标，SableStructureBridge 读原生数据，PhysicalObstacleSnapshot 提供导航障碍，StructureDeckGeometry 找可站面，ShipLandingTarget 跟踪并确认登船，MCP 文件整理观察结果。这几层共享同一甲板判断；A97 是共享判断内部把读取范围扩大成禁止范围，修正应落回该判断，不能在每个调用者外面各补一套例外。

AE2 的主要阅读顺序是 Ae2ResourceSupply（请求到底表示什么）→ Ae2SupplyPlanner（选哪些物品、装在哪）→ Ae2SupplySession（访问、取物、制作、确认、归位）。Ae2TerminalAccess 管终端位置，Ae2ReflectionBridge 管模组接口。这里最大的负担集中在会话近两千行和许多阶段；先整理“进入收尾”和“收尾失败”的关系（A99），并让库存最终检查对应请求含义（A100），再考虑把相邻阶段及其状态收在已有模块中。

电梯代码分成原生读取与操作、勘察几何、运动执行和整个乘梯流程。两个具体整理方向是让危险接触沿用共用规则（A102），并把“先距离排序”放在完整候选成立之后（A103）。明确电梯身份的读取与通用展示限量也应分开处理（D56）。

Ponder 的文字读取与结构回放确实是不同工作：PonderInstructionReader 只提取日程文字，PonderNativeReplay 在独立演示世界推进，PonderStructureSnapshot 做几何投影，PonderKnowledgeSource 整理给模型读取的资源。这里不宜把全部文件硬合成一个读取器；可先消除空区域的无关投影限制（A109），再决定旁白分页是否复用编译结果（D61）。

### F28 · 两条结构查找入口中，一条只剩固定失败

LocateStructureTool → LocateOps → LocateStructureTaskRecord → LocateStructureCompanionTask 仍注册为内部工具，但未发现现用语义入口调用；它不查世界线索、不能成功；真正按已看到的事实寻找结构的是 PhysicalStructureSearchCompanionTask。先决定旧入口是否连接到它或停用，再判断薄转发文件是否有保留价值。不能将只读登记表检查描述成已完成结构定位，详见 A113。

聊天的文件各自对应实在的步骤：ChatMessage 检查一句话是否合法，ChatTyping 决定打字进度，ChatScreenView 管实际输入框，ChatSession 管一次提交和人的接管，ChatTask 接入任务调度。它们并非五种聊天实现；注释已写明每步管什么，成功只表示交给原版客户端，不保证服务器收到。

### F29 · 原地交互仍带有已经不用的移动遗留

InteractAtCompanionTask 当前 buildNav 返回 null，超出触及范围就让上层先移动；类里却还保留 WALK_SPEED、没有调用的 repositionable 和“首次寻路失败”等错位注释。与之不同，InteractEntityCompanionTask 的自动靠近和一次换站位仍在使用。可以整理前者遗留，不能因为名字相似就把后者一起删掉。

FollowCompanionTask 的“默认跟主人”旧注释也已过时：现用 FollowTool 要求选定实体，并记录 UUID；null 目标只会睡眠，没有默认主人查找。注释已按当前路径改写，是否删除空目标旧分支由后续决定。

## 大文件怎样处理

已读的获取材料执行器有约 2772 行，加工执行器约 1804 行，普通建造执行器约 1579 行。整理建议是先列出完整流程，再把同一阶段的状态、判断与动作收在一起；现有帮助类能承担的就归入现有位置。先退役旧路、消除重复规则，再决定需要几个真正独立的模块。

下一轮若开始重构，可先做 F01–F03 这种证据清楚、能直接减少误导性入口的项目，再处理仅一处使用的小辅助和重复契约。具体删除、合并和接口调整仍由你决定。
