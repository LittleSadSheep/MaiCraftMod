# 09 命名与术语

读代码的 AI 和调 MCP 的 AI 往往只看名字就动手，不会先去读设计文档。名字起得含糊或会被读成别的意思，它们就会按错的理解写代码、调接口，项目就这样一点点跑偏。所以命名在这里当作设计来做：本文列出命名原则、审出来的易误解词和改法、全部核心术语，以及没改的词为什么不改。

代码里的类型名、包名、MCP 字段、文档用词，都以本文为准。

## 1. 命名原则

1. **说人话**：用玩家和普通程序员都会说的词。不用比喻（"差事""工位""护栏"），不用行话（"仲裁""对账""句柄"），不用生造的缩写。
2. **脱离上下文也不会被读成别的意思**：起名时问一句"只看这个名字，Java 程序员、Minecraft 玩家、调 MCP 的 LLM 会以为它是什么"。会被读成线程池、网络端口、药水效果、集成测试、OP 权限的词，一律换掉。
3. **一个名字只指一样东西，一样东西只有一个名字**：代码、文档、MCP 字段、日志用同一个词；同一个词不能在两层里指两样东西（例如"步骤"只指目标里的一步，任务里的一段叫"动作"）。
4. **中文和英文一一对应**：每个核心概念有一个中文说法和一个英文名（第 3 节），写文档用前者，写代码用后者，不另造同义词。
5. **枚举值直接回答一个问题**：例如"此刻能不能打断"的取值是"两个动作之间 / 正常干活 / 停下不安全"，读到值就知道该怎么做，不需要再查注释。
6. **不用空泛的词**：类型名里不出现 Manager、Helper、Util、Info、Data 这类词，按它实际做的事起名。
7. **注释写含义和原因，不写出处和历史**：不写"见某文档第几节"（文档会改）、不写"v0 是这样做的"（版本对比会过时，历史看 git log）。

后三条中可以机械检查的部分由构建检查（`SourceRulesTest` 与测试资源 `naming-rules.txt`），违反时构建失败，失败信息里写着原因和改法。

## 2. 审出来的易误解词

v1 奠基时第一版命名里，以及准备从 v0 移植的代码里，脱离上下文会被读成别的意思的词，全部列在这里。左边的叫法已经不用。

| 原来的叫法 | 不看上下文会被理解成 | 现在叫 | 意思 |
| --- | --- | --- | --- |
| 可打断程度 `DELICATE`（精致/精细） | 东西做得精致；看不出和"能不能打断"有什么关系 | `UNSAFE_TO_STOP` 停下不安全 | 悬空、贴边、驾驶中、正等游戏确认交互结果，现在停下可能更危险 |
| `FREE` / `BUSY` | 空闲 = 没有任务 | `BETWEEN_ACTIONS` 两个动作之间 / `WORKING` 正常干活 | 有任务，只是此刻手上没有进行中的动作 |
| 急迫程度 `COMFORT` / `HARMFUL` / `LETHAL` | 舒适 = 一种好状态；看不出要多快处理 | `LATER` 找空当 / `SOON` 尽快 / `NOW` 立刻 | 直接回答"多快必须处理" |
| 反射、身体需求、身体维护 | 反射 = Java 反射 | 生存需求 `SurvivalNeed` | 坠落、溺水、着火、被打、饥饿、天黑、太暗…… |
| 身体仲裁、`PreemptionRule` | 仲裁 = 法律或分布式系统里的仲裁 | 打断规则 `InterruptRule` | 生存需求能不能打断手上的任务 |
| `kernel.schedule` | 定时任务（`@Scheduled`、cron） | `kernel.interrupt` | 每刻决定角色听谁的 |
| 差事 | 看不出和任务什么关系 | 临时任务 | 生存需求创建的、插进来的任务 |
| 执行器、`PhasedExecutor`、`ExecutorRegistry` | Java 的 `Executor` 线程池 | 任务 `Task`、分阶段任务 `PhasedTask`、任务工厂表 `TaskFactories` | 逐刻控制角色做一件事的对象 |
| 子步骤 `Step` | 目标里的"第几步" | 动作 `Action` | 任务在一个阶段里做的一件具体的事 |
| 任务单 `TaskRecord` | 数据库里的一条记录 | 任务输入 `TaskInput` | 要做什么，不可变 |
| 任务句柄 `TaskHandle` | 操作系统句柄、文件句柄 | 任务运行 `TaskRun` | 一次任务运行的记录：编号、状态、结果、起止时刻 |
| `TaskStatus` | 和 `TaskState`、结果状态三个"状态"分不清 | `TickResult` | 推进一刻后的情况：还在做，或已有结果 |
| 统一回执 `Outcome` | 回执 = 收据；`Goal.outcome` 又是"想要的结果"，同词两义 | 任务结果 `TaskResult`；目标里的那句话叫 `purpose` | 任务做得怎样 |
| 卡点 `Blocker` | 看不出是"问题"还是"阻塞线程的东西" | 问题 `Problem` | 卡在哪、怎样能继续 |
| 效果 `Effect` | Minecraft 的药水效果（状态效果） | 变化 `Change` | 已确认在世界里发生的变化 |
| 事实 `Facts` | 太泛 | 结果细节 `ResultDetails` | 能力特有的结果字段 |
| 未确认 `uncertain` | 不确定 = 不知道要不要做 | `unconfirmed` 没能确认 | 已提交、但游戏没确认结果的交互 |
| `NEED_TOOL` | MCP 里的 LLM 会读成"需要调用另一个 MCP 工具" | 并入 `NEED_ITEM` | 缺够格的镐、斧之类，就是缺东西 |
| `NEED_CONSENT` | — | `NEED_APPROVAL` | 和"许可"配套：超出许可要 LLM 同意 |
| `NATIVE_REFUSED` | 原生 = native 代码 | `REFUSED_BY_GAME` | 游戏或模组拒绝了这次交互 |
| `TIME_WINDOW` / `WORLD_RULE` / `STALLED` / `INTERNAL` | 不够直白 | `WRONG_TIME` / `NOT_POSSIBLE_HERE` / `STUCK` / `INTERNAL_ERROR` | — |
| 授权 `Mandate` | 授权 = 登录鉴权；mandate 是生僻词 | 许可 `Permissions` | 这次任务允许角色改变世界到什么程度；**不是** OP 权限，被服务器拒绝属于 `REFUSED_BY_GAME` |
| `upkeep`（许可里的开关） | 维护费 | `survival_needs` | 是否处理生存需求；不叫 `survival`，免得被读成生存模式 |
| 提问 `Decision` | 决定 = Mod 自己做的决定 | 问题 `Question`（向 LLM 提的问） | 只允许三种原因 |
| `IntentAction`、`PENDING` | 和任务状态 `PENDING` 同名不同义 | `StepDecision`、`NOT_READY` | 能力对这一步的决定；信息还不全 |
| 翻译（能力看现场决定下一步） | 语言翻译、Minecraft 的翻译键 | 决定 `decide` | — |
| `StepHooks` / `ChildOutcome` | — | `AbilityHooks` / `AfterTask` | 能力的特殊处理 |
| 句柄、观察句柄、`ref` | 句柄 = 系统句柄；ref = git 引用、React ref | 观察编号，字段名 `id` | `e12`、`f3`、`b5` |
| `Bearing` / `bearing` | 机械轴承；航海用语 | `toward`（目标对象里）、`direction`（观察视图里） | 朝哪边 |
| 目标（同时指 Goal 和 Target） | 两样东西一个词 | 目标 `Goal`、目标对象 `Target` | 想要的结果；要去的地方或要处理的东西 |
| 契约、契约正文 `ContractText` | 合同；design by contract | 能力说明 `AbilityDoc` | 写给 LLM 看的能力用法 |
| 能力描述符 `AbilityDescriptor` | 文件描述符 | 能力规格 `AbilitySpec` | 关于一个能力、不随运行变化的全部信息 |
| 能力可见性 `Visibility` | 感知里的"看得见" | 是否列出 `Listing` | 是否出现在默认的能力列表里 |
| 参数词汇表 `ParamVocabulary` | — | 参数名表 `ParamNames` | 登记过的参数名及含义 |
| 参数 `action` | 和"动作 Action"同名 | `operation` | 一个能力内部的几种操作选哪一种 |
| `count` 的两种意思 | "再多几件"还是"背包里总共几件"、"做几次" | 统一为"这次要多做多少" | 不是背包里的总数 |
| MCP 工具 `wait` | 和能力 `wait`（在游戏里等条件）同名 | `events` | 按游标读任务事件 |
| `observe(what="memory")` | LLM 的对话记忆 | `world_memory` | 角色记得的地点、容器、资源 |
| Attention 事件 | 机器学习里的注意力 | 任务事件（Amaidesu 一侧仍可叫 attention） | 任务开始、提问、结束…… |
| 身体、伙伴、`BodyContext` | 身体 = 实体的身体朝向；伙伴 = 宠物 | 角色、`PlayerContext` | Mod 控制的本地玩家 |
| 身体端口、`*Port` | 网络端口 | 按用途起名，例如 `PlayerInput` | 移植 v0 的端口类时改名 |
| `ClientActorBoundary` | actor 是戏剧与 v0 的旧叫法 | 玩家控制权边界 `PlayerControlBoundary` | 每刻确认谁能操作本地玩家、上下文何时失效 |
| `InputLease`（`ItemUseInputLease`） | 租约 = 合同；lease 不说明占用的是什么 | 按住使用键 `UseKeyHold`（待集成时接入） | 任务已开始的那次持续使用，原版只在仍按住时给出按住投影 |
| 平台层 `platform` | MultiLoader 模板里 platform 专指加载器抽象 | 游戏接口层 `game` | 和 Minecraft 客户端直接打交道的地方 |
| 对外入口 `gateway` | API 网关 | MCP 入口 `mcp` | 内嵌的 MCP 服务 |
| 联动 `integration` | 集成测试 | 联动模组 `compat` | Create、AE2、Mekanism 等的适配 |
| 协议 `protocol` | MCP（Model Context Protocol） | 网络消息 `network` | 客户端与服务端 MaiCraft 之间的消息 |
| `platform.server` | MCP 服务 | `game.serverlink` | 和服务端 MaiCraft 通信的客户端一侧 |
| 行为层包 `reach` / `act` / `procure` / `upkeep` / `mandate` / `attempt` / `memory` | 看不出是什么，或者有别的意思 | `approach` / `interaction` / `acquire` / `survival` / `permission` / `retry` / `worldmemory` | 见第 4 节 |
| `Reach`（伸手距离） | — | `InteractionRange` | 与 Minecraft 的属性名 interaction range 一致 |
| `Condition` | 战利品表的条件等 | `WaitCondition` | 要等的条件 |
| 进度表 `ProgressMeter`、停滞窗口 | 仪表 | 进度跟踪 `ProgressTracker`，`Stuck` / `TimedOut` | 多久没进展算卡住、最多做多久 |
| 旁证、作证 | 法律用语 | 服务端确认、确认信息 | 服务端告诉客户端交互的真实结果 |
| 对账 | 财务用语 | 确认 | 提交交互后逐刻核对游戏有没有生效 |
| 心跳、装配 | 网络心跳；机械装配 | 每刻推进、启动时创建与登记 | — |
| 底座、换芯、护栏、清册、分诊、门控、信封、投影 | 比喻或行话 | 基础代码、重写、架构检查、旧逻辑清单、归类、拦截、返回格式、整理 | — |
| 讲道理的伙伴 | 看不出具体指什么 | 像正常玩家一样 | 默认许可的取值 |

## 3. 术语表

### 3.1 一件事从下达到完成

```text
目标 Goal              LLM 想要的一个结果（"去睡觉"）；sequence 的目标里有几步
└─ 步骤 step           目标里的一步；能力看现场对这一步做出决定 StepDecision
   └─ 任务 Task        逐刻控制角色做一件事，每次运行新建；输入是 TaskInput，运行记录是 TaskRun
      └─ 阶段 phase    分阶段任务 PhasedTask 的进度，例如"选床 → 拿床 → 放床 → 走到床边 → 躺下"
         └─ 动作 Action  一个阶段里做的一件具体的事，例如"走到能看见床头的站位"
            └─ 原生交互  发给游戏的一次正常交互：右键、攻击、挖掘、点容器界面
```

| 中文 | 代码 | 意思 |
| --- | --- | --- |
| 角色 | `PlayerContext`、`localPlayer()` | Mod 控制的本地玩家。"玩家"指人类玩家或其他玩家 |
| 目标 | `Goal` | LLM 想要的一个结果，只说要什么，不说怎么做 |
| 目标对象 | `Target` | 要去的地方或要处理的东西：`here`、`seen`、`landmark`、`position`、`player`、`direction`、`previous` |
| 观察编号 | `Target.Seen.id`、MCP 字段 `id` | observe 给每样看到的东西的编号，`e` 实体、`f` 地形特征、`b` 方块或设施 |
| 步骤 | `StepContext` | 目标里的一步 |
| 这一步的决定 | `StepDecision` | 还没准备好 / 直接给结果 / 运行一个或几个任务 / 提问 / 记住地点 / 等条件 |
| 任务 | `Task` | 逐刻控制角色做一件事的对象 |
| 任务输入 | `TaskInput` | 要做什么，不可变，能存盘和比较 |
| 任务运行 | `TaskRun` | 一次任务运行的记录，LLM 用 task 工具查到的就是它 |
| 任务状态 | `TaskState` | `PENDING` 没开始 / `RUNNING` 进行中 / `FINISHED` 已结束 |
| 推进一刻的情况 | `TickResult` | 还在做，或已有结果 |
| 分阶段任务 | `PhasedTask` | 所有任务的基类 |
| 阶段 | 各任务自己的枚举 | 分阶段任务的进度 |
| 动作 | `Action`、`ActionStatus` | 一个阶段里做的一件具体的事，由玩家行为层提供 |
| 原生交互 | `game.interaction` | 像真人玩家一样通过游戏的正常交互做事，不直接改世界或背包；先提交，再逐刻确认 |
| 提交交互 | `InteractionSender` | 向游戏提交一次原生交互的入口；同一时刻只允许一项动作在等确认 |
| 逐刻确认记录 | `PendingInteraction` | 一次已提交交互的等待状态：何时提交、等多久、观察到什么才算结束 |
| 交互确认 | `InteractionConfirmation` | 操作后如何检查结果；只读当前客户端事实，不自动证明服务器已确认 |
| 交互机会 | `InteractionOpportunity` | 每刻一次的交互名额，世界动作、菜单点击和模组协议共用 |
| 界面操作 | `MenuActions`、`PendingMenuAction` | 容器界面的原生点击、搬运与关闭；一次操作的等待记录 |
| 交互瞄准 | `Interaction`、`BlockDigger`、`FirstPersonInteractionTargeting` | 把一次鼠标操作或挖掘拆成瞄准、出手、确认几刻完成 |
| 子任务 | `kernel.child` | 一个步骤或组合任务运行的另一个任务 |
| 任务工厂表 | `TaskFactories` | 任务输入类型 → 创建任务的工厂 |
| 目标推进器 | `GoalRunner` | 把一个目标逐刻推进到有结果的对象，本身是一个任务 |
| 目标运行 | `GoalRun`、`GoalRunState` | 一次目标推进的记录：编号、目标、处境、进行到第几步、结果 |
| 目标运行存储 | `GoalRunStore` | 目标推进的记录在这里保存与读回；内核只认这个接缝 |

### 3.2 结果

| 中文 | 代码 | 意思 |
| --- | --- | --- |
| 任务结果 | `TaskResult` | 所有能力共用的结果结构，见 07 第 6.1 节 |
| 结果状态 | `TaskResult.Status` | `DONE` / `PARTIAL` / `FAILED` / `CANCELLED` |
| 问题 | `Problem` | 卡在哪（`message`）、怎样能继续（`suggestion`）、种类（`kind`） |
| 变化 | `Change` | 已确认在世界里发生的变化 |
| 没能确认的交互 | `unconfirmed` | 已提交、游戏没确认结果；不能盲目重做 |
| 试过的办法 | `Attempt(tried, result)` | 换过的办法和结果摘要 |
| 结果细节 | `ResultDetails` | 能力特有的结果字段 |
| 向 LLM 提问 | `Question` | 只允许三种原因：`NEED_APPROVAL`、`CHOOSE_ONE`、`UNCLEAR_TARGET` |
| 重试策略 | `behavior.retry.RetryPolicy`、`RetryDecision` | 一个办法失败之后怎么走：同一个办法再试、换下一个办法，还是带着完整事实结束；同一种失败重复有上限 |
| 退避 | `behavior.retry.Backoff` | 同一个办法再试之前等多少刻：按失败次数逐次加倍，封顶为给定的上限 |
| 提问升级 | `behavior.retry.QuestionEscalation` | 判断该不该向 LLM 提问并把现场事实组织成问句；只有超出许可的失败会升级，其他情况一律不问 |

### 3.3 生存需求与打断

| 中文 | 代码 | 意思 |
| --- | --- | --- |
| 生存需求 | `SurvivalNeed` | 一个正常玩家干活时也会顺手处理的事 |
| 临时任务 | `SurvivalNeed.createTask` 创建的 `Task` | 插进来处理生存需求的任务，做完就结束 |
| 主任务 | — | LLM 下达的任务 |
| 急迫程度 | `Urgency` | `LATER` 找空当 / `SOON` 尽快 / `NOW` 立刻 |
| 此刻能不能打断 | `Interruptibility` | `BETWEEN_ACTIONS` 两个动作之间 / `WORKING` 正常干活 / `UNSAFE_TO_STOP` 停下不安全 |
| 打断规则 | `InterruptRule.canInterrupt` | `NOW` 打断一切；`SOON` 不打断停下不安全的；`LATER` 只在两个动作之间 |
| 控制循环 | `ControlLoop` | 每刻按打断规则决定角色听谁的，并推进那个任务一刻；主任务被临时任务压栈，临时任务做完从原地接着做 |
| 本刻的决定 | `ControlLoop.Decision` | 控制循环一刻的结论：推进了哪个任务、哪个需求插进来（`interrupting`）、谁被规则按住（`deferred`）、有没有任务就此结束 |
| 坠落判断 | `FallDanger` | 读下落距离、生命、下面是不是虚空，给出坠落有多急的纯函数 |
| 溺水判断 | `DrowningDanger` | 读头是否在水里、剩几泡氧气、是否已在掉血，给出换气有多急的纯函数 |
| 被埋判断 | `BuriedDanger` | 读是否卡在实心方块里，给出窒息有多急的纯函数 |
| 生存处境 | `SurvivalSituation` | 每刻从角色身上一次取齐的观察事实（下落距离、生命、头部方块与氧气、会窒息的格子），三个判断各自从中读自己要的；结论仍由判断纯函数给出 |
| 处境读取器 | `SurvivalSituation.SituationReader` | 每刻从角色上下文取一份生存处境的接缝；测试里换成按脚本回答的替身 |
| 换气 | `BreathNeed` / `BreathTask` | 憋到告急时抬头按住跳跃上游、头一出水就结束的临时任务 |
| 刨出 | `DigOutNeed` / `DigOutTask` | 卡在实心方块里时挖开埋住身体那一格的临时任务 |
| 落地防护 | `FallNeed` / `FallGuardTask` | 这一摔会摔死时，对手中的水桶放水缓冲的临时任务；没有水桶就如实交代做不了 |
| 挖一格的动作缝 | `BlockBreaking` | 刨出任务与原生挖掘之间的接缝：朝一格挖一下、回答本刻有没有真挖开 |
| 记住地点的接缝 | `RemembersPlaces` | 目标推进把"记住这个地点"交给它；世界记忆实现它 |

## 5. 考虑过、但保留的词

| 词 | 可能的误解 | 为什么保留 |
| --- | --- | --- |
| MCP 工具 `execute` | Minecraft 的 `/execute` 命令 | 参数是 `goal`，结构上不会和命令混；工具描述写明"不是 /execute，发命令用能力 chat"。改成 `do`、`start` 反而更含糊 |
| `spi` 子包 | Java 的 ServiceLoader 机制 | 意思相同（给别人实现的接口），只是登记方式不同；package-info 写明"启动时明确登记，不用 ServiceLoader" |
| 能力 ability | Minecraft 的 `Player.getAbilities()` | MCP 侧沿用多年，LLM 已经熟悉；术语表写明区别 |
| 玩家行为 behavior | Minecraft 生物 AI 的 `Behavior` | 包名在 `org.maiwithu.maicraft` 下，不会和 Minecraft 的类混用；意思也相近（一段可推进的行为） |
| 内核 kernel | 操作系统内核 | 在应用代码里普遍指核心框架；不叫 core，免得重演 v0 的 core 包什么都往里放 |
| 容器界面 menu | 游戏主菜单、暂停菜单 | 和 Minecraft 代码里的 Menu 同名同义；中文统一说"容器界面" |
| 地形特征 features | Minecraft 世界生成里的 Feature | 意思相近（树林、河流就是世界生成的地物） |
| `server` 包 | MCP 服务 | Minecraft 模组里 server 普遍指服务端；MCP 相关的代码都在 `mcp` 包，那里不用 server 这个词 |
| 原生交互 | 原生 = native 代码 | 沿用 v0 规则里的说法；术语表写明"像真人玩家一样通过游戏的正常交互" |

## 6. 新增一个名字时

1. 先查本文有没有现成的说法，有就用。
2. 没有就按第 1 节起名，问一句"只看名字会被读成什么"。
3. 在第 3 节（或第 4 节）加一行；如果它替换了一个容易误解的叫法，在第 2 节也加一行。
4. 要防止旧叫法回来的，把它加进测试资源 `common/src/test/resources/naming-rules.txt`（`word` 是类型名里的词，`term` 是中文说法），写上原因和改法。
5. MCP 能看到的名字（工具、字段、枚举值、能力名、参数名）改动时，同步 07，并在 `CHANGELOG.md` 记一条。
