## 已看部分的发现

（随审查推进逐层补全；已有证据详见 [01-诊断](01-诊断.md)。）

### 第 1 层 入口

规模：`mcp` 包 29 个文件 5683 行，其中 `EmbeddedMcpService` 1425 行、`MaiCraftRuntimeFacade` 1014 行、`PublicToolCatalog` 702 行。

**做对的**

- 手写的 HTTP / JSON-RPC MCP 服务，会话、版本协商、鉴权、来源校验都齐全。
- **超时语义设计得很仔细**：超时后先问运行时"请求开始了没有"，区分"还没动过游戏，可以安全重试"和"已经开始，结果未知"。这是对的，要保留。
- `request_key` 幂等、自动生成、命中计数，思路正确。
- 校验错误会附上该能力的参数签名，方便调用方改正（最近的提交还在加强这一点）。

**问题**

| 严重度 | 发现 |
| --- | --- |
| 严重 | `perceive` 一身兼五职（观察、查能力、查知识库、上网、等事件），13 种 view 共用 17 个参数，`focus` 有 6 种含义 |
| 严重 | **门面层承担了业务规则**：新任务顶替旧任务的策略、从检查点恢复的任务怎样重新挂回调度器、死亡后"复活 / 旁观"答复的特判，都写在 `MaiCraftRuntimeFacade` 里 |
| 严重 | **死亡与重生这一条生命周期散在三处**：门面（答复特判）、`GameplayAttentionMonitor`（908 行，执行原生复活、重生后背包对比）、`IntentRuntime`（死亡决策的持有、退役、收尾） |
| 一般 | 传输层混入领域：错误路径里调用 `MachineDesignRejection.inspectRequest`；知识库冻结回执在传输层特判 |
| 一般 | 工具描述里写具体能力的特例（`plan` 讲 `build_machine`，`task` 讲睡觉白天门） |
| 一般 | 每个工具都带 `server_id`，Mod 不读；`reminders` 附在每一次返回里 |
| 一般 | `GameplayAttentionMonitor` 一个类同时管伤害片段汇总、死亡与重生、反射通知、装备观察、常驻提醒 |

### 第 3 层 编排

**做对的**

- "恢复不等于重新批准"：从检查点回来的任务先暂停，结构级校验，不拿当前规则追溯否决历史任务。
- 世界身份绑定，换世界、换连接后旧任务不会被误用。
- 消费前强制落盘的"提交检查点"（`checkpointBeforeSubmission`），防止重启后重复消费。

**问题**

| 严重度 | 发现 |
| --- | --- |
| 致命 | `IntentTask`（1647 行）按具体任务单类型和能力 ID 写满特例（睡觉 89 处引用、取物、交易、烹饪、施工、探索、机械动力、移动……），任何能力的特殊需求都要改它 |
| 严重 | `IntentRuntime`（1228 行）是上帝对象：计划、任务表、请求键、地标、持久化、世界绑定、死亡决策、提交检查点、Attention、聊天流、校验、控制权、自卫位移……60 多个公开方法，被下层通过单例 `IntentRuntime.get()` 调用 46 处 |
| 严重 | 内核的 `execute` 里点名了施工设计、建筑场景、随行补光三个能力的适配器，为它们走"不占身体"的特殊路径（应由能力自己声明执行方式） |
| 一般 | 决策答复的合法性校验（`validateDecisionAnswer`，约 80 行）集中在运行时里，但决策的含义分散在各适配器 |

### 第 4 层 调度

**做对的**

- "身体只有一双手，每刻只有一个使用者"的模型是对的；被抢占保留进度、等待时不消耗自己的期限，也是对的。
- 换手前检查"现在停下会不会摔"，这条安全考虑是游戏事实，要保留。

**问题**

| 严重度 | 发现 |
| --- | --- |
| 致命 | 仲裁没有"紧急程度"和"能不能打断"的概念，只能靠 `Task` 上 5 个布尔开关和按具体类型的特判（`winner instanceof MLGChain`、`winner instanceof BreathChain`）拼出来，每次实机事故就再加一个豁免 |
| 严重 | 心跳 `ClientRuntime.tick` 按写死的顺序手动推进约 20 个全局单例子系统；顺序本身就是隐性规则，新增子系统只能往里插 |
| 严重 | **随行补光是绕过仲裁的第二个身体使用者**：在主任务之后"借剩余的准星和操作机会"插火把，与主任务之间靠临时规则共享身体 |
| 一般 | 心跳里有能力专属的收尾：丢弃物品后扑火（`DiscardFireCleanup`）、交通收尾、施工预览闸 |
| 一般 | `sync` 槽、空闲姿态、手持锁释放钩子（`HandPinRelease`、`TaskSessionHooks`）这类历史机制仍在，部分已无监听者 |

## 结论

### 一、看全之后的判断

1. **问题不在某几处，而在结构和流程。** 16 层里有 9 条"致命"：内核被能力特例污染、同一机制各写一遍、仲裁靠补丁开关、一个能力散在十几个文件、契约与实现互相矛盾、感知鸿沟、服务端定位没想清、测试锁死实现细节……它们互相加强，所以修一处会在别处冒出来。
2. **v1 真正值钱的是三样东西，而不是它的结构**：
   - 已证明正确的**底座**：身体端口与"提交 → 对账"协议、导航与 Baritone 包装、SQLite 记忆库、MCP 传输与超时语义、知识库、多加载器构建与 CI、模组的反射桥与 mixin；
   - 写在注释和分支里的**游戏事实**（实机换来的）；
   - **模组联动的门道**（Create、AE2、Mekanism、物理载具怎么读、怎么点）。
   这三样都可以搬走或清点出来，不依赖于保留 v1 的结构。
3. **行为本来就要大改**（按游戏常理合并、删补丁、换契约）。"先保持行为不变地整理结构，再改行为"等于做两遍。
4. **现有测试不能当安全网**：三分之一的测试反射进私有实现，结构一动就会大面积失效。
5. **乱的根源是流程**："实机出问题 → 在出问题的地方加一条规则"，没有归属，没有分类，没有架构护栏。开发速度极快（70 天 3000 个提交），换一套代码而不换流程，几周后会再长出同样的东西。

### 二、四种走法

| 走法 | 结论 | 理由 |
| --- | --- | --- |
| A 继续修补 | 否 | 就是现状 |
| B 原地大型重构（先保行为，再逐步改） | 否 | 成本最高：要在没有安全网的情况下保持 20 万行的行为，同时重写测试，之后还要再改一遍行为；旧结构会持续把新代码拉回老样子 |
| C 同仓库渐进换芯（新旧共存，靠桥接） | 可行但不选 | 最难也最终要扔掉的部分是"桥"：新内核要托管旧能力，就得复刻 `IntentTask` 的全部特例、Tool 通道、反射开关；新旧两套跑在同一个 jar、同一个身体上，直播版本随时可能被改坏；隔离只能靠检查规则，挡不住 Agent 照抄旧写法 |
| **D 新仓库重建 v2** | **选这个** | 见下 |

### 三、决定：新仓库重建 v2，v1 冻结维护

```text
v1（本仓库）   冻结：不再加功能，只修影响直播的问题；继续承担直播，直到 v2 达到切换标准
               同时作为"资料库"：清点游戏事实、移植底座文件的来源

v2（新仓库）   从第一天起按新架构写：分层与护栏、对外接口 v2、玩家行为模型、能力模块、实现规范
               底座按"移植清单"从 v1 搬过来（带来源路径与提交号），其余一律按领域规格重写
               服务端作为必需组件重新定义职责：权威结果、归属记录、模组数据读取；不提供透视

Amaidesu       新增一个面向 v2 的 Minecraft Agent，通过配置在 v1 / v2 之间切换（Harness 本来就支持按配置选 Agent）
```

**为什么是新仓库，而不是同仓库新目录**：

- 没有"桥"：v2 不需要托管任何旧能力，最复杂、最终要扔的那部分工作直接省掉；
- 物理隔离：仓库里没有旧代码，Agent 无从照抄；需要的旧东西只能按移植清单显式搬入；
- 直播安全：v1 原样不动，v2 怎么改都不会影响正在用的版本；
- 版本、更新日志、CI 各自独立，不必让 v1 的 `dev` / `main` 规则去兼容两个产品；
- 服务端既然已经是必需的，客户端与服务端的分工最好在一张白纸上重新划。

**代价与对策**：

| 代价 | 对策 |
| --- | --- |
| 功能断档：直播很依赖 Create 机器和飞行器（实测实例就是"机械动力航空学"），这两块合计约 4 万行 | 切换按里程碑分批：生存类直播先换到 v2，机器和载具直播在 v2 达到对应里程碑之前继续用 v1；机器的整机比对引擎和模组读取代码按移植清单搬过去，契约与流程重写 |
| 要同时维护两个版本 | v1 冻结，只修影响直播的问题，不加功能；所有新想法只进 v2 |
| "第二系统综合症"：新系统设计过度、迟迟追不上 | 规格先行、按里程碑交付、每个里程碑都有明确的切换标准；横切模型只做当前领域用得到的部分 |
| 移植文件丢失 Git 历史 | 移植清单记录每个文件的 v1 路径与提交号；v1 仓库永久保留作为档案 |
| 旧存档 | v2 不读取 v1 的任务检查点；提供一次性导入地标、蓝图、机器档案的工具 |

### 四、比"重写"更重要的：换流程

v2 必须从第一天起执行下面五条，否则会重蹈覆辙：

1. **规格先行**：每个领域先有经两位批准的规格（03 第 5 节模板），再写代码。
2. **护栏从第一天起就严格**：分层规则、类与方法大小上限、契约快照、能力 ID 字面量限制，全部进 `check`，没有基线可以冻结。
3. **实机问题处理规程**：实机发现问题时，先判断它属于哪一类——缺了一条游戏事实、某个行为模型有缺陷，还是规格没想到。然后在**该归属的地方**修，并补一个场景测试。**不允许在出问题的地方就地加一条特判。**
4. **约束登记**：任何"拒绝执行 / 提前失败"都要登记类别（03 第 4 节五类），P、G、S 类不允许新增。
5. **设计评审**：规格、对外接口、行为模型的变更由 Claude 评审；具体实现由 ChangingSelf 的 Agent 完成。
