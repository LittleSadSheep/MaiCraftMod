# 02 目标架构（v1）

> 前提：按 [00-全景审查](00-全景审查.md) 的结论，v1 在 `v1` 分支从零按本架构建设；v0 在 `dev` 分支冻结维护，作为直播版本和资料来源。
> 已经写成代码的部分（包结构、内核接口、架构检查）**以代码为准**；本文说明职责、边界与理由，不再复制接口定义。名字与术语以 [09-命名与术语](09-命名与术语.md) 为准。

## 1. 设计原则

1. **一样东西只归一个地方。** 一个能力的知识归它自己的包；一条游戏事实归一个实现；一条约束归一条登记过的规则；一项服务归一层。
2. **内核不认识能力。** 打断、目标推进、子任务运行、进度、存储对所有能力一视同仁。能力需要特殊处理时，通过扩展点挂进来，不改内核。
3. **能力是薄的，玩家行为是厚的。** "怎么像个人一样靠近、瞄准、拿东西、腾背包、吃饭、看、放弃、提问"写一次，放在玩家行为层；能力只负责"这件事要达成什么、按什么顺序组合玩家行为"。
4. **判断和动手分开。** 判断写成读接口、给结论的纯函数，可以离线测试；任务只负责把结论变成原生交互，并如实确认。
5. **依赖只往下走，并由构建检查。** 规则写进 `check`，从第一天起严格执行，没有"历史违规名单"。
6. **v1 不含旧代码。** 需要的 v0 代码只能按移植清单明确搬入，并记录来源；其余一律按规格重写。
7. **LLM 看到玩家看到的。** 藏执行细节（路线、点击、槽位），不藏观察事实（是什么、在哪）。
8. **客户端动手，服务端提供确认信息。** 角色的一切动作都由客户端以第一人称完成，观众看到的就是它做的；服务端提供权威结果、方块归属记录和模组数据，但不替角色动手，也不提供透视。
9. **名字脱离上下文也不会被读成别的意思。** 见 09。

## 2. 分层

```text
L5 bootstrap   启动：创建服务，按已安装的模组登记能力与联动模组
L4 mcp         MCP 入口：传输、五个 MCP 工具（07）、观察视图、知识库
L3 ability     能力：每个能力（或一组相关能力）一个包        L3 compat  联动模组：只实现 spi
L2 behavior    玩家行为：站位、交互、拿东西、背包、生存需求、许可、重试、世界记忆、出行、容器界面、感知（03）+ 寻路
L1 kernel      内核：任务模型、打断规则、子任务运行、进度跟踪、目标推进、参数规格、能力框架、任务结果、任务事件、存储
L0 game        游戏接口：角色、原生交互、容器界面、读世界、加载器环境、和服务端通信的客户端一侧、mixin
```

另外三块：

| 部分 | 位置 | 规则 |
| --- | --- | --- |
| 网络消息 | `network` | 客户端与服务端 MaiCraft 之间的消息定义、版本协商；不依赖任何一侧；和 MCP 无关 |
| 服务端 | `server` | Minecraft 服务端一侧。只依赖 `network` 与 Minecraft 服务端；客户端任何层不引用它 |
| 调试界面 | `debug` | 只读，可以依赖到 L2；只有启动引用它 |

寻路在 `behavior.navigation`：全仓只有 `behavior.navigation.baritone` 可以碰 Baritone 的非 `baritone.api` 包。

### 依赖规则表

| 谁 | 可以依赖 | 不可以依赖 |
| --- | --- | --- |
| game | `network`、Minecraft 客户端 | 任何上层 |
| kernel | game | behavior、ability、compat、mcp |
| behavior | kernel、game | ability、compat、mcp |
| ability.X | behavior、kernel、game、`ability.Y.api`、`ability.Y.spi` | ability.Y 的内部包、compat、mcp |
| compat.X | behavior、kernel、game、`ability.*.spi` | 其他 compat、ability 的内部包、mcp |
| mcp | kernel、behavior、`ability.*.api` | ability 和 compat 的内部包 |
| bootstrap | 全部 | — |
| server | `network`、Minecraft 服务端 | 客户端的任何包 |

**对 Minecraft 客户端的写操作只允许出现在 game**：`MultiPlayerGameMode`、`ClientPacketListener`、`KeyMapping`；`Minecraft.getInstance()` 只允许 game 与 debug 调用。其他层可以只读地使用 `LocalPlayer`、`ClientLevel` 与 `BlockPos`、`ItemStack` 等值类型。

`spi` 子包放"给别人实现的接口"（例如联动模组提供的物品来源）。实现由启动时按模组是否安装明确登记，**不用 Java 的 ServiceLoader**。

## 3. 客户端与服务端分工

v0 自 2026-10-04 起已要求服务器安装 MaiCraft，但架构仍按"服务端可选、缺了就回退"组织。v1 把服务端当作必需组件，重新划分职责：

| 事情 | 由谁做 | 说明 |
| --- | --- | --- |
| 角色的一切动作（走、看、点、挖、放、开容器界面） | 客户端 | 第一人称原生交互，观众看到的就是它做的 |
| 原生交互的结果确认 | 客户端为主，服务端提供确认信息 | 客户端照旧"提交 → 逐刻确认"；服务端可以回报"这个玩家刚才破坏 / 放置 / 交互了哪一格"，作为权威确认 |
| 方块归属：哪些方块是哪位玩家放的 | 服务端 | 监听放置事件记录；M7 的保护判断从"客户端猜测"变成"服务端记录" |
| 模组数据：机器状态、AE2 网络库存与合成作业、Create 动力网络、Mekanism 配置、生产事件 | 服务端 | 客户端读不到或读不准的数据，由服务端读取后回报 |
| 场景感知（M12） | 客户端 | 以玩家视野为准；**服务端不提供透视** |
| 世界记忆、任务、存盘点 | 客户端 | 存在客户端的 SQLite，按世界身份分开 |

网络消息沿用 v0 已经成熟的部分（版本协商、双方支持的功能清单、请求记录、只认已登录连接的玩家身份），删除"可选"与客户端回退的双后端结构。消息注册保持 `optional`：没装 Mod 的普通玩家照样能进服，只有 AI 控制的客户端必须等握手。

## 5. 核心抽象：职责与要点

### 5.1 任务模型（`kernel.task`，已实现）

- **任务输入不可变**（`TaskInput`，各能力用 record 实现），只说"要做什么"。一次运行的生命周期由 `TaskRun` 记录，只能 PENDING → RUNNING → FINISHED 前进，违反顺序直接抛异常。
- **任务一律继承 `PhasedTask`**：进度用阶段枚举表达；换阶段、暂停与收尾动作、卡住判定、记录变化、组装任务结果由基类负责。**换阶段本身不算进展**，只有动作报告的真实进展才算。写法见 08 第 3 节。
- **动作 `Action`**：玩家行为层以动作的形式提供可组合的一段段行为；`runActionThen(context, () -> 下一步)` 把"还在做 / 失败上报 / 做完才换阶段"写成一行。
- **任务工厂表 `TaskFactories`**：任务输入类型 → 创建任务的工厂；工厂只接收任务输入，服务由能力在登记时通过闭包交给任务；重复登记直接报错。

### 5.2 任务结果（`kernel.result`，已实现）

`TaskResult` 把"目标达成没有"（DONE / PARTIAL / FAILED / CANCELLED）与"交互做成了什么"（`changes` 已确认的变化 / `unconfirmed` 没能确认的交互）分开。失败必须写明问题（`Problem`），完成与取消不能带问题。`Problem.Kind` 是一组小而稳定的种类（07 第 6.1 节）。能力特有的细节用 record 实现 `ResultDetails`，不用 `Map<String, Object>`。

### 5.3 进度与打断（`kernel.progress`、`kernel.interrupt`，规则已实现）

- `ProgressTracker` 按任务实际被推进的刻数计时，被打断的时间天然不计；多久没进展算卡住、最多做多久，由能力按自己的节奏给出。
- `InterruptRule` 是唯一的打断规则：`NOW`（立刻）打断一切，`SOON`（尽快）不打断停下不安全的动作，`LATER`（找空当）只在两个动作之间插进来。急迫程度 `Urgency` 与此刻能不能打断 `Interruptibility` 放在 `kernel.task`，避免包循环。
- `SurvivalNeed` 是"判断有多急 + 创建临时任务"：每刻给出自己有多急，需要处理时创建一个临时任务（普通的任务）。`ControlLoop`（WP-2.2）每刻按打断规则决定角色听谁的，并推进那个任务。**角色同一时刻只听一个任务的**：v0 绕过打断规则的随行补光，在 v1 里也作为生存需求走同一条规则。

### 5.4 目标、参数与能力（`kernel.goal`、`kernel.param`、`kernel.ability`，已实现）

- **目标对象** `Target` 是全接口唯一的"指一个地方或东西"的方式（07 第 4 节）；坐标的 y 可省略，到了附近再找能站的高度。
- **许可** `Permissions` 只表达取值，默认值是"像正常玩家一样"；"这一格能不能动"的判断在玩家行为层的 M7，全仓只有那一个检查点。许可不是 OP 权限。
- **提问** `Question` 只允许三种原因（超出许可要同意、后果不同的几种做法要选、目标对象说不清），类型上写不出别的。
- **这一步的决定** `StepDecision` 由能力的 `decide` 给出，取消了 v0 的"工具名 + JSON"通道，能力直接给出任务输入。
- **参数规格** `ParamSpec` 让能力说明里的参数表、MCP 入口的校验与规范化、带类型的取值同出一源；参数名必须先登记在 `ParamNames`。
- **能力模块** `AbilityModule` 是一个能力的唯一入口；`AbilitySpec` 承载 v0 散在十几个文件里的名单（执行方式、需要的模组、知识条目、是否列出……）；`AbilityRegistry` 登记能力时同时登记它的任务。
- 能力私有、需要跨重启保存的步骤状态，在 WP-2.3 随存储一起加入 `AbilityModule`。

### 5.5 内核扩展点

`GoalRunner`（WP-2.3）不对具体任务输入类型做 `instanceof`，也不比对能力 ID。它只认两种东西：

- **特征接口**，按归属分两边：属于**输入**的特征挂在任务输入上（例如"一次性消耗要绑定父任务的持久身份，防止重启后重复消耗"）；属于**结果**的特征挂在结果的 `ResultDetails` 上（例如"确认了一个位置，后续步骤可以引用"、"登记了自己搭建的区域，后续步骤要避开"）。任务输入不可变，结果不能塞回任务输入。
- **能力钩子** `AbilityHooks`（已定义）：只有能力自己知道的特殊处理。钩子是例外通道，每个实现都要在领域规格里说明为什么玩家行为层解决不了。

### 5.6 子任务运行（`kernel.child`，WP-2.1）

`ChildTaskRunner` 是子任务生命周期全仓唯一的实现：继承时限、创建任务、`start`、逐刻 `tick`、把异常转成 INTERNAL_ERROR 问题、转发暂停、`close` 收结果、松开按键。`GoalRunner` 与组合型任务都通过它运行子任务。

### 5.7 服务怎么传

服务分两组，各在自己的层：

| 服务组 | 所在层 | 内容 | 谁创建、谁使用 |
| --- | --- | --- | --- |
| 内核服务 | kernel | 任务存储（任务表、请求键）、任务事件、存储、能力注册表 | 启动创建；内核与 MCP 入口使用 |
| 玩家行为 | behavior | 站位、交互、容器界面、拿东西、背包、生存需求、许可与保护、重试、世界记忆、出行、感知 | 启动创建；交给能力模块，再由能力通过闭包交给任务 |

内核不持有任何玩家行为（那会让 L1 依赖 L2）。不写 `X.get()` 单例，不写可变 `static` 字段；服务一律从构造函数传入。

### 5.8 联动 spi

| 接口 | 定义在 | 实现方 |
| --- | --- | --- |
| `ItemSource` | `behavior.acquire.spi` | 背包、记得的容器、合成、烧炼、采掘、收获、狩猎、交易（玩家行为层自带）；随身背包、AE2（联动） |
| `TravelMode` | `behavior.travel.spi` | 步行（玩家行为层自带）；喷气背包、飞行器、Create 电梯、传送门、船（联动） |
| `ObstacleSource` | `behavior.navigation.spi` | 物理结构（联动） |
| `BreakAccelerator` | `behavior.interaction.spi` | FTB Ultimine（联动） |
| `MachineType` | `ability.machine.spi` | Create、Mekanism、AE2（联动） |
| `KnowledgeSource` | `mcp.knowledge` | 原版、配方、FTB 任务、Ponder、Wiki |

启动时按模组是否安装登记实现；能力是否可用，由它声明的 `requiredMods` 是否都装了决定。
