# 02 目标架构（v2）

> 前提：按 [00-全景审查](00-全景审查.md) 的结论，v2 在 `v2` 分支从零按本架构建设；v1 在 `dev` 分支冻结维护，作为直播版本和资料来源。
> 已经写成代码的部分（包结构、内核契约、护栏）**以代码为准**；本文说明职责、边界与理由，不再复制接口定义。

## 1. 设计原则

1. **一样东西只归一个地方。** 一个能力的知识归它自己的包；一条游戏事实归一个实现；一条约束归一条登记过的规则；一项服务归一层。
2. **内核不认识能力。** 调度、目标推进、子任务监护、进度、持久化框架对所有能力一视同仁。能力需要特殊处理时，通过扩展点挂进来，不改内核。
3. **能力是薄的，行为模型是厚的。** "怎么像个人一样靠近、瞄准、拿东西、腾背包、吃饭、看、放弃、求助"写一次，放在行为层；能力只负责"这件事要达成什么、按什么顺序组合行为"。
4. **决策和执行分开。** 决策写成读接口、出结论的纯函数，可以离线测试；执行器只负责把结论变成原生操作，并如实对账。
5. **依赖只往下走，并由构建强制。** 规则写进 `check`，从第一天起严格执行，没有"历史违规基线"。
6. **v2 不含旧代码。** 需要的 v1 代码只能按移植清单显式搬入，并记录来源；其余一律按规格重写。
7. **LLM 看到玩家看到的。** 藏执行细节（路线、点击、槽位），不藏观察事实（是什么、在哪）。
8. **客户端动手，服务端作证。** 角色的一切动作都由客户端以第一人称完成，观众看到的就是它做的；服务端提供权威结果、归属记录和模组数据，但不替角色动手，也不提供透视。

## 2. 分层

```text
L5 bootstrap      启动装配：按已安装模组注册能力模块和联动模块
L4 gateway        对外入口：MCP 传输、对外接口 v2（07）、视图投影、知识库
L3 ability        能力模块：每个能力（或能力族）一个包            L3 integration  联动模组：只实现 SPI
L2 behavior       玩家行为模型 M2–M12（03）+ 步行引擎
L1 kernel         内核：任务模型、仲裁规则、子任务监护、进度表、目标推进、参数规格、能力注册框架、统一回执、事件、持久化框架
L0 platform       平台：身体端口、原生操作与回执、菜单端口、世界读取、加载器环境、与服务端协议的客户端一侧、mixin
```

旁路上下文：

| 上下文 | 位置 | 规则 |
| --- | --- | --- |
| 协议 | `protocol` | 客户端与服务端共用的消息定义、版本协商；不依赖任何一侧 |
| 服务端 | `server` | 只依赖 `protocol` 与 Minecraft 服务端；客户端任何层不引用它 |
| 步行引擎 | `behavior.navigation` | 全仓只有 `behavior.navigation.baritone` 可以碰 Baritone 的非 `baritone.api` 包 |
| 调试界面 | `debug` | 只读，可以依赖到 L2；只有启动装配引用它 |

### 依赖规则表

| 谁 | 可以依赖 | 不可以依赖 |
| --- | --- | --- |
| platform | `protocol`、Minecraft 客户端 | 任何上层 |
| kernel | platform | behavior、ability、integration、gateway |
| behavior | kernel、platform | ability、integration、gateway |
| ability.X | behavior、kernel、platform、`ability.Y.api`、`ability.Y.spi` | ability.Y 的内部包、integration、gateway |
| integration.X | behavior、kernel、platform、`ability.*.spi` | 其他 integration、ability 的内部包、gateway |
| gateway | kernel、behavior、`ability.*.api` | ability 和 integration 的内部包 |

| server | `protocol`、Minecraft 服务端 | 客户端的任何包 |

**Minecraft 客户端的写操作只允许出现在 platform**：`MultiPlayerGameMode`、`ClientPacketListener`、`KeyMapping`；`Minecraft.getInstance()` 只允许 platform 与 debug 调用。其他层可以只读地使用 `LocalPlayer`、`ClientLevel` 与 `BlockPos`、`ItemStack` 等值类型。

## 3. 客户端与服务端分工

v1 自 2026-10-04 起已要求服务器安装 MaiCraft，但架构仍按"服务端可选、缺了就回退"组织。v2 把服务端当作必需组件，重新划分职责：

| 事情 | 由谁做 | 说明 |
| --- | --- | --- |
| 角色的一切动作（走、看、点、挖、放、开菜单） | 客户端 | 第一人称原生输入，观众看到的就是它做的 |
| 原生操作的结果确认 | 客户端为主，服务端作旁证 | 客户端照旧"提交 → 对账"；服务端可以回报"这个玩家刚才破坏 / 放置 / 交互了哪一格"，作为权威旁证 |
| 方块归属：哪些方块是哪位玩家放的 | 服务端 | 监听放置事件记账；M7 保护判定从"客户端猜测"变成"服务端记录" |
| 模组数据：机器状态、AE2 网络库存与合成作业、Create 动力网络、Mekanism 配置、生产事件 | 服务端 | 客户端读不到或读不准的数据，由服务端读取后回报 |
| 场景感知（M12） | 客户端 | 以玩家视野为准；**服务端不提供透视** |
| 世界记忆、任务、检查点 | 客户端 | 存在客户端的 SQLite，按世界身份隔离 |

协议沿用 v1 已经成熟的部分（版本协商、能力清单、请求账本、只认已认证连接的玩家身份），删除"可选"与客户端回退的双后端结构。载荷注册保持 `optional`：没装 Mod 的普通玩家照样能进服，只有 AI 客户端必须等握手。

## 5. 核心抽象：职责与要点

### 5.1 任务模型（`kernel.task`，已实现）

- **任务单是不可变输入**（`TaskRecord`，各能力用 record 实现），只描述"要做什么"。生命周期由内核的 `TaskHandle` 记录，只能 PENDING → RUNNING → FINISHED 前进，非法迁移直接抛异常。
- **执行器一律继承 `PhasedExecutor`**：进度用阶段枚举表达；阶段切换、子步骤暂停与收尾、停滞判定、效果累积、统一回执组装由基类负责。**换阶段本身不算进展**，只有子步骤报告的真实进展才算。写法见 08 第 3 节。
- **子步骤 `Step`**：行为模型以子步骤的形式提供可组合的动作；`runThen(context, () -> 下一步)` 把"还在做 / 失败上抛 / 做完才转移"写成一行。
- **执行器注册表**：任务单类型 → 执行器工厂；工厂只接收任务单，服务由能力模块在登记时通过闭包注入；重复登记直接报错。

### 5.2 统一回执（`kernel.outcome`，已实现）

`Outcome` 区分"目标达成没有"（DONE / PARTIAL / FAILED / CANCELLED）与"动作做成了什么"（achieved / uncertain）。失败必须写明卡点，完成与取消不能带卡点。`Blocker.Kind` 是一组小而稳定的类别（含 STALLED）。能力特有事实用 record 实现 `Facts`，不用 `Map<String, Object>`。

### 5.3 进度与仲裁（`kernel.progress`、`kernel.schedule`，规则已实现）

- `ProgressMeter` 按执行器实际被推进的刻数计时，被抢占的时间天然不计；停滞窗口与总上限由能力按自己的节奏给出。
- `PreemptionRule` 是仲裁的唯一规则：致命打断一切，有害打断空闲与忙碌，舒适只在空闲插入。紧急程度 `Urgency` 与可打断程度 `Interruptibility` 放在 `kernel.task`，避免包循环。
- `Need`（需求）是"评估器 + 差事工厂"：每刻给出自己有多急，需要时创建一次处理差事（普通执行器）。`BodyArbiter`（WP-2.2）每刻评估需求、按规则决定能否抢占当前任务。**没有第二个身体使用者**：v1 绕过仲裁的随行补光，在 v2 中作为一种需求参与仲裁。

### 5.4 目标、参数与能力（`kernel.goal`、`kernel.param`、`kernel.ability`，已实现）

- **目标模型** `Target` 是全接口唯一的"指一个地方或东西"的方式（07 第 4 节）；坐标的 y 可省略，到场再解析。
- **授权** `Mandate` 只表达取值，默认档是"讲道理的伙伴"；"这一格能不能动"的判定在行为层的 M7，全仓只有那一个检查点。
- **提问** `Decision` 只允许三种原因（需要授权、后果不同的选择、目标有歧义），类型上写不出别的。
- **翻译结果** `IntentAction` 取消了 v1 的"工具名 + JSON"通道，能力直接给出任务单。
- **参数规格** `ParamSpec` 让契约字段说明、入口校验与规范化、类型化取值同出一源；参数名必须先登记在 `ParamVocabulary`。
- **能力模块** `AbilityModule` 是一个能力的唯一入口；`AbilityDescriptor` 承载 v1 散在十几个文件里的名单（执行方式、可用前提、知识引用、可见性……）；`AbilityRegistry` 登记能力时同时登记它的执行器。
- 能力私有、需要跨重启保存的步骤状态，在 WP-2.3 随持久化框架加入 `AbilityModule.stepState()`。

### 5.5 内核扩展点

`GoalRunner`（WP-2.3）不对具体任务单类型做 `instanceof`，也不比对能力 ID。它只认两种东西：

- **特征接口**，按归属分两边：属于**输入**的特征挂在任务单上（例如"单次原生消费要绑定父任务的持久身份，防止重启后重复消费"）；属于**结果**的特征挂在回执的 `Facts` 上（例如"确认了一个位置，后续步骤可以引用"、"登记了自己搭建的区域，后续步骤要避开"）。v2 的任务单是不可变输入，结果不能塞回任务单。
- **能力钩子** `StepHooks`（已定义）：只有能力自己知道的特殊处理。钩子是例外通道，每个实现都要在领域规格里说明为什么行为模型解决不了。

### 5.6 子任务监护（`kernel.child`，WP-2.1）

`ChildSupervisor` 是子任务生命周期全仓唯一的实现：继承期限、创建执行器、`start`、逐刻 `tick`、捕获异常并转成 INTERNAL 卡点、转发暂停、`close` 收结果、松开按键。`GoalRunner` 与组合型执行器都通过它驱动子任务。

### 5.7 服务注入

服务分两组，各在自己的层：

| 服务组 | 所在层 | 内容 | 谁组装、谁使用 |
| --- | --- | --- | --- |
| 内核服务 | kernel | 目标存储（任务表、请求键）、事件总线、状态存储、能力注册表 | 启动装配创建；内核与入口使用 |
| 行为模型 | behavior | 靠近、操作、菜单、取物、背包、维护、授权与保护、尝试、记忆、出行、感知 | 启动装配创建；注入给能力模块，再由能力通过闭包交给执行器 |

内核不持有任何行为模型（那会让 L1 依赖 L2）。不写 `X.get()` 单例，不写可变 `static` 字段。

### 5.8 联动 SPI

| SPI | 定义在 | 实现方 |
| --- | --- | --- |
| `MaterialSource` | `behavior.procure.spi` | 背包、容器记忆、合成、烧炼、采掘、收获、狩猎、交易（行为层自带）；随身背包、AE2（联动） |
| `TravelProvider` | `behavior.travel.spi` | 步行（行为层自带）；喷气背包、飞行器、Create 电梯、传送门、船（联动） |
| `ObstacleProvider` | `behavior.navigation.spi` | 物理结构（联动） |
| `BreakAccelerator` | `behavior.act.spi` | FTB Ultimine（联动） |
| `MachineTypeProvider` | `ability.machine.spi` | Create、Mekanism、AE2（联动） |
| `KnowledgeSource` | `gateway.knowledge` | 原版、配方、FTB 任务、Ponder、Wiki |

启动装配按模组是否安装注册实现；能力是否可用，由它声明的 `requires` 是否满足决定。

## 8. 持久化

- 沿用 v1 的 SQLite 底座（按分区、世界身份、文档键存文档；WAL；消费前强制落盘）。数据文件与 v1 分开存放，互不覆盖。
- 每种文档有版本号；能力私有的步骤状态由各能力自己负责编解码。
- **v2 不读取 v1 的任务检查点**。提供一次性导入工具，把 v1 的地标、蓝图、机器档案导入 v2。
