# 05 执行手册（给执行 Agent）

**规则以仓库根的 `AGENTS.md` 为准**（所有 Agent 共用，进 Git）；本机路径见不入库的 `AGENTS.local.md`。
本手册只写"怎么做"的标准流程，不重复规则。

背景：v2 在 `v2` 分支从零建设，v1 在 `dev` 分支冻结维护。你大部分时间在 `v2` 工作；读 v1 只为两件事：清点领域旧逻辑（清册），以及按移植清单搬运底座文件。

## 一、开工与收工

1. 读 `docs/design/README.md`，找到要做的工作包卡片（04），在看板上认领。
2. 读卡片涉及的设计文档；写代码前读 02 与 08。
3. 做完：相关测试与架构护栏通过 → 提交 → 按第五节汇报 → 停下，不顺手开始下一个工作包。

## 二、验证命令

```bash
./gradlew :common:test                         # 公共模块全部测试（含架构护栏）
./gradlew :common:test --tests '*ParamSpecTest' # 只跑相关的测试类
./gradlew :fabric:build :neoforge:build         # 两个加载器打包
```

Windows 下用 `gradlew.bat`（Git Bash 里的注意事项见 `AGENTS.local.md`）。全量 `build` 由 CI 负责，不顺手跑。长时间的构建放到后台运行，中途只报关键进度。

## 三、标准做法

### 3.1 移植一个 v1 文件

1. 在 `docs/design/移植清单.md` 先登记一行：v1 路径、v1 提交号、目标路径、计划做的整理。
2. 从 `dev` 取回原文件：`git checkout <v1 提交号> -- <v1 路径>`，再 `git mv` 到目标路径，只改 `package` 与 `import` → 提交（"移植：……，无逻辑变化"）。这样 `git log --follow` 能追到 v1 的历史。
3. 按清单做整理（删掉领域特判、改用注入的服务、补中文注释……）→ 单独提交。
4. 架构护栏通过后才算完成；把清单那一行的状态改为已完成并写上提交号。

不在移植清单里的代码不移植，按规格重写。

### 3.2 写领域清册（读 v1，只清点、不评价、不修改）

```markdown
# <领域> 旧逻辑清册（v1 dev 提交 <哈希>）

## 1 范围
| 文件 | 行数 | 角色（翻译 / 执行器 / 任务单 / 钩子 / 反射 / 提醒 / 测试） |

## 2 主流程
从公开能力到原生操作的实际调用链，按代码写，不按文档写。

## 3 规则条目
| 编号 | 位置（文件:行） | 触发条件 | 效果（拒绝 / 失败 / 提问 / 重试 / 特例 / 常量） | 注释里给出的理由（摘要） | 来源提交（git log -L 或 blame） | 覆盖它的测试 | 实机事故编号 | 建议类别（可选，写明把握程度） |

## 4 向 LLM 提问的出口（逐个列出问题和选项）
## 5 失败出口（按失败类型统计，并列出位置）
## 6 常量与阈值
## 7 跨领域依赖（引用了哪些其他领域的类，各用来做什么）
## 8 当前对外契约（参数表摘要）
## 9 现有测试（测试类 → 它断言的行为要点）
## 10 v1 直播中在这个领域出过的问题（来自 v1 维护记录）
```

规则条目要**全**：所有会让角色"不做、换做、等一等、问一下、失败"的分支都算，宁可多列，不可漏。完整样板见 [06-试点规格-睡觉](06-试点规格-睡觉.md) 第 5 节。清册写进 `docs/design/领域/<领域>-清册.md`，交给 Claude 写规格。

### 3.3 实机问题处理规程（最重要）

实机或测试暴露问题时，**先归类，再动手**：

| 问题属于 | 在哪里修 | 例子 |
| --- | --- | --- |
| 缺了一条游戏事实 | 把事实加到它归属的模型或平台层（只加一次），常量注释写明类别 F 与来源 | 醒来的实体包和时间包不同刻到达 |
| 某个行为模型有缺陷 | 改那个模型；所有用到它的能力一起受益 | 遮挡时换工位的候选不够 |
| 规格没想到这种情况 | 停下来，补规格，经批准后再改实现 | 床被别的玩家占了怎么办 |
| 实现没按规格写 | 按规格改实现 | — |

每一类都要补一个能重现该场景的离线测试或实机验收项。**不允许**在出问题的执行器里加一条只为这次场景服务的特判。

### 3.4 实现一个领域

1. 读批准后的规格，列出要建的类（08 第 1 节的标准结构）。
2. 先写决策类和它们的离线测试，再写执行器（继承 `PhasedExecutor`）和子步骤替身测试，最后写模块注册、契约资源。
3. 参数名只用词汇表里的；需要新概念时先在 `ParamVocabulary` 登记并写清含义，同步 07 第 5 节。
4. 更新契约快照（显式更新，并在提交说明里写清变化）、`CHANGELOG.md`、能力文档。
5. 交给两位做实机验收；验收中发现的问题按 3.3 处理。

## 四、遇到问题怎么办

| 情况 | 做法 |
| --- | --- |
| 规格与游戏现实对不上 | 停下来，把具体出入写清楚，交给 Claude 或两位决定 |
| 想复制 v1 的一段代码 | 先登记进移植清单；不属于底座的代码不移植，按规格重写 |
| 护栏挡住了你认为合理的写法 | 不要绕过，提出来讨论 |
| 和别人的提交冲突 | `rebase` 解决；不确定该保留哪边就问；不强制推送 |
| v1 直播出了问题 | 只有接到明确的 v1 修复工作包才动 `dev`；修法以最小改动为准，并在对应领域清册里记一笔 |

## 五、汇报格式

```text
提交：<哈希> <说明>（逐条列出）

移植清单：新增 N 条（如有）
未完成 / 偏离卡片的地方：……
需要人决定的事：……
```
