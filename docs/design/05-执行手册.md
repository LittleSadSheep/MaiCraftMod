# 05 执行手册（给执行 Agent）

**规则以仓库根的 `AGENTS.md` 为准**（所有 Agent 共用，进 Git）；本机路径见不入库的 `AGENTS.local.md`。
本手册只写"怎么做"的标准流程，不重复规则。

背景：v1 在 `v1` 分支从零建设，v0 在 `dev` 分支冻结维护。你大部分时间在 `v1` 工作；读 v0 只为两件事：清点领域旧逻辑（旧逻辑清单），以及按移植清单搬运基础代码文件。

## 一、开工与收工

1. 读 `docs/design/README.md`，找到要做的工作包卡片（04），在看板上认领。
2. 读卡片涉及的设计文档；写代码前读 02 与 08。
3. 做完：相关测试与架构检查通过 → 提交 → 按第五节汇报 → 停下，不顺手开始下一个工作包。

## 二、验证命令

```bash
./gradlew :common:test                         # 公共模块全部测试（含架构检查）
./gradlew :common:test --tests '*ParamSpecTest' # 只跑相关的测试类
./gradlew :fabric:build :neoforge:build         # 两个加载器打包
```

Windows 下用 `gradlew.bat`（Git Bash 里的注意事项见 `AGENTS.local.md`）。全量 `build` 由 CI 负责，不顺手跑。长时间的构建放到后台运行，中途只报关键进度。

## 三、标准做法

### 3.1 移植一个 v0 文件

1. 在 `docs/design/移植清单.md` 先登记一行：v0 路径、v0 提交号、目标路径、计划做的整理。
2. 从 `dev` 取回原文件：`git checkout <v0 提交号> -- <v0 路径>`，再 `git mv` 到目标路径，只改 `package` 与 `import` → 提交（"移植：……，无逻辑变化"）。这样 `git log --follow` 能追到 v0 的历史。
3. 按清单做整理（删掉领域特例、改成从构造函数传入服务、按 09 改名、补中文注释……）→ 单独提交。
4. 架构检查通过后才算完成；把清单那一行的状态改为已完成并写上提交号。

不在移植清单里的代码不移植，按规格重写。

### 3.2 写领域旧逻辑清单（读 v0，只清点、不评价、不修改）

```markdown
# <领域> 旧逻辑清单（v0 dev 提交 <哈希>）

## 1 范围
| 文件 | 行数 | 角色（能力适配 / 任务 / 任务输入 / 钩子 / 生存需求 / 提醒 / 测试） |

## 2 主流程
从公开能力到原生交互的实际调用链，按代码写，不按文档写。

## 3 规则条目
| 编号 | 位置（文件:行） | 触发条件 | 效果（拒绝 / 失败 / 提问 / 重试 / 特例 / 常量） | 注释里给出的理由（摘要） | 来源提交（git log -L 或 blame） | 覆盖它的测试 | 实机事故编号 | 建议类别（可选，写明把握程度） |

## 4 向 LLM 提问的出口（逐个列出问题和选项）
## 5 失败出口（按失败类型统计，并列出位置）
## 6 常量与阈值
## 7 跨领域依赖（引用了哪些其他领域的类，各用来做什么）
## 8 当前对外能力说明（参数表摘要）
## 9 现有测试（测试类 → 它断言的行为要点）
## 10 v0 直播中在这个领域出过的问题（来自 v0 维护记录）
```

规则条目要**全**：所有会让角色"不做、换做、等一等、问一下、失败"的分支都算，宁可多列，不可漏。完整样板见 [06-试点规格-睡觉](06-试点规格-睡觉.md) 第 5 节。旧逻辑清单写进 `docs/design/领域/<领域>-旧逻辑清单.md`，交给 Claude 写规格。

### 3.3 实机问题处理规程（最重要）

实机或测试暴露问题时，**先归类，再动手**：

| 问题属于 | 在哪里修 | 例子 |
| --- | --- | --- |
| 缺了一条游戏事实 | 把事实加到它归属的模型或游戏接口层（只加一次），常量注释写明类别 F 与来源 | 醒来的实体包和时间包不同刻到达 |
| 某个行为模型有缺陷 | 改那个模型；所有用到它的能力一起受益 | 遮挡时换站位的候选不够 |
| 规格没想到这种情况 | 停下来，补规格，经批准后再改实现 | 床被别的玩家占了怎么办 |
| 实现没按规格写 | 按规格改实现 | — |

每一类都要补一个能重现该场景的离线测试或实机验收项。**不允许**在出问题的任务里加一条只为这次场景服务的特例。

### 3.4 实现一个领域

1. 读批准后的规格，列出要建的类（08 第 1 节的标准结构）。
2. 先写判断类和它们的离线测试，再写任务（继承 `PhasedTask`）和动作替身测试，最后写能力模块、能力说明资源。
3. 参数名只用参数名表里的；需要新概念时先在 `ParamNames` 登记并写清含义，同步 07 第 5 节。类名、字段名、枚举值先查 09；09 里没有的概念，按 09 第 6 节先定名再写。
4. 更新接口快照（明确更新，并在提交说明里写清变化）、`CHANGELOG.md`、能力文档。快照在 `common/src/test/resources/snapshots/`，由 `InterfaceSnapshotTest` 比较；有意的改动用 `MAICRAFT_UPDATE_SNAPSHOTS=1 ./gradlew :common:test --tests *InterfaceSnapshotTest --rerun` 重写，再看一遍 diff 是不是自己想要的。
5. 交给两位做实机验收；验收中发现的问题按 3.3 处理。

### 3.5 接一个联动模组

做法与理由见 02 第 5.8 节。只新建这个模组自己的包，再在联动清单里加一行。

1. 先看要用的东西能不能从游戏数据认出来（方块标签、配方、原版接口）。能的话改玩家行为层，不写联动，也不写方块 ID 名单。
2. 读模组源码，核对要调用的类与方法（`AGENTS.md` 的"联动模组"一节），登记进 `docs/design/领域/` 下的事实清单，写明源码位置与版本。
3. `neoforge/build.gradle` 加 `compileOnly`，版本与实测实例装的一致，写进 `gradle.properties`。jar 按 maven 坐标取：官方 maven 优先，没有再用 Modrinth（坐标 `maven.modrinth:<项目 slug>:<版本号>`，仓库已在 `neoforge/build.gradle` 放行）或 CurseMaven；不引用本机路径（CI 拿不到）。模组依赖的库（例如精妙背包的精妙核心）也要一起 `compileOnly`，不然它的父类解析不了。
4. `common` 的 `compat.<模组>`：写模组读写接缝（只用 Minecraft 与 Java 的类型）和联动入口。联动入口继承 `CompatModule`，在 `contribute` 里把 spi 实现交给登记表，碰读写端的每一下都经自己的 `call("在做什么", …)`；游戏逻辑与判断都写在这里，用替身读写端离线测试。
   - 物品来源要走过去、点开、搬东西的，交建法：`registry.itemSource(this, services -> new 来源(services, 读写端))`。`SourceServices` 是进世界后才有的玩家行为（当刻的角色、靠近、交互、保护判断、物品标签、认得出哪些界面、方块扫描），和自带来源用的同一套，不另造。不用这些的来源直接交实例。
   - 模组界面要读两侧、搬东西的，交布局证明：`registry.menuLayout(this, 证明)`（`MenuLayoutProof`，按菜单类型注册 ID 认界面，只证明模组自己的界面，不能改写原版）；没有证明的模组界面一格都不点。开界面用 `ClientMenuOpening`，布局传 `services.menuLayouts()`。
   - 界面挂在方块的一个部件上（线缆上的面板这类）：读写端给出部件框（世界坐标），用 `ClientMenuOpening` 收部件框的构造，靠近与右键都对准这个框（`ApproachTarget.ofBlockPart`、`Interactions.useBlockPart`）。
   - 界面里的操作走模组自己的包、不是原版点格子的：用 `OpenedMenu.submitModAction(在做什么, 发包, 确认条件, 期限)`，和点格子同一套规矩（上一下结清、界面画过、占本刻的交互机会），本刻发不了返回空，下一刻再试；发包经联动入口的 `run`。
5. NeoForge 模块的 `neoforge.compat.<模组>`：实现读写接缝，直接调用模组的类，只翻译、不判断；`LinkageError` 由联动入口的 `call` 转成 `ModApiMismatch` 并停用，读写端不用自己接。
6. 需要服务端读数据的，在 `server.compat.<模组>` 登记服务端操作；读写端同样放在 `neoforge.compat.<模组>`。服务端的登记槽还没有，第一个需要它的模组来时和分层规则一起定。
7. 联动清单加一个支持的模组：`ClientCompatCatalog.mods()`（需要服务端读数的再加 `ServerCompatCatalog`）里 `new SupportedMod(模组 ID, 名字, new VerifiedVersions(下界, 上界), () -> new 联动入口(new 读写端()))`。读写端只在 lambda 体里 new，清单类的字段、方法签名与静态初始化里不出现模组的类。没装、版本不在范围、创建出错三种情况的检查已有离线测试覆盖，各模组只测自己的联动入口与 spi 实现。
8. 有能力离开这个模组就用不了的，在它的 `AbilitySpec` 里写上 `requiredMods`；没装时能力不登记，按名字下达会回 `unknown_ability` 并说清缺哪个模组。
9. 实机：装了、没装、版本不在范围三种情况各启动一次，看日志里那一行「联动 <名字>（<模组 ID>）：…」写的是已登记、没装跳过，还是版本不在范围不登记。

需要改玩家行为层、能力或 MCP 入口才接得上时，停下来，写清 spi 接口缺了什么，交给 Claude 或两位决定。

## 四、遇到问题怎么办

| 情况 | 做法 |
| --- | --- |
| 规格与游戏现实对不上 | 停下来，把具体出入写清楚，交给 Claude 或两位决定 |
| 想复制 v0 的一段代码 | 先登记进移植清单；不属于基础代码的代码不移植，按规格重写 |
| 架构检查挡住了你认为合理的写法 | 不要绕过，提出来讨论 |
| 和别人的提交冲突 | `rebase` 解决；不确定该保留哪边就问；不强制推送 |
| v0 直播出了问题 | 只有接到明确的 v0 修复工作包才动 `dev`；修法以最小改动为准，并在对应领域旧逻辑清单里记一笔 |
