# 01 诊断：为什么会"改了这坏了那"

所有数字取自 2026-10-08 的 `dev`（`7f808ee9b`），统计范围是 `org.maiwithu.maicraft`，不含内嵌 Baritone 和第三方签名源码。
> 用词：本文描述的是 v0，沿用 v0 当时的叫法（回执、任务单、仲裁、反射、契约……）；v1 的叫法见 [09-命名与术语](09-命名与术语.md)。

## 一、体量与开发节奏

| 项 | 数值 |
| --- | ---: |
| 自研主代码 | 1447 个文件，207,743 行 |
| 测试代码 | 920 个文件，96,228 行（其中 841 个是带 `main` 方法的独立测试） |
| 内嵌 Baritone（不改） | 333 个文件，40,331 行 |
| 仓库提交总数 | 3077（约 70 天） |
| 近 30 天提交 | 2107 |
| 其中 `fix` / `feat` / `refactor` | **841** / 577 / 115 |
| 近 30 天 `fix` 最多的领域 | build 119、machine 97、create 43、acquire 34、mcp 33 |

**修复比新功能还多**，这是"打地鼠"的直接证据：每修一处就在别处冒出新问题。

## 二、症状 → 证据 → 根因

### 症状 1：一个能力散在十几个地方，改一处漏一处

| 证据 | 数值 |
| --- | --- |
| 写着 `"maicraft:xxx"` 能力 ID 字面量的文件 | 40 个 |
| 近 30 天被改得最多的文件 `SemanticAbilityCatalog`（全部能力的契约写在一个 `switch` 里） | **168 次** |
| 增改一个能力要动的位置 | 契约目录、概要表、可用性表、知识引用表、参数规范化、适配器 `switch`（分三层 `supports()`）、内部工具注册、任务单类、执行器注册、执行器、持久化编解码、`IntentRuntime` 能力清单、`IntentTaskRecord` 计数清单、夜休可打断清单…… |

以 `maicraft:craft` 为例：至少 13 个文件里写着这个 ID，各自维护一份关于它的知识。

**根因**：项目按技术层横切（契约 / 翻译 / 工具 / 任务 / 持久化），没有按能力纵切。任何一个能力的知识都被拆到所有层里。

### 症状 2：通用内核里写满了具体能力的特例

`IntentTask`（总任务的逐刻推进器，按理说应该对所有能力一视同仁）里：

- 按具体任务单类型做 `instanceof` 分支：`SleepTaskRecord`、`SemanticAcquireTaskRecord`、`SemanticTradeTaskRecord`、`SemanticCookTaskRecord`、`BuildTaskRecord`、`SemanticBuildSupplyTaskRecord`、`SemanticExploreTaskRecord`、`MoveToTaskRecord`……
- 睡觉专用：自带床回退、换位重试、"白天门"决策中继、重挂等待、防重问三态；
- 探索专用：兴趣点决策中继；机械动力专用：续建令牌；施工专用：工程编号保留；地形授权共享……

`IntentStateCodec`（持久化）同样把"取物起始数""翻箱范围"这类能力私有状态写进了通用格式。

**根因**：内核没有扩展点，能力想要特殊处理只能改内核。于是每加一个能力，所有能力的公共路径都要承担风险。

### 症状 3：同一套机制，各写一遍，写法还不一样

| 机制 | 重复次数 |
| --- | ---: |
| 子任务生命周期（创建 → 启动 → 逐刻推进 → 收结果 → 松手 → 转发停止） | **30 多处**各自手写，`AbstractCompanionTask.runChild` 的注释还写着"不会把 stop 转发给子任务" |
| 原生操作回执（存回执字段 → 每刻 poll → 结束时归还操作额度） | 53 个文件、60 个回执字段、72 次 `poll`、40 次 `retireOneShotForTaskBoundary` |
| 瞄准收敛 | 18 个文件 |
| 手动延长截止时间 `extendDeadlineTo` | 139 处（统一的 `ProgressBudget` 只有 12 个文件在用） |

**根因**：缺少可复用的动作原语。每个任务都从最底层的端口直接写起，于是同一个坑要在每个任务里各踩一遍。

### 症状 4：同一条游戏事实被实现了很多遍，而且互相矛盾（"左右脑互博"）

| 游戏事实 | 现状 |
| --- | --- |
| 伸手距离 | 10 多处各写常量：4.5、4.45、4.25、3.0。1.21 里它本来是玩家属性 `blockInteractionRange` / `entityInteractionRange`，应该直接读取。 |
| 能不能够到床 | `SleepCompanionTask` 用眼距 ≤ 4.5；`NightRestTask` 照搬服务端 `isReachableBedBlock` 的轴向距离盒。**两者对同一张床会给出不同结论。** |
| 饥饿 | 15 个文件各自读取 `getFoodData()`；施工任务里自带一整套"种田 → 备餐 → 吃饭"（`BuildFoodFarmSupply`、`BuildFoodMaterials`、`BuildFoodPreparation`、`BuildFoodStockSupply`）。 |
| 背包满 | 30 多个任务各自处理 `NO_SPACE`。 |
| 物料获取 | 10 多条并行管线：取物、施工供料、物料协调、支撑供料、创造模式供料、食物备料、着陆物料、生产投料、副手补给、传送门资源、工具准备、AE2 五件套、背包供料、容器供料…… |
| 契约 vs 实现 | 契约散文里写着"当前持久等待有缺陷""数量会宽松转换""目录虽保留 nearest 但适配器不按它定位"。契约、`ParameterNormalizer`、适配器三处各自对参数做一套解释。 |

**根因**：没有"一个事实只在一处"的归属规则。哪里撞到问题就在哪里补，补出来的版本互不知道彼此的存在。

### 症状 5：约束越补越多，补丁上面再补丁

- `Task` 接口上为反射仲裁陆续加了 5 个布尔开关：`suppressesSurvivalReflexes`、`onlyWhenBodyReleased`、`urgentBodyRescue`、`drivesBodyContinuously`、`yieldsToContinuousDriving`。每一个都是某次实机事故后补上的豁免，再为豁免补豁免。根子在于仲裁模型里只有"注册顺序"，没有"紧急程度"和"此刻能不能被打断"这两个概念。
- 注释里写着"不得 / 不能"的有 **2091 处**；失败出口 447 个；向 LLM 提问的出口 109 个。
- 授权参数 44 个，共 12 种（`may_alter_terrain` ×17、`allow_rare_consumables` ×6、`allow_combat` ×5、`allow_harm` ×5……）。LLM 必须提前猜该开哪个，猜错就会得到"失败 → 带上新开关重提"的循环。`FailureType` 的提示文字本身就在教 LLM 这样重提。
- `RecoveryLadder`（统一的换策略重试）写好了，**生产代码里却没有一个调用点**。

**根因**：约束没有归属、没有分类、没有来源记录，也就没有人能判断哪条可以删。补丁只会累加，不会退出。

### 症状 6：依赖关系是一张网，谁都能碰到谁

- 顶层包之间有 **43 对双向依赖**。最严重的几对：`core.task ↔ task`（362/2）、`core.integration ↔ core.task`（124/99）、`intent ↔ core.task`（57/44）、`core.integration ↔ server`（38/36）。
- 底层任务通过单例 `IntentRuntime.get()` 往上够语义层，共 46 处，用来取地标、任务表、事件、记忆。
- 120 个可变的 `static` 字段。

**根因**：没有分层规则，也没有工具强制执行。单例让任何代码都能直接调用任何服务。

### 症状 7：历史双通道还在

- 内部 Tool 通道：适配器返回"工具名 + JSON 参数"，工具再去"提交"任务单，`IntentTask` 用 `captureNext` 这张"网"把提交拦下来改成返回。项目自己的架构文档写得很清楚：`captureNext` 存在的全部理由，就是把前者掰成后者。这个通道涉及 53 个工具类、42 处 `IntentAction.Tool`。
- `task/`（调度）和 `core/task/`（具体任务）两个同名包；`client/` 在一个纯客户端 Mod 里什么也说明不了；`core/` 同理。
- [附录-文件职责审计](附录-文件职责审计.md) 已核实的死代码：旧移动执行层 15 个文件（3262 行）、11 个旧导航目标类、无调用的账本、钩子和请求桥……

### 症状 8：测试只能靠黑魔法

- 业务逻辑直接持有 `LocalPlayer` / `ClientLevel`，测试只能用 `Unsafe.allocateInstance` 凭空造出 Minecraft 对象（72 个测试文件），并用反射改私有字段（323 个测试文件）。
- 841 个测试各自私有一份 `check()`；79 个回归组的成员靠手工维护。
- 大量测试断言的是"补丁行为"本身，例如 `SleepBedFallbackRegression`（839 行）。补丁删掉，测试也就失去意义。

### 症状 9：观众一眼看到的东西，LLM 看不到

直播画面里，观众能直接看到前面是悬崖还是河、左边有只羊、远处有个村庄、身后有僵尸在叫。LLM 通过 `perceive` 拿到的却是：

| LLM 看到的 | 缺什么 |
| --- | --- |
| `surroundings.nearby_entities`：16 格方盒内实体的类型和距离 | **没有方向、没有位置、没有可引用的编号**；不检查视线，墙后的怪也算"附近"。LLM 知道"7.3 格外有只僵尸"，但不知道它在哪边、能不能看见它 |
| `local_decision_summary`：脚下附近的可站面、门、攀爬物、危险方向 | 只有近处脚下这一圈；看不到远一点的地形 |
| `nearby_facilities`（要点名才给）：设施的类型、数量、最近距离 | **故意不给坐标**，注释写明"感知层不替能力选目标"。LLM 没法说"用左边那个箱子" |
| `terrain_overview`（要点名才给） | 注明是给飞行着陆初选用的粗采样，"不构成步行寻路输入" |
| `situation` 加 `focus=maicraft:navigation` | 返回的是导航引擎、交通运行时、喷气背包的**内部诊断状态**，这是给开发者排错用的数据 |

而项目里**其实有一双"眼睛"**：`LookAroundTool` 把周围画成以角色为中心的俯视语义网格（平地、台阶、落差、墙、水、岩浆），类注释写着"空间视图是她的眼睛"；另有 `ScanNearbyEntitiesTool`、`ScanBlocksTool`。可它们只是内部工具，四个公开工具没有任何一条路能调到。对外收敛成四个工具的时候，眼睛被落下了。

此外，**全仓没有任何声音感知**：玩家靠字幕就能知道身后有东西，伙伴不行。

**根因**：对外的原则"只给投影，剔除内部坐标"，本意是不让 LLM 微操路线和点击，却把"看到的东西是什么、在哪"也一起剔掉了。再加上感知是按工程模块拼出来的（脚下一块、设施一块、物理结构一块、导航诊断一块），没有一个"玩家此刻看到了什么"的统一场景。

### 症状 10：要不要打，没有依据

`Menace`（苦力怕爆炸半径、末影水晶）、`CombatThreats`（谁打了我、什么伤害）、`RetreatThreats`（谁在追我）都只描述威胁本身，**没有"我方战力对比威胁"的评估**。于是"打还是跑"、"床边有怪要不要清"、"夜里露天要不要躲"这些决定，只能靠各处写死的规则或者去问 LLM。

### 症状 11：对外的消息通道各自为政

伙伴要告诉 LLM 的事，分散在好几条通道里：Attention 事件流、附加在**每一个**工具返回值里的 `reminders`（10 个提醒类）、`maicraft://chatflow` 资源、冻结回执 URI、`task(get, path)`。其中提醒和 Attention 的事件有重叠，提醒和身体维护（饿了、缺火把、多日未睡）也有重叠：伙伴自己能处理的事，却以提醒的形式推给了 LLM。

## 三、根因

> **没有"归属"。** 一个能力的知识不归属于一个包，一条游戏事实不归属于一个实现，一条约束不归属于一个理由，一项服务不归属于一个层。所以每次修改都必须同时改动很多地方，每次漏改都会在实机里冒出来。

> **信息是按工程模块组织的，而不是按玩家的视角组织的。** 感知、回执、提醒都是"哪个模块有什么就报什么"，而不是"一个玩家此刻看到了什么、做成了什么、卡在哪"。

重构的全部设计，都是在回答两个问题："这个东西归谁"，以及"一个玩家会怎么看、怎么做"。

## 四、不是问题的部分（保留并迁入）

不是所有东西都要推倒。下面这些设计是对的，迁到新位置后继续使用：

- **原生操作的"提交 → 对账"协议**：`NativeActionPort`、`NativeActionReceipt`、`NativeConfirmation`，以及"连续稳定刻确认""版本变了就判不确定"等规则。这是整个项目最扎实的部分。
- **身体端口**：`LocalPlayerContext`、`BodyControlPort`、`MenuPort`，以及每刻重新取得上下文、每刻只准提交一次操作的纪律。
- **四个公开工具**和 Attention 事件流：对外通道设计清晰，保持不变。"不让 LLM 微操路线、点击、槽位"这条原则也保留；要改的只是它被误用到了观察事实上（症状 9）。
- **`LookAroundTool` 的以角色为中心的语义网格**：表示方式是对的，接进新的感知模型（M12）继续用。
- **世界身份绑定、SQLite 记忆库、"恢复不等于重新批准"**的纪律。
- **"发出不等于成功"**这条信条，以及 AGENTS.md 里"原生动作成功与设计是否达标分开判断""不用预测门控"等原则。新的行为模型就是建立在这些原则之上的。
- **内嵌 Baritone 作为步行引擎**（ADR 0008 的边界）。
