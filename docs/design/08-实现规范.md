# 08 实现规范（v1 的代码怎么写）

02 定的是"包和层"，03 定的是"游戏行为"，这一份定的是**一个类、一个方法该怎么写**。名字怎么起见 [09-命名与术语](09-命名与术语.md)。v0 的很多问题出在这一层：

| 现状 | 数量 |
| --- | ---: |
| 执行层（`core/task`、`core/integration`）里直接读写 `JsonObject` 的文件 | 193 |
| `Map<String, Object>` 的出现次数（回执、进度、诊断几乎全用它） | 1129 |
| 一个任务的私有字段数（`FirstPersonBuildCompanionTask`） | 108 |
| 同一个任务里的 `if` | 525 |
| 静态工具类 `*Ops` | 13 个，2038 行 |
| `TaskRecord.setState` | 不校验状态迁移，任何状态都能改成任何状态 |
| 失败类型 | 一部分用字符串比较（`"occluded".equals(...)`） |

本规范约束 v1 的全部代码，包括从 v0 移植过来、又做过整理的文件。

## 1. 一个能力包的标准结构

```text
ability/sleep/
├─ SleepModule.java          能力入口：能力规格、对每一步的决定、登记任务（唯一对外的类）
├─ SleepParams.java          带类型的参数 record + ParamSpecs（全部参数规格）
├─ SleepInput.java           任务输入 record：要去哪张床、在多大范围里找
├─ SleepDecider.java         看现场决定这一步下一件做什么（纯函数为主）
├─ SleepTask.java            任务：按阶段推进
├─ SleepDetails.java         本能力特有的结果细节 record
├─ BedChooser.java           本能力特有的判断（纯函数，可离线测试）
└─ （api/、spi/ 仅在确有外部使用方时才建）

resources/assets/maicraft/abilities/sleep.md      能力说明
test/…/ability/sleep/                             离线场景测试
```

除了 `SleepModule`，包里的类一律包内可见（不写 `public`），让 Java 本身挡住跨能力的内部依赖。

## 2. 类型纪律

| 规则 | 说明 |
| --- | --- |
| **`JsonObject` 只出现在 MCP 入口与参数规格框架** | MCP 入口用 `ParamSpecs` 把参数解析成带类型的 `ParamValues`，能力再转成自己的参数 record；决定和任务从不 `getAsInt`。唯一例外是图纸、修改、逐格清单这类嵌套的结构化正文（`JSON_OBJECT` / `JSON_ARRAY`）：以 `JsonElement` 交给能力，能力在入口一次转成自己的记录（`DesignFormat`、`BuildCells` 等），之后不再传 `JsonElement` |
| **结果用 record，不用 Map** | 每个能力定义自己的 `ResultDetails` record；任务结果由 `TaskResult` record 表达；转成 JSON 是 MCP 入口的事 |
| **失败用枚举** | `Problem.Kind` 是枚举；任何地方不比较失败字符串 |
| **状态用阶段枚举，不用布尔字段** | 任务的进度是一个 `Phase` 枚举，加上每个阶段自己的少量数据。禁止用 `boolean enteredSleep; boolean morningObserved; boolean nightSkipped…` 拼出隐式状态机 |
| **任务输入不可变** | 任务输入（record）只说"要做什么"；运行中会变的东西只在任务里。生命周期由 `TaskRun` 校验（PENDING → RUNNING → FINISHED，结束后不可再改） |
| **不用静态可变状态** | 服务从构造函数传入（内核服务、玩家行为，见 02 第 5.7 节）。不写 `X.get()` 单例，不写可变 `static` 字段（架构检查强制） |
| **不用静态工具类装业务逻辑** | 业务规则属于某个模型或能力；纯几何、纯数学的小工具可以是静态方法 |
| **时间单位** | 内部用游戏刻；对外（参数、结果）用秒；换算只在 MCP 入口和结果组装处做 |

## 3. 任务的写法：阶段

v1 所有任务都继承 `kernel.task.PhasedTask`（以代码为准，这里说明怎么用）：

| 子类要写的 | 作用 |
| --- | --- |
| 构造器 `super("睡觉", Phase.CHOOSE_BED, new ProgressTracker(多少刻没进展算卡住, 最多推进多少刻))` | 名字、第一个阶段、按本能力节奏给出的进度跟踪 |
| `Action enter(P phase)` | 进入某阶段时调用一次，返回这个阶段要做的动作；只做判断的阶段返回 null |
| `Next<P> tick(P phase, TickContext context)` | 每刻推进当前阶段：`Next.stay()`、`Next.go(阶段, 原因)`、`Next.done(结果)`、`Next.fail(问题)` |
| 可选：`details()`、`remaining()`、`describePhase()`、`onPhaseChange()` | 能力特有的结果细节、没做完的部分、阶段中文名、换阶段之后要做的事 |

| 基类提供的 | 作用 |
| --- | --- |
| `runActionThen(context, () -> 下一步)` | 推进动作一刻：还在做就留在本阶段，失败就把问题原样上报，做完了才执行给定的走向 |
| `runAction(context)` | 只推进动作一刻并返回状态，用于需要自己看失败原因的阶段 |
| `recordChange(变化)`、`recordUnconfirmed(变化)`、`recordAttempt(试了什么, 结果)` | 记下已确认的变化、没能确认的交互、试过的办法；结束时自动进结果 |
| `recordProgress(什么进展)` | 记一次不经过动作的真实进展 |

基类统一负责：换阶段时收尾旧动作、准备新动作并写日志；被生存需求打断时暂停动作，结束时收尾；
卡住判定（**换阶段本身不算进展**）；组装任务结果；被替换、取消或角色没了时如实交代已发生的变化；
处在两个动作之间时报告 `BETWEEN_ACTIONS`，让找空当处理的生存需求可以插进来。

### 样例：睡觉任务的骨架

按 06 规格，只展示结构。`behaviors.*` 的动作 API 是示意，以阶段 3 玩家行为的实现为准。

```java
/** 公开"睡觉"的任务：选床 -> （没床就放自带床或现做一张）-> 走到床边 -> 躺下。 */
final class SleepTask extends PhasedTask<SleepTask.Phase> {

    enum Phase { CHOOSE_BED, GET_BED, PLACE_BED, APPROACH, LIE_DOWN }

    private final SleepInput input;
    private final Behaviors behaviors;
    private final BedChooser chooser;
    private BedChoice bed;                       // 选中的床：世界里原有的，或刚放下的自带床
    private BedSource source = BedSource.WORLD;

    SleepTask(SleepInput input, Behaviors behaviors) {
        super("睡觉", Phase.CHOOSE_BED, new ProgressTracker(STUCK_AFTER_TICKS, MAX_TICKS));
        this.input = input;
        this.behaviors = behaviors;
        this.chooser = new BedChooser(behaviors.worldMemory(), input.permissions());
    }

    @Override protected Action enter(Phase phase) {
        return switch (phase) {
            case CHOOSE_BED -> null;
            // 身上没床：用身上、随身背包、已知箱子里的材料拿到一张床（M4），羊毛不够就剪羊毛或打野生羊
            case GET_BED -> behaviors.acquire().obtain(ItemTags.BEDS, 1, Purpose.SLEEP);
            // 把床放到站位能看见床头、又不会压到自己的两格上（M2 选位 + M3 放置）
            case PLACE_BED -> behaviors.interaction().placeCarriedBed();
            // 走到同时满足服务端床距离、交互距离和视线的站位；被挡住时由 M2 换站位
            case APPROACH -> behaviors.approach().approach(StandSpots.forBed(bed.head()));
            // 右键床头并确认真的躺下；确认期间日期前进，说明一觉睡到了天亮，也算成功（M3）
            case LIE_DOWN -> behaviors.interaction().use(bed.head(), SleepConfirmation.INSTANCE);
        };
    }

    @Override protected Next<Phase> tick(Phase phase, TickContext context) {
        return switch (phase) {
            case CHOOSE_BED -> chooseBed(context);
            case GET_BED -> runActionThen(context, () -> {
                source = BedSource.CRAFTED;
                return Next.go(Phase.PLACE_BED, "拿到了床");
            });
            case PLACE_BED -> runActionThen(context, () -> {
                bed = BedChoice.placedAt(behaviors.interaction().lastPlaced());
                if (source == BedSource.WORLD) source = BedSource.CARRIED;
                recordChange(Change.of(Change.Kind.BLOCK_PLACED, bed.blockId(), 1));
                return Next.go(Phase.APPROACH, "床放好了");
            });
            case APPROACH -> runActionThen(context, () -> Next.go(Phase.LIE_DOWN, "到床边了"));
            case LIE_DOWN -> lieDown(context);
        };
    }

    private Next<Phase> chooseBed(TickContext context) {
        // 下界、末地用床会爆炸，这是原版规则：不提问，直接结束并说明
        if (!WorldRules.bedsWork(context.player().level())) {
            return Next.fail(Problem.of(Problem.Kind.NOT_POSSIBLE_HERE, "这个维度用床会爆炸"));
        }
        Optional<BedChoice> found = chooser.choose(context, input.area());
        // 已加载范围分几刻扫完；没扫完不能当成"附近没有床"
        if (found.isEmpty() && !chooser.scanComplete()) return Next.stay();
        if (found.isPresent()) {
            bed = found.get();
            recordProgress("选中了" + bed.describe());
            return Next.go(Phase.APPROACH, "选中了" + bed.describe());
        }
        // 附近没有能用的床：身上有就放自带的，没有就先去弄一张
        return behaviors.inventory().has(context, ItemTags.BEDS)
                ? Next.go(Phase.PLACE_BED, "附近没有能用的床，放自带的")
                : Next.go(Phase.GET_BED, "附近没有床，身上也没有，先弄一张");
    }

    private Next<Phase> lieDown(TickContext context) {
        ActionStatus status = runAction(context);
        if (status instanceof ActionStatus.Running) return Next.stay();
        if (status instanceof ActionStatus.Done) return Next.done(TaskResult.done("躺下了"));
        // 被游戏拒绝时，按提示语分流（完整分流见 06 第 3 节）：被占用就换床，床边有怪交给威胁评估
        Problem refusal = ((ActionStatus.Failed) status).problem();
        return switch (SleepRefusal.of(refusal)) {
            case OCCUPIED -> {
                chooser.exclude(bed);
                yield Next.go(Phase.CHOOSE_BED, "床被占了，换一张");
            }
            case MONSTERS_NEARBY -> Next.go(Phase.CHOOSE_BED, "床边有怪，重新选床");
            case OTHER -> Next.fail(refusal);
        };
    }

    @Override protected ResultDetails details() {
        return new SleepDetails(source);
    }
}
```

和 v0 的 `SleepCompanionTask` 加上 `AbilityAdapter.sleep()` 对比：瞄准、确认、交还交互机会、换站位、面板描述、卡住判定、结果组装全都不在这里了；这里只剩"睡觉"这件事本身的流程。

## 4. 判断与动手分开

- **判断类**（`BedChooser`、`StandSpots` 的选位、`ThreatAssessment`、`ItemAcquisition` 的比价）写成纯函数：输入只读接口（`WorldQuery`、`InventoryView`、`WorldMemoryView`、`PermissionsView`），输出结论 record。不控制角色，不读 `Minecraft.getInstance()`。
- **动手的类**（任务、动作）只负责把结论变成原生交互，并如实确认。
- 好处：判断类可以用替身做离线测试，覆盖率要求 100%；动手的类用"动作替身"测试（第 8 节）。

## 5. 规则常量

每个会改变角色行为的常量（距离、阈值、上限、时长），都写成命名常量，并在注释里标明类别与来源：

```java
/** 醒来的实体包和时间包不在同一刻到达，醒后留出的同步时间。F 游戏事实，来源：122 实机。 */
static final int WAKE_SYNC_TICKS = 200;
```

类别用 03 第 4 节的五类。**v1 不允许出现 P、G、S 类常量**：发现需要它们，说明某个模型有缺陷，应该修模型。

## 6. 每刻预算

费时的扫描（找方块、找床、场景感知、路线探测）不得在单刻内跑完，也不得各自实现"分几刻做完"。统一使用游戏接口层的扫描服务：提交查询，之后每刻查询进度，结果带"是否扫完"。"没扫完"永远不能当成"没有"。

## 7. 日志、面板与事件

- 阶段切换、动作开始和结束、卡住的原因，由基类统一记录，同时驱动调试面板和任务事件。
- 能力代码里只在出现领域特有的关键事实时才写日志，每个类用 SLF4J 的 `LoggerFactory.getLogger(本类.class)`，不再手写 `[maicraft-sleep]` 这类前缀。

## 8. 测试

测试用 JUnit 5，放在 `common/src/test/java`，与被测类同包。`./gradlew :common:test` 跑全部，`--tests <测试类>` 只跑相关的。

| 被测对象 | 写法 |
| --- | --- |
| 判断类 | 用替身接口构造场景（世界、背包、记忆），直接断言结论 |
| 任务 | 用动作替身（参考 `kernel/task/ScriptedAction`）：按脚本逐刻返回"在做 / 有进展 / 做完 / 失败"，断言阶段走向、最终结果和细节 |
| 玩家行为 | 判断部分同"判断类"；动手部分用游戏接口层的替身（按脚本返回交互的确认结果） |
| 能力说明 | 接口快照（WP-2.4） |
| 真实游戏 | 只在实机验收清单里验证，离线测试不模拟 Minecraft 物理 |

- 测试不使用 `Unsafe`，不用反射改私有成员（架构检查强制）。需要读任务内部状态时，说明这个状态该进结果或结果细节。
- 断言用 JUnit 自带的 `Assertions`。
- 测试方法名写成一句场景（会在什么处境下怎样），中文英文都行；同一个测试类里统一一种写法（架构检查强制），新测试类沿用所在包已有的写法，不为统一而批量改名。
- 每个领域规格第 9 节的场景，都要有对应的离线测试或实机验收项。

## 9. 线程

- 所有游戏状态只在客户端线程读写。网络线程只在 MCP 入口通过 `onClient` 把请求交给客户端线程（沿用 v0 的做法，它是对的）。
- 禁止自己开线程或使用 `CompletableFuture` 链访问游戏对象。联网资料等确需后台线程的工作，集中放在 `mcp.knowledge`。

## 10. 大小上限

| 对象 | 上限 | 超过怎么办 |
| --- | ---: | --- |
| 类 | 800 行（架构检查强制） | 拆阶段或拆判断类；确需例外，登记在 `common/src/test/resources/architecture-exemptions.txt` 并写明理由 |
| 方法 | 80 行（架构检查强制） | 拆方法 |
| 任务的字段 | 15 个 | 阶段私有的数据收进阶段自己的小 record |
| 一个阶段的 `tick` | 40 行 | 说明这个阶段做了不止一件事，再拆 |

## 11. 注释

- 注释写**这段代码是什么、为什么这样设计**，用中文游戏逻辑说明触发条件、角色动作、执行顺序与原因。例：`// 刨坑 -> 出坑 -> 拿材料 -> 建房`。
- 不写"见 docs 某文档第几节"、工作包编号、"v0 是这样做的"、"重构后删除了 X"：文档会改、版本对比会过时，历史看 git log（架构检查强制）。
- 名字与术语只用 09 里的说法；09 第 2 节列出的旧叫法不再出现（架构检查强制）。
