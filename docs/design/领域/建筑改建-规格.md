# 建筑改建 领域规格

> 状态：待批准。起草：Claude（10-15 直播装门与改建会话）。
> 起因：实机检验证据 E66。10-15 晚场直播里 LLM 改木屋"庇护所"，手上只有 `observe(scene, grid=true)` 那张 17×17 的平面格子（`#` 是墙），看不出门洞、地面在哪一层、屋里多高。它想在屋里"清出两格地面"放床，算错了高度，把西墙的两块云杉木板 (15, 64, 18)、(15, 64, 19) 拆了；门的位置也是从格子上猜的，第一扇门装在 (17, 63, 15)，第二扇装到 (14, 63, 17)，门就装歪了。机器那边有 `machine_inspect`、机器档案、补丁并进整机比对，房子还没有。
> 依据：v0 没有改建房子的能力，不另做旧逻辑清单；第 5 节归类的是现有清单里和"读现场、看布局、改了再比"相关的条目：[感知与观察-旧逻辑清单](感知与观察-旧逻辑清单.md) S-05、S-32–S-34、S-51、S-55–S-57，[建造与照明-旧逻辑清单](建造与照明-旧逻辑清单.md) B43、B45、BP13、C91–C93、PJ01–PJ09，[机器与任务-旧逻辑清单](机器与任务-旧逻辑清单.md) M53、M90、M91、M111、M114。
> 范围：在[建造-规格](建造-规格.md)之上加四样东西：建筑档案、`design` 读现场成图纸、建筑的布局、改建流程。施工引擎、蓝图核对、图纸格式、设计存储都沿用建造规格，不另写一套。所有者已同意这个方向（10-15）。

## 1 范围

| v1 能力 | 这次加什么 |
| --- | --- |
| `design` | 新操作 `capture`（读现场）：把现场已有的一栋建筑读成一张新图纸，按层画、带方块状态，门、床、楼梯都在里面，同时给出这栋的布局 `layout`；`inspect` 也给布局 |
| `build` | 盖完自动记一份建筑档案；`target` 可以写档案名，这时就是改建：按新图纸或逐格补丁补建，结束后整栋比对 |
| `observe(world_memory)` | 列出建筑档案（名字、在哪） |

图纸格式加一种对象 `LAYERS`（层图）。机器档案与机器能力不动；补丁合并的规则抽出来两边共用（第 3.6 节）。

## 2 真人怎么做

**盖完**：自己盖的房子自己知道：叫什么、照哪张图盖的、门朝哪。

**改之前先看**：走进屋里、绕外面一圈，看清门在哪、墙多高、地面是哪一层、屋里哪儿空着能放床。别人的房子只知道自己看到的那些。

**改**：在图纸上改（这里开个门、那两格放床、加一层），照着图纸补盖，改完对一遍整栋，不只看改的那几格：拆墙的时候把旁边的火把碰掉了，也要知道。

**不做的事**：不把墙当地面拆；不替作者重新设计；别人的房子不动，碰到要问。

## 3 新逻辑

### 3.1 建筑档案

```text
建筑档案 BuildingArchive
  name          档案名：build 的 name；没给就用图纸名，同一世界撞名时加 "@x,y,z"
  dimension     维度
  anchor        锚点：蓝图原点落在的那一格
  rotation      朝向：0 / 90 / 180 / 270
  design_id     照哪一版图纸盖的；逐格或结构文件盖的为空
  blueprint     整栋蓝图：相对锚点的逐格目标，图纸编译的结果并上后来的补丁
  bounds        范围（包围盒）
  last_check    最近一次整栋比对的时间与一句结论

存在哪          按世界存（图纸按实例存，档案记的是"这个世界里哪儿有一栋"）
                世界记忆加一种 BUILDING（在哪、叫什么），observe(world_memory) 列出来
什么时候记      build 用 design_id / cells / file 施工结束：done、partial、取消都记，
                档案里写的是整份蓝图，last_check 如实写还差几格，不冒称建成
                单格 block：落在某栋档案的范围里就并进那一栋并整栋比对；不在任何一栋范围里不建档
                design(capture) 给了 name 而这栋还没有档案：建一份（锚点是读的范围的最小角，朝向 0）
存不进          只记问题（存储坏了、超出文档大小），施工照常结算，不改判
```

档案名能当目标：`target` 写 `{"kind": "landmark", "name": "庇护所"}` 时，先找记过的地点，再找建筑档案、机器档案。记过的地点和建筑档案同名、而且在同一处（地点落在档案范围里），就是同一栋；同名不同处问 `UNCLEAR_TARGET`。

### 3.2 `design(capture)`：读现场

```text
1 定范围     target 是建筑档案 → 档案范围
             是 b# / 坐标 / 记过的地点 / here → 从那一格起自动框：沿"不是天然地形"的方块
             （不是地面、石头、天然的草木与树）连通扩开，连上被它们围住的空气，再往下带一层地面；
             给了 radius 就不自动框，改用以 target 为中心、边长 2×radius+1 的方盒
             上限 32×32×32 格，超了按参数错误报，并写明自动框到了多大
2 读格       范围里每一格：已加载，并且角色看得见、或归属记录是角色自己放的，才读；
             其余记"没看到"，不按空气算
             方块状态按建造的状态归一：开关、充能、含水、点亮这些运行态不进图纸；
             门上半、床头照实记成两格；方块实体的内容（箱子里有什么）不读
3 成图       存一版新图纸（新 design_id；名字用 name，有档案用档案名，都没有写"现场@x,y,z"）：
             材料表每种方块状态一项；一个 LAYERS 对象按层画（3.3）；
             空气默认不声明，没看到的也不声明
4 布局       从读到的格算 layout（3.4）
5 交付       design_id、anchor（范围最小角，照这一版补建就落在这里）、bounds、层数、每种材料几格、
             没看到几格、layout、层图（层数多就按页给，带 next_page，用 design(inspect, page) 接着读）
             有档案时另给 check：档案的整栋蓝图对现场比，和 build 结束时的整栋比对一个形状（3.5）
```

`capture` 不动角色、不改世界，只读客户端已加载的格子、存一版图纸，和 `design` 的其余操作一样当场返回。

### 3.3 层图对象 `LAYERS`

图纸格式里和 `MESH`、`INSTANCE`、`ROOF` 并列的一种对象：一层一张字符图。`capture` 读出来的就是它，LLM 也可以自己写。

```json
{
  "name": "现场",
  "type": "LAYERS",
  "location": [0, 0, 0],
  "legend": {
    "P": "spruce_planks",
    "L": "spruce_log[axis=y]",
    "D": "spruce_door[facing=south,half=lower,hinge=left]",
    "d": "spruce_door[facing=south,half=upper,hinge=left]",
    "_": "Clear"
  },
  "layers": [
    {"y": 0, "rows": ["PPPPPPP", "PPPPPPP", "PPPPPPP"]},
    {"y": 1, "rows": ["LPPDPPL", "P.....P", "LPPPPPL"]},
    {"y": 2, "rows": ["LPPdPPL", "P.....P", "LPPPPPL"]}
  ]
}
```

- 方向和 `observe` 的格子一样：北朝上（-Z）、东朝右（+X）。一行是同一个 z，第几行就是 z 偏移几；一个字符一格，第几个字符就是 x 偏移几；`y` 是层的高度偏移。偏移都相对对象的 `location`。
- `legend`：字符 → 材料名（材料表里的那一项）。`.` 和 `?` 不声明（空着、没看到，施工不管这一格）；映射到 `Clear`（`minecraft:air`）的字符才是"清空这一格"。
- `capture` 写的材料名是方块 ID 加摆放属性，例如 `spruce_door[facing=south,half=lower,hinge=left]`，材料表里对应项的 `properties` 就是方括号里那些，写了就是验收标准。
- 改层图（`design(update)` 的 `edits.objects` 里按名字合并）：给 `layers` 只换写到的那几层，别的层留着；给 `set: [{"at": [x, y, z], "material": "名字"}]` 逐格改，`material` 写 `.` 是改成不声明。层图和别的对象叠在一起时照 `overlap_policy`。
- 层图编译成计划格：每个声明的字符一格，属性按材料项归一（建造的 `BlockStateRules`），和别的对象编译出来的格没有区别。

### 3.4 布局 `layout`

从一份逐格的格子（`capture` 读到的，或一张图纸编译出来的）算，纯函数，只报事实，不判这栋房子好不好、能不能住、能不能走通。

```text
floors      每层能站的地面：地面方块那一层的 y、上面净高几格、有顶的能站格数
doors       每扇门：下半在哪、哪种门、朝向、铰链、开着没、两侧哪一边有顶（屋里那一侧）
openings    墙上的口子：一格宽两格高、两侧都能站、没装门的记门洞；眼睛高度一格高的记窗洞
windows     玻璃、玻璃板
beds        床脚、床头、朝向
climbs      楼梯、梯子、藤蔓、脚手架、活板门：在哪、连着哪两层地面
facilities  箱子、工作台、熔炉这类，认法和场景里的设施一样
free_floor  有顶、能站、头上两格都空的地面格，连成片的分一组，给范围与格数（放床、放箱子用）
```

"有顶"是头顶 8 格内有实心方块；"能站"照站位的判断（脚下实心、身体那两格空）。布局在 `capture`、`inspect` 和改建后的整栋比对里给；数量多时按种类分组给总数，不截断。

### 3.5 改建：改图纸 → 按图补建 → 整栋比对

```text
1 看         design(capture, target=档案名)：现场成图 + 布局 + 和档案差在哪
             或 design(inspect, design_id=档案记的那一版)：看当初的图
2 改         design(update, design_id, edits) → 新一版（父版本是旧图）
             也可以不改图，直接写逐格补丁
3 补建       build(design_id=新一版, target=档案名)：锚点、朝向用档案的；施工引擎照常
             （对上的格跳过，不对的按许可拆换，缺料去拿，垫的临时方块收回）；
             档案的整栋蓝图换成新一版的编译结果，design_id 记新一版
             build(cells=[…], target=档案名)：cells 的 offset 相对档案锚点；补丁并进档案的整栋蓝图：
             同一格以补丁为准，补丁没提的旧目标留着
             build(block=…, target=档案范围里的一格)：同上，一格的补丁
4 整栋比对   补建结束，整栋蓝图对现场比：每格 MATCHES / WRONG_BLOCK / WRONG_STATE / MISSING / UNKNOWN，
             范围里没声明却有东西的记 EXTRA，只作信息；没对上的每一格都列（在哪、要什么、现场是什么），
             不截断，太多时按结论分组给总数、明细给直达路径；有没加载的格就不给"整栋一致"；
             再算一次布局一起给
5 结算       动作做了什么（changes、unconfirmed）、整栋对不对（check）、能不能住（不判）三件分开写；
             补建的格做完了而整栋有别的格不对（拆墙时碰掉了火把、水流进来），施工照样按施工的结果结束，
             差异进 check，由 LLM 决定要不要再改
```

`target` 是档案名时给了和档案不一样的 `rotation`，按参数错误报：改建沿用档案的朝向，换朝向就是另盖一栋。许可照建造规格：自己放的方块按 `natural` 能拆换；别人的格子受保护，一次列出问 `NEED_APPROVAL`。

### 3.6 和机器档案的关系

补丁合并（同一格以补丁为准、补丁没提的留着、补丁里写的格按补丁的先后排）现在写在机器的 `MachinePatch` 里。把逐格这部分抽成施工引擎旁边的一个纯函数 `BlueprintPatch.merge`，建筑档案和机器档案共用；机器自己的部件、安装段、装后设置的合并留在 `MachinePatch`。整栋比对和整机比对用同一个 `BlueprintCheck.compare`。机器档案的其余规则不动。

### 3.7 组合的模型

M7（许可、保护、方块归属：读格时"自己放的"靠归属记录）、M9（世界记忆的 BUILDING）、M12（看得见才读）、施工引擎与 `BlueprintCheck`（建造规格）、`DesignStore`、`DesignEdits`。本规格自己特有的只有：自动框范围、层图对象、布局的算法、建筑档案与它的补丁合并。

## 4 能力说明

参数都是参数名表里已有的：`target`、`name`、`radius`、`design_id`、`cells`、`block`、`rotation`、`edits`、`page`。

### `design`

| 参数 | 必填 | 说明 |
| --- | :---: | --- |
| `operation` | ✅ | 加 `capture` |
| `target` | capture | 读哪一栋：建筑档案名、b#、坐标、记过的地点、here |
| `name` | | capture 时：新图纸的名字；这栋还没有档案时用这个名字建档 |
| `radius` | | capture 时不自动框，改读以 target 为中心的方盒 |

能力说明加一句：

> capture 把现场已有的一栋建筑读成一张新图纸：按层画、带方块状态，看不见的格子不读；同时告诉你这栋的楼层、门、门洞、窗、床、上下楼的地方和屋里能放东西的空地。改了图再用 build 指着这栋补盖。

结果细节 `DesignDetails` 加：`anchor`、`bounds`、`unseen`（没看到几格）、`layout`（3.4）、`layers`（层图，按页）、`check`（有档案时，形状同 build）。`inspect` 的结果也带 `layout`。

### `build`

| 参数 | 必填 | 说明 |
| --- | :---: | --- |
| `name` | | 新建筑的档案名；`target` 已经是档案时不用给 |

`target` 可以写建筑档案名，这时是改建（3.5）。能力说明加一句：

> 盖完会记一份建筑档案。target 写档案名就是改这一栋：照新一版图纸或逐格补丁补盖，结束后对整栋比一遍，哪格不对都列出来。

结果细节 `BuildDetails` 加：`archive`（名字、锚点、朝向、design_id）、`check`（`complete`、每种结论几格、`differences[]` 每格在哪 / 结论 / 要什么 / 现场是什么、`extra[]`）、`layout`（改建时）。

## 5 旧逻辑归类表

类别：F 游戏事实 / C 玩家常识 / P 补丁 / G 预判拦截 / S 过严或无意义。

| 编号 | 位置 | 内容 | 类别 | 去向 |
| --- | --- | --- | --- | --- |
| 感知 S-51、S-05 | `perceive(view=construction_site)`、`ConstructionSiteGeometry` | 有界体积（半径 1..8）的场地勘测：调色板加水平连续段，只给脚下一层以上；按锚点生成标签与快照编号，交给施工 | C | 重写为 `design(capture)`：按层的字符图带方块状态，存成一版图纸，用 design_id 和档案名指它，不发快照编号；范围自动框，上限 32 格 |
| 感知 S-32–S-34 | `LocalFloorSense` | 脚下摘要：楼层候选、门与攀爬物单列；看得见和只是已加载分开标，不当成有路 | C | 思路进布局的 `floors`、`doors`、`climbs`：只对一栋建筑算，不做脚下摘要；不标"有路"，也不判能不能走 |
| 感知 S-55、S-56 | `LookAroundTool` | 俯视字符网格，高度折成一个移动符号 | C | 不动：v1 的 `observe(grid)` 照旧给走路用；看建筑用层图，不把高度折掉 |
| 感知 S-57 | `BlueprintReadTool` | 读图纸的尺寸、用料、层分布 | C | 保留：`design(inspect)` 按层给，加布局 |
| 建造 B43、C91–C93 | `BuildTraversabilityVerifier` | 建完扫描入口、房间、上下楼，走不通判失败 | C（规划器时代） | 建造规格已删除；本规格只把门、门洞、楼梯列成观察事实，不判失败 |
| 建造 B45、PJ01–PJ09 | `BuildProjectStore` 等 | 冻结施工单、修订只改要求、支撑账 | C（v0） | 不恢复：建筑档案记的是"照什么盖的"，不是施工单；续建、改建都靠重新核对，范围可扩可缩 |
| 建造 BP13 | `ConstructionOwnership` | 施工归属账 | F | 不恢复：读现场时"自己放的"问服务端方块归属记录 |
| 机器 M53 | `inspect_machine` | 默认按档案足迹定范围 | C | 照搬：capture 指着档案就读档案范围 |
| 机器 M90、M91、M111 | `MachineComparisonTargets` | 冻结比较目标进档案；补丁同位覆盖、范围外保留；改完比整机 | C | 照搬到建筑档案（3.5），合并规则抽成两边共用（3.6） |
| 机器 M114 | 留档 | 留档失败只记问题不改判施工 | C | 照搬 |

本规格不新增"拒绝执行 / 提前失败"，只有参数错误（范围超上限、改建换朝向），都归 C。

## 6 行为变化清单（拍板用）

| # | 场景 | 现在（v1） | 之后 |
| --- | --- | --- | --- |
| 1 | 盖完一栋房子 | 什么都不记，只有施工开始时世界记忆里一条"这里在盖东西" | 记一份建筑档案：名字、图纸版本、锚点、朝向、范围、最近一次比对；`observe(world_memory)` 看得到 |
| 2 | 想改一栋已有的房子 | 只有 17×17 的平面格子，墙是 `#`，看不出高度、门洞、地面 | `design(capture)` 读成层图，带方块状态，附楼层、门、门洞、窗、床、上下楼、屋里空地 |
| 3 | 改 | 自己算坐标写 `cells`，结果只核对补丁那几格 | 改图纸（换层、逐格 set）或写补丁，`build(target=档案名)` 补建，结束后整栋比对写进结果 |
| 4 | 给已有房子装一扇门 | 单格 `build`，不知道门洞在哪 | 布局列出门洞；落在档案范围里的单格并进那一栋，整栋比对 |
| 5 | 改建时拆墙碰掉了旁边的东西 | 看不到 | 整栋比对列出那一格（要什么、现场是什么），施工结果不改判 |
| 6 | 别人的房子 | 平面格子里一样是 `#` | 只读看得见的格，没看到的记数；拆改照旧受保护要问 |
| 7 | 指一栋房子 | 只能写坐标或记过的地点 | 档案名可以当 `target` |

## 7 游戏事实的新归属

## 8 不做的东西

- 不判一栋房子好不好、能不能住、能不能走通；不替 LLM 改图、挑放床的位置。
- 不发快照编号；不恢复冻结施工单、修订施工单。
- 不读箱子里的东西（要看就 `use` 打开）。
- 拆整栋、把一栋搬到别处不在这次范围（读出来的图纸本来就能拿去别处盖）。

## 9 验收

**离线场景测试**（判断类用替身接口，任务用动作替身）：

1. 自动框：从门那一格起，框住墙、屋顶、屋里的空气和下面一层地面；旁边的树、草不进框；超过 32 格报参数错误并写明框到多大；给了 radius 用方盒。
2. 读格：角色在屋外，屋里看不见的格记没看到；墙是自己放的（归属记录是自己）照读；没加载的不按空气算。
3. 成图：门、床两格都在；开着的门读成门（不带 open）；含水的台阶不带 waterlogged；材料名带摆放属性；空气不声明。
4. 层图编译：`.`、`?` 不出计划格，映射到 Clear 的出清空格；行列和 x、z 对得上；`edits` 只换写到的层、`set` 逐格改。
5. 布局：两层小屋的 floors（y、净高）、门（朝向、屋里那一侧）、门洞、窗洞、床、楼梯连着哪两层、屋里空地分片；布局不出"能不能住"之类的结论。
6. 建档：design_id / cells / file 盖完记档；partial 和取消也记，last_check 写还差几格；单格 block 落在档案范围里并进那一栋、范围外不建档；撞名加 @x,y,z；存不进只记问题。
7. 改建：新一版图纸整份替换档案蓝图；逐格补丁同位覆盖、范围外留着；锚点朝向用档案的，给不同的 rotation 报参数错误。
8. 整栋比对：补丁那几格对了、旁边一格被改坏 → differences 列出那一格，施工结果仍是 done；有没加载的格 complete=false；EXTRA 只作信息。
9. 档案名当目标：同名同处的地点和档案是同一栋；同名不同处 UNCLEAR_TARGET。

**实机验收**：

1. 10-15 的场景：木屋"庇护所"已经在，没有档案。`design(capture, target=庇护所, name=庇护所)` → 层图里看得出地面是哪一层、墙几格高、北墙上的门洞；`free_floor` 列出屋里能放床的两格。LLM 改图把床放进空地、门装进门洞，`build(target=庇护所)` 补建，整栋比对全 MATCHES，西墙没被拆。
2. 改建拆一段墙开窗，窗边的火把掉了：整栋比对报那一格 MISSING，施工 done。
3. 村庄里别人的房子：站在门外 capture，屋里没看到的格计数；走进屋再 capture 一次，看到了屋里；改它的墙问 NEED_APPROVAL。
4. 新盖一栋，`observe(world_memory)` 看到档案；用档案名 `travel` 过去。

## 10 待拍板

| # | 问题 | 建议 |
| --- | --- | --- |
| D1 | 读现场放在 `design` 的新操作 `capture`，还是像机器那样另开一个只读能力（例如 `building_inspect`） | `design(capture)`：所有者说的就是"design 能把现场读成图纸"，LLM 只学一个能力；它不动角色、不改世界，和 design 别的操作一样当场返回。操作名 `capture` 只看名字会被读成截图，拿不准可以换 `read_site` |
| D2 | 读哪些格：范围里已加载的全读，还是只读看得见的和自己放的 | 只读看得见的和自己放的（归属记录是自己），其余记没看到。"看到玩家看到的"；自己盖的房子自己知道；角色进屋里再读一次就看到屋里 |
| D3 | 范围怎么定：从目标那格自动框，还是只给 radius 方盒 | 自动框为主，给了 radius 用方盒，上限 32 格。LLM 说不清一栋房子的边界，自动框按"不是天然地形"的方块连通去找，和真人看一眼房子有多大一样 |
| D4 | 读出来的空气格声明成"清空"，还是不声明 | 不声明。图纸没写的格本来就不是"必须为空"；照读出来的图补建时，屋里后来放的东西不会被当成要清掉的。要清空就写成 Clear |
| D5 | 层图对象的写法：一层一张字符图，北朝上东朝右，一行一个 z、一个字符一个 x，`legend` 字符 → 材料名 | 照此。和 `observe` 的格子同一个方向，LLM 不用换算；改一格就是改一个字符 |
| D6 | 建筑档案放哪、按什么存 | 放 `ability.design.api`（`DesignStore` 旁边）：build 已经依赖它，design 的 capture 也要查档案，放这里不多出新的依赖方向；按世界存在能力自己的文档里，世界记忆记一条 BUILDING |
| D7 | 什么时候记档 | design_id / cells / file 的施工结束就记（含 partial、取消，last_check 如实写）；单格 block 落在档案范围里并进那一栋，范围外不记；capture 给了 name 也建档 |
| D8 | 档案名怎么起，和记过的地点同名怎么办 | build 的 name；没给用图纸名，撞名加 @x,y,z，不问。记过的地点和档案同名同处算同一栋，同名不同处问 UNCLEAR_TARGET |
| D9 | 布局给哪些、在哪给 | 3.4 那八样，在 capture、inspect 和改建后的整栋比对里给。`observe(detail, id=档案名)` 要不要也给一句概要（几层、几扇门、有没有床），所有者定；建议先不加，观察只管看得见的 |
| D10 | 改建时给了不一样的 rotation | 报参数错误：改建沿用档案的朝向，换朝向就是另盖一栋 |
| D11 | 补丁合并抽成建筑和机器共用的 `BlueprintPatch.merge`，还是建筑另写一份 | 抽出来共用：同一条规则只写一处；机器的部件、安装段、装后设置的合并留在机器 |
