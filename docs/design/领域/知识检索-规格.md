# 领域规格：知识检索

> 状态：已批准（2026-10-10，所有者定"都按建议来"）：第 10 节 11 项按建议执行，含两处规则例外（第 3 项读 Ponder 的非公开字段、第 5 项 JEI 插件类里一个静态字段）与对物资规格的一句修改（第 10 项）。起草：Claude（知识检索会话）；审查会话审过。
> 范围：LLM 查资料时能用的三类模组来源：Create 的思索（Ponder）、配方查看器 EMI 与 JEI 里的配方、FTB 任务书；把它们串在一起的物品资料页；给机器能力用的只读配方查询与思索结构。不绑里程碑。
> 依据：v0（`dev`，`aa97940c9`）`mcp/knowledge/` 与 `core/integration/{ponder,emi,ftbquests}/` 的读取部分：入口、读取与整理的文件逐个读过，思索回放与结构快照的内部只读到规则级。本域没有单独的旧逻辑清单，旧逻辑直接在第 5 节归类。模组侧核对的源码与版本见第 3.9 节。
> 边界：任务书的提交、勾选、领奖是 `quest` 能力（里程碑三，规格由机器规格会话出），本域只读。读任务书的那一层（`compat.ftbquests` 的读取接缝 `QuestBook` 与它的读写端）只做一份，由本域定义和实现；`quest` 能力经它自己 `spi` 里的接口用到这一层，发包的动作接缝由 `quest` 规格定义。机器怎么读状态、怎么施工，以及"把思索里的结构当蓝图建"，归机器领域。联网查 Wiki（`lookup` 的 `wiki`）不在本规格。

## 2 真人怎么做

不知道一样东西怎么做，按一下 JEI 或 EMI 看配方：看到"搅拌"一栏，下面画着动力搅拌器和工作盆，要加热，就知道得搭一台搅拌机。不知道一台机器怎么用，按住 W 看思索：一段段小动画配着文字，告诉你右键点哪里、手里拿什么、要多快的转速。整合包有任务书的，翻开看这一章还有哪些没做、要交什么、给什么奖励。

玩家不背百科，用到才查；查不到会说"JEI 里没这东西""这个包没有任务书"，不会编一个。看见的是界面上画出来的东西：被隐藏的配方、还没解锁的任务，玩家看不到，也不去猜。

## 3 新逻辑

### 3.1 LLM 怎么查

全部经 `lookup`，只读，不动角色。

| 想知道 | 调用 | 得到 |
| --- | --- | --- |
| 有哪些资料 | `lookup(topic="knowledge")` | 资料目录：随包常识每篇一行，各来源一行索引（例如"Create 思索：共 312 个场景"），以及每个来源的现状 |
| 一样东西是什么、怎么用 | `lookup(topic="knowledge", id="create:mechanical_mixer")` | 这件物品（方块）的资料页（第 3.3 节） |
| 按名字找 | `lookup(topic="knowledge", query="搅拌器")` | 名字、ID、标题对得上的物品资料页、思索场景、任务书条目，命中多的排前 |
| 读一篇 | `lookup(topic="knowledge", id="<资料地址>")` | 正文 |
| 怎么做出来 | `lookup(topic="recipe", id="create:andesite_alloy")` | 配方页（第 3.6 节） |
| 能拿它做什么、这台机器能做什么 | `lookup(topic="recipe", id="create:mechanical_press", uses=true)` | 用途页 |
| 只知道中文名 | `lookup(topic="recipe", query="安山合金")` | 名字对得上的物品 ID 列表，`next` 建议读第一个的配方页 |

`topic=knowledge` 的 `id` 原来接受资料地址和末段名；现在也接受物品或方块的注册 ID，读它的资料页。注册 ID 带冒号、没有 `://`，和资料地址分得开。

### 3.2 来源与条目

| 来源 | 在哪 | 目录里列什么 | 能搜到什么 | 一篇正文 |
| --- | --- | --- | --- | --- |
| 机制常识 | 内置（随包 Markdown） | 每篇一行 | 每篇 | 原文 |
| 物品资料页 | 内置（读游戏数据） | 不列（物品太多） | 每件注册物品，按 ID 与当前语言的名字 | 第 3.3 节 |
| Create 思索 | 联动 `compat.ponder` | 一行索引 | 每个思索场景，按物品名、ID 与演示结构名（场景标题要编译才有，读到时才出现） | 第 3.4 节 |
| 任务书 | 联动 `compat.ftbquests` | 一行索引 | 每章、每个可见的任务书条目，按标题；交物品的条目也按物品 ID 搜得到 | 第 3.5 节 |
| 配方 | 联动 `compat.emi`、`compat.jei`；都没装时读游戏配方表 | 不进资料目录，走 `topic=recipe` | 按物品名找物品 ID | 第 3.6 节 |

目录与搜索分开：目录只列内置常识和各来源的索引，免得一次塞进几千行；搜索覆盖每个来源的全部条目。这改变了 `KnowledgeSource.entries()` 的含义（只交目录行），搜索改走 `searchCandidates(query)`（第 3.8 节）。

资料地址：

| 条目 | 地址 |
| --- | --- |
| 物品资料页 | `maicraft://knowledge/item/<命名空间>/<路径>` |
| 思索索引 | `maicraft://knowledge/ponder/index` |
| 思索场景 | `maicraft://knowledge/ponder/<命名空间>/<路径>/<序号>`：某个物品的第几个场景，序号从 1 起，按思索界面里的顺序 |
| 任务书索引 | `maicraft://knowledge/quests/index` |
| 任务书的一章 | `maicraft://knowledge/quests/chapter/<16 位十六进制>` |
| 任务书条目 | `maicraft://knowledge/quests/quest/<16 位十六进制>` |

### 3.3 物品资料页：一件东西的总入口

LLM 想知道"这是什么、怎么用、怎么做、在哪用"时先读这一页。它不重复别处的正文，只给事实和去处：

```text
# 动力搅拌器（create:mechanical_mixer）
- 方块形态：create:mechanical_mixer；方块状态：facing（north / south / east / west）……
- 物品说明：游戏里鼠标悬停看到的文字
- 按住 Shift 看到的用法：摘要；条件 → 效果，逐条（模组按这种格式写在语言文件里的才有）
- 思索场景：2 个
    maicraft://knowledge/ponder/create/mechanical_mixer/1  用动力搅拌器处理物品
    maicraft://knowledge/ponder/create/mechanical_mixer/2  ……
- 配方：能做出它的配方 3 条 → lookup(topic=recipe, id=create:mechanical_mixer)
        它是"搅拌""无序合成（动力搅拌器）"两类加工的工作站，共 41 条 → 加 uses=true
- 任务书：2 个条目要交它（标题、地址）
```

- 物品说明与"按住 Shift"那段都从当前语言读，和玩家看到的一样。按住 Shift 的说明是 Create 及其附属模组的写法（语言文件里 `<物品的翻译键>.tooltip.summary`、`.condition1`、`.behaviour1`……），按键名约定读，读不到这一段就不出现，不另写名单。
- "相关资料"由各来源回答"跟这件物品有关的条目"（第 3.8 节的 `entriesAbout`）。机器领域以后也能挂自己的资料进来，例如某台机器的使用要点。
- 某个来源没装、还没加载、读出错，这一行写现状（第 3.7 节），不写"没有"。

### 3.4 思索场景

一个场景对应思索界面里的一段演示。正文：

```text
# 用动力搅拌器处理物品（create:mechanical_mixer 的第 1 个场景）
演示结构：create:mechanical_mixer/mixer（作者放在资源里的结构文件）
说明：思索里的创造马达代表外部动力输入，不是要照搬的建材；演示里的等待刻数是动画节奏，不是加工速度。
旁白与操作提示（按出现顺序；关键帧处分段）
  第 1 段
    1. 动力搅拌器配合下方的工作盆，可以把物品搅拌成别的东西
    2. 〔操作提示〕右键，手持 create:wrench
  第 2 段
    3. ……
结构：见下（JSON）
```

结构给 JSON，机器能力读的就是这一段：

```json
{
  "scene": "maicraft://knowledge/ponder/create/mechanical_mixer/1",
  "size": [5, 4, 5],
  "blocks": [{"offset": [2, 1, 2], "block": "create:basin", "properties": {"facing": "down"}}],
  "keyframes": [
    {"index": 1, "narration": [1, 2], "changed": [{"offset": [2, 3, 2], "block": "create:mechanical_mixer", "properties": {}}]},
    {"index": 2, "narration": [3], "changed": [], "removed": []}
  ]
}
```

- `blocks` 是作者的演示结构文件原样（全部格，不分"这时候展示了没有"）。
- `keyframes` 是在一个独立的演示世界里把场景从头放到尾，每到一个关键帧记下：这一段的旁白编号，以及相对上一帧被场景改了的格（换成别的方块、拆掉）。某一帧的完整方块集合 = `blocks` 加上到这一帧为止的改动。
- 看不出某一格在那一刻有没有显示出来（第 10 节第 4 项）。
- 回放只在第一次读结构时做，在客户端线程上分几刻做完，读的那次等它做完或超时；结果按场景缓存，换语言、重载资源、换世界时作废。
- 场景里的方块实体数据、实体、演示用的转速只是演示现场，不是施工配置，正文里不给。

思索索引一页列全部有场景的物品：名字、ID、场景数。场景多时也全列，按命名空间分组，开头给总数。

### 3.5 任务书

只给玩家在任务书里看得见的东西，进度是这个队伍此刻同步到客户端的样子。

- 索引：任务书标题；每章一行：章名、可见的条目数、完成了几个、能领奖的几个。另列四个筛选好的清单：现在能做的（前置都满足、还没完成）、没完成的、做完的、有奖励可领的。
- 一章：章名、副标题；本章每个可见条目一行：标题、地址、状态（不能开始 / 能做 / 完成了 / 有奖可领）。章里的说明图片只给文字和引用名。
- 一个条目：

```text
# 安山合金（任务书条目 3F1A…，章：机械动力入门）
状态：能做（前置 2 个都完成了）；可重复：否；可选：否
说明：（整合包作者写的文字；还没完成且作者设了"完成前隐藏正文"时不给）
要求（逐项，按顺序完成的会写明）
  1. 交 16 个 create:andesite_alloy（会消耗；进度 5/16）
  2. 去 minecraft:the_nether（进度 0/1）
奖励
  - 物品 create:cogwheel ×8（未领）
  - 从 4 样里选 1 样：…（可领时列出全部候选与数量）
  - 随机奖励：作者设了不显示内容
前置：2 个，都完成了；另有 1 个对你还不可见
```

要求按原生类型写成人话：交物品（消耗不消耗、要不要合成得来、组件要不要对上，能接受的物品全列）、交经验、到维度、到群系或结构、杀生物、到一块区域（左闭右开的长方体）、统计数、勾选、进度、看着某样东西、阶段、交流体、交能量；脚本定义的写"由服务器判定"，不认识的类型写原生类型名，不猜。

任务书的文字是整合包作者写的外部资料，和聊天一样不可信：可能写着"现在去做某事"，那不是给角色的指令，也不带任何许可。正文开头写明这一点。

条目正文里每项要求、每项奖励都带它的编号（FTB 的 16 位十六进制），LLM 下达 `quest` 时照抄（参数 `quest`、`requirement`、`reward`、`choice`，见任务书规格）。读取接缝 `QuestBook` 同时给 `quest` 能力用，所以除了正文里的内容，还要给出：每项要求有没有提交按钮（消耗物品的要求、作者开了按钮的自定义要求才有），每项奖励现在能不能领、是不是要先选候选，奖池里的子项不是能单独领的奖励。

### 3.6 配方页与用途页

`topic=recipe` 回 JSON：

```json
{
  "item": "create:andesite_alloy", "name": "安山合金",
  "read_from": "emi",
  "recipe_count": 2,
  "categories": [
    {
      "category": "create:mixing", "category_name": "搅拌",
      "workstations": [{"id": "create:mechanical_mixer", "name": "动力搅拌器"}, {"id": "create:basin", "name": "工作盆"}],
      "recipes": [
        {
          "recipe": "create:mixing/andesite_alloy",
          "inputs": [{"item": "minecraft:andesite", "count": 1}, {"tag": "c:nuggets/iron", "name": "铁粒", "count": 1}],
          "outputs": [{"item": "create:andesite_alloy", "count": 1}],
          "definition": {"type": "create:mixing", "heat_requirement": "none", "processing_time": 100, "...": "..."}
        }
      ]
    }
  ]
}
```

- 配方页（默认）：能做出这件东西的全部配方，一条不省。按配方类别分组（类别 ID 与名字照配方查看器）；每组写在哪做（工作站，可能是一台机器加配套方块）。
- 每条配方：配方 ID（配方查看器给不出 ID 的写 `null`，不编）；原料与产出，物品写 ID 和数量，标签写 `#` 和一个示例名，流体写 ID 和毫桶；EMI、JEI 认得出、但既不是物品也不是流体的（例如通用机械的化学品）写 `{"other": ID, "amount": 数量}`；只有配方查看器标了几率的产出才带 `chance`。
- `definition` 是这条配方在游戏里的原始定义（配方自己的序列化格式转成 JSON），加热要求、加工时间、带几率的副产物这些"配方里写着、界面上不一定画出来"的东西都在这里，原样给，不解释。查看器给不出背后的游戏配方（例如它自己生成的展示用配方）就不带这一项。
- 用途页（`uses=true`）：两部分。一是"它当原料或催化剂的配方"，二是"它当工作站的加工"（机器就是这里）。都按类别分组，每条配方压成一行：配方 ID、产出、原料，不带 `definition`。要看某一条的全部细节，查它产出物的配方页。用途页也全列，开头给每类的条数与总数。
- 被配方查看器隐藏的配方与类别不给：玩家在界面上也看不到。
- 一页里同一类别下背后是同一条游戏配方的，只出现一次。

### 3.7 配方从哪读；没装、没加载好时怎么说

配方的来源一次只用一个，不合并：

```text
装了 EMI 且已加载完        → 读 EMI
否则装了 JEI 且运行时可用  → 读 JEI
否则                      → 读游戏配方表
```

- 两个都装时读 EMI：EMI 会把 JEI 插件注册的类别原样导入（类别 ID 不变，已有原生 EMI 类别的跳过），所以 EMI 看到的是两者之和，不用自己再去重。
- EMI 刚进世界时要加载几秒。这段时间由 JEI 回答，结果里 `read_from` 写的是实际读的那个。
- 游戏配方表是从服务器同步到客户端的全部配方，模组的加工配方也在里面，原料、产出、`definition` 都读得到；读不到的是"这类配方在哪台机器上做"，以及配方查看器自己拼出来的展示配方。这时 `workstations` 为空，结果附一句："这个实例没装配方查看器（EMI 或 JEI），模组加工配方看得到原料和产出，看不出用哪台机器做。"

现状怎么说：

| 情况 | 回答 |
| --- | --- |
| 物品 ID 不存在 | `unknown_id` |
| 有这件东西，但没有任何配方能做出它 | 空列表，注明"在 EMI 里没有做出它的配方；这不代表拿不到，可能要挖、打、交易" |
| 配方查看器还在加载、JEI 也没有 | 用游戏配方表回答，注明"EMI 还在加载配方" |
| 联动停用（装的版本和编译时的对不上） | 退到下一个来源，注明哪个停用了、为什么 |
| 没装 Ponder | 物品资料页的思索一行写"这个实例没装思索（Ponder）"；搜索不出思索场景；资料目录不列思索 |
| 装了 Ponder，这件东西没有场景 | "没有思索场景"，不说它没有功能 |
| 没装 FTB 任务 | 资料目录不列任务书 |
| 装了，但还没进世界 / 服务器还没同步 / 这个服务器没有任务书 / 任务书界面被服务器禁用 / 队伍被锁 | 任务书索引写对应那一句，不给旧数据 |
| 思索回放超时或出错 | 旁白照给，结构一节写"这一场景的结构没取到：原因" |

资料目录（`lookup(topic=knowledge)` 不带 `id`、`query`）最后附各来源的现状，例如"Create 思索：可用，312 个场景""任务书：服务器还没同步""配方：EMI"。没列出来的来源就是这个实例没有。

```text
compat.ftbquests     联动入口 + 读取接缝 QuestBook（只读自己队伍：章节、可见条目、要求与进度、
                     奖励与奖池候选、领取状态）；可见性、要求、奖励的整理。quest 能力的动作接缝也放这里，由 quest 规格定义
neoforge.compat.*    读写端：直接调用模组的类，只翻译

mcp.tool.LookupTool  topic=recipe 与 uses 参数；读游戏与模组的部分交给客户端线程
```

- 配方查询放在玩家行为层的 `behavior.recipe`：机器能力（L3）要用它核对"这台机器真能做这道工序"，联动模组（L3）要实现它，MCP 入口（L4）要拼页面，三方都看得到玩家行为层。来源的先后、工作站、配方类别都是 Minecraft 的事，内核不认识它们；`KnowledgeSource` 只是通用的资料条目，留在内核。
- 和 `RegistryRecipeReads` 的分工：那是拿东西用的，只读合成、烧炼、石切三种、要能真的去做；这里是给人看的，什么类型都读、只读不做。两者都读游戏配方表，各管各的，不合并。`obtain` 不从配方查看器拿配方去执行。
- 线程：配方查看器、思索、任务书、游戏配方表都只能在客户端线程读。`LookupTool` 和 `EventsTool`、`ExecuteTool` 一样收 `mcp.tool.ClientThread`，由启动传实现，把这部分交到下一个客户端刻做完再回；随包常识不用等。不在世界里时这部分回答"角色不在世界里"（`not_in_world`），随包常识照常可读。
- EMI 先于 JEI 的顺序写在 `RecipeLookup` 里：两个联动互相看不见，谁先谁后只能由上面一层定。`RecipeLookup` 按"EMI、JEI、游戏配方表"的顺序问，每个先回答自己现在能不能用。

几条模组事实，写进 `机器联动模组事实清单.md`：

- EMI 与 JEI 同装时，EMI 导入 JEI 插件的类别，类别 ID 不变；原生 EMI 类别已有的、或该命名空间已有原生 EMI 插件的跳过（`emi/xplat/.../jemi/JemiPlugin.java:189-254`）。

- FTB 任务 2101.1.36 要求 FTB Library 不低于 2101.1.36、FTB Teams 不低于 2101.1.9（`FTB-Quests/gradle.properties`），实测实例里的 FTB Library 是 2101.1.32。

### 3.10 给机器能力的接口

机器规格会话要三样，本域按下面的形状提供：

| 要的 | 本域给的 | 怎么用 |
| --- | --- | --- |
| 按物品查加工：什么能做出它；这台机器能做什么 | `RecipeLookup.making(物品)`、`using(物品)`、`atWorkstation(物品)`，返回第 3.6 节的配方记录（含类别、工作站、原料、产出、`definition`） | 机器能力在设计审阅里直接调，不自己读配方；LLM 走 `lookup(topic=recipe)` 看同样的内容 |
| 思索场景的结构与关键帧 | 第 3.4 节的结构 JSON：演示结构全部格，加每个关键帧的旁白编号与改动 | 某一帧的方块集合由机器能力自己叠出来，再换成它的蓝图格式 |
| 机器和部件"怎么用" | 物品资料页（第 3.3 节），`lookup(topic=knowledge, id=<方块 ID>)` | 机器能力说明里只写"不确定怎么用就查这一页"，不再把模组行为事实塞进能力说明 |

"思索里每一帧哪些格显示出来了"给不了（第 10 节第 4 项）。

### 3.11 让 LLM 找得到

v0 的维护记录 033、066、140：资料一直在，LLM 从来不去读；补进能力说明里的模组行为事实又在一次目录改写中丢了。v1 的做法：

1. `lookup` 的工具描述写清四个主题各查什么，其中一句点明"不知道一样东西怎么用、怎么做，先查它的资料页或配方"。
2. 能力的 `AbilitySpec.knowledgeUris` 列相关资料；机器类能力列它常用的物品资料页。
3. 物品资料页做总入口，从一件东西能走到它的思索、配方、任务书条目。
4. 搜索认中文名：LLM 常写"搅拌器"而不是 `create:mechanical_mixer`。
5. 资料只放在资料里：模组行为事实在物品资料页与思索里，能力说明不复制，改一处不会漏另一处。

## 4 对外接口的变化

不是能力，没有参数规格与结果细节。`lookup` 的变化：

| 参数 | 变化 |
| --- | --- |
| `topic` | `recipe` 接上 |
| `id` | `topic=knowledge` 时也接受物品或方块的注册 ID，读它的资料页；`topic=recipe` 时是物品 ID |
| `query` | `topic=recipe` 时按名字找物品 ID |
| `uses` | 新增，布尔，默认 `false`；只在 `topic=recipe` 时用：`true` 查能拿它做什么、它当工作站能做什么 |

返回：`topic=knowledge` 不变（目录多一项 `sources` 现状；正文仍是 `id`、`title`、`text`）。`topic=recipe` 是第 3.6 节的 JSON。

接口快照、07 第 2.2 节、`CHANGELOG.md` 随实现一起改。

## 9 验收

**离线测试**（读写端用替身，不需要模组）：

1. 来源顺序：EMI 可用时只读 EMI；EMI 加载中读 JEI；都没有读游戏配方表并附那句说明；EMI 停用后退到 JEI。
2. 配方页：分类别、写工作站；标签原料写 `#`；查看器给不出 ID 的写 `null`；同一类别下背后是同一条游戏配方的只出一次。
3. 用途页：当原料的与当工作站的分两部分；每类条数与总数对得上；不带 `definition`。
4. 隐藏的配方与类别不出现。
5. 物品资料页：有思索、有配方、有任务书条目时各一行；某个来源没装、加载中、停用各写现状；按住 Shift 的说明读不到就不出现。
6. 目录只列常识与各来源索引；搜索按中文名、ID、标题都能找到思索场景与任务书条目。
7. 思索：旁白顺序、按关键帧分段、操作提示的写法；结构 = 演示结构 + 每帧改动；回放超时时旁白照给、结构写原因。
8. 任务书：可见性的五条（第 7 节）逐条；四个筛选清单；进了没有任务书的服务器不给旧书；要求的各类型写法；脚本类型写"由服务器判定"。
9. 联动停用：读写端抛 `LinkageError` 后，配方退到下一个来源、思索与任务书的目录为空并写明原因，`lookup` 不报内部错误。

**实机**（NeoForge 开发客户端，EMI 1.1.24、JEI 19.38.0.366、Create 6.0.11）：

1. 查 `create:andesite_alloy` 的配方：有"搅拌"类别，工作站是动力搅拌器加工作盆；`read_from` 是 `emi`。
2. 把 EMI 挪走只留 JEI，同一查询照样有"搅拌"，`read_from` 是 `jei`；两个都挪走，写明看不出机器。
3. 查 `create:mechanical_press` 的用途：有"压制"一节，条数和 EMI 界面上的一致。
4. 读动力搅拌器的资料页与第一个思索场景：旁白与游戏里按 W 看到的一致（含转速要求那句）；结构里有工作盆和搅拌器。
5. 进世界后立刻查配方：EMI 还在加载时由 JEI 回答，过几秒再查变成 EMI。
6. 装 FTB 任务后在带任务书的单人世界里读索引、一章、一个条目，和书里看到的一致；完成一项后重读，进度跟着变。退出后进一个没有任务书的服务器，任务书写"这个服务器没有任务书"。
7. 联动的三次启动：装了、没装、版本范围改窄，日志各写对应那一句。

## 10 待两位决定

| # | 问题 | 建议 |
| --- | --- | --- |
| 1 | EMI 和 JEI 都装时读哪个；要不要把两边的结果合起来 | 读 EMI，不合并。EMI 已经导入了 JEI 的类别，合并只会带来重复和去重规则。EMI 加载中由 JEI 顶上 |
| 2 | 用途页很长时（铁锭这种基础材料可能上百条）怎么办 | 全列，按类别分组、每条一行，开头给每类条数与总数。不截断；LLM 很少查基础材料的用途，查了也需要看全 |
| 3 | 思索的旁白怎么读（02 第 5.8 节"不用反射"的例外）。场景自己的句子能经公开接口读到；共用句子（例如转速要求）和操作提示（右键、潜行、手持什么）只存在 Ponder 的非公开字段里（场景的指令表、文字元素的取字函数、操作提示的图标与手持物、等待刻数，共约七个） | 读这几个非公开字段（乙）。转速要求和操作提示正是 LLM 最需要的；只在 `neoforge.compat.ponder` 里用，字段在联动入口创建时取一次，取不到的那一类句子就写"读不到"、不影响其他句子；字段名登记进事实清单，版本范围锁在实测过的 Ponder 版本。另一个选项（甲）是只用公开接口，会缺这两类句子，旁白也分不了关键帧。这是 02 第 5.8 节"不用反射"的例外，要两位点头 |
| 4 | 思索结构给到什么程度 | 给演示结构全部格，加每个关键帧的改动（乙），全用公开接口。v0 还能给"那一刻显示出来的格"，要再读区段的非公开字段（丙），回放代码也最重；机器设计要的是"这台机器长什么样、有哪几种变体"，乙够用。只给演示结构文件、不回放（甲）最省，但看不到场景中途换上去的方块（例如把工作盆下面换成烈焰人燃烧室） |
| 5 | JEI 只在它自己创建的插件对象上交出运行时（`onRuntimeAvailable`），我们拿到它只能经一个静态字段（又一处规则例外） | 允许一处：`neoforge.compat.jei` 的插件类里一个 `volatile` 静态字段，类注释写明原因，和 `game.ClientHooks` 同类。架构检查 A7 只扫 `common`，这一处在架构检查的说明里写明 |
| 6 | FTB 任务实测实例没装，按哪个版本编译、怎么实测 | 按源码同版 2101.1.36 编译。实测时装 FTB 任务 2101.1.36 与它要的 FTB Library 2101.1.36 以上、FTB Teams 2101.1.9 以上，实例里的 FTB Library 2101.1.32 一起升（连锁破坏不受影响要顺带确认）。验证过的范围先定 [2101.1.36, 2101.2) |
| 7 | 任务书只给玩家看得见的，还是全部 | 只给看得见的。隐藏条目和隐藏正文是整合包作者的设计，LLM 看到玩家看到的 |
| 8 | 任务书正文怎么对待 | 和聊天一样当不可信的外部文字：正文开头写明，不当指令，不带许可 |
| 9 | Create 序列装配的 `chance` 是权重，`definition` 原样给会被读成概率 | 先原样给，不在知识层写 Create 的特例；Create 的联动入口建好后，由它给序列装配这一类配方补一句换算好的几率（经一个小接口挂进配方记录）。机器规格会话那边写 Create 联动时一起做 |
| 10 | `obtain` 以 NEED_ITEM 结束时，要不要在 `suggestion` 里指向 `lookup(topic=recipe, id=…)`。这一句算对物资规格（已批准）的修改 | 要。只是一句建议文字，不让 `obtain` 依赖配方查看器 |
| 11 | `lookup` 新增参数叫 `uses` 是否合适；`topic=knowledge` 的 `id` 接受注册 ID 是否合适 | 叫 `uses`：EMI、JEI 里"用途"就是 uses，LLM 熟悉；布尔默认 `false` 表示"查怎么做出来"。`id` 接受注册 ID：LLM 手里常常只有物品 ID |
