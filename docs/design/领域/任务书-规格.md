# 领域规格：任务书

> 状态：已批准（2026-10-10，用户定"都按建议来"，第 10 节各项按建议执行）。起草：Claude（机器规格会话）。
> 范围：能力 `quest`——对 FTB 任务书里的一个条目做一次原生动作：提交物品、手动勾选、领取奖励。里程碑三。
> 依据：[机器与任务-旧逻辑清单](机器与任务-旧逻辑清单.md)第 3.9 节（Q01–Q11，v0 `dev` `aa97940c9`）、[机器联动模组事实清单](机器联动模组事实清单.md)第 6 节、v0 `docs/dev/quests.md`。
> 边界：读任务书（章节、任务、要求、进度、奖励、奖池候选、可见性）归[知识检索-规格](知识检索-规格.md)（已批准，`f28b7095a`）：它定义并实现 `compat.ftbquests` 的读取接缝 `QuestBook` 与读写端，第 3.5 节末尾写了给 `quest` 的三样——每项要求和奖励的编号、有没有提交按钮、能不能领与要不要先选，奖池子项不是奖励；本规格只管动作，读的那一层不做第二份。电梯、机器与它无关。

## 2 真人怎么做

打开任务书，翻到那个任务，看要求：要交 8 块铁锭就点"提交"，背包里的铁锭少了、进度条满了就是交上了；手动勾选的任务点一下"完成"；完成的任务点"领取"，奖励进背包，是选择奖励就先挑一样再领。点了没反应就看看是不是没到条件（东西不够、任务还没解锁），不会连点。该选哪个奖励、下一个做什么，自己拿主意（在这里是 LLM 拿主意）。

## 3 新逻辑

```text
1 校验     operation ∈ submit（交物品）/ confirm（手动勾选）/ claim（领奖）
           quest 必填（任务书里任务的编号，16 位十六进制）
           submit / confirm 要 requirement（任务里那条要求的编号）；claim 要 reward（本任务的根奖励编号）
           choice 只在领选择奖励时给（候选编号）；格式错、编号形状不对 → 计划阶段一次报全
2 读状态   经 spi 读这个条目现在的样子（只读自己队伍）：看得见吗、能开始吗、要求完成没有、奖励领没领、是不是选择奖励、候选有哪些
           任务书没装、没同步到 → UNSUPPORTED / NOT_FOUND，写明原因
           编号对不上任何可见条目 → NOT_FOUND
3 已满足   submit / confirm：要求已经完成 → 完成，"开始时已完成"
           claim：奖励已经领过 → 完成，"已经领过"（不证明当时领的是这次想选的）
4 条件     submit 只对会消耗物品、有提交按钮的要求（物品要求、自定义带按钮的要求）；观察、击杀、流体这类自动完成的要求 → NOT_POSSIBLE_HERE，
             写明这条要求是怎么完成的
           confirm 只对手动勾选的要求
           claim 只对这个任务自己的根奖励；奖池里的子节点不是可领的奖励 → INVALID_PARAMETER
           交物品时身上没有要交的 → NEED_ITEM，写清要什么、差多少（不自动去弄：交什么是 LLM 的决定）
           选择奖励没给 choice → 提问 CHOOSE_ONE，列出候选（Mod 不替 LLM 选）
           任务还没解锁、被屏蔽 → REFUSED_BY_GAME，附任务书给的原因
5 发送     等本刻的交互机会，发一次原生请求（提交 / 勾选 / 领取）；发出前记"已尝试"，发出后绝不补发
6 观察     逐刻看任务书同步与背包：最后一次变化后再等一小会儿没有新变化，或发出后一段时间没有任何变化就收尾
           （初值：变化后 250 毫秒、发出后 3 秒；FTB 没有专门的回应，这两个数只是等待窗口）
7 结算     submit：要交的物品确实少了 → ITEM_CONSUMED；要求进度变了 / 完成了 → done
           confirm：要求完成了 → done
           claim：背包多了东西 → ITEM_GAINED；领取状态变了 → done
           发出了但窗口内什么都没变 → partial，进 unconfirmed（"发出了提交，任务书没有反应"），不重发
           发出了、背包变了但进度没变（同步晚到）→ partial，changes 照实写，remaining 写"等任务书同步"
```

**跨重启**：任务不跨重启；目标恢复后重新从第 2 步读现场：要求已完成就是已满足，没完成而东西还在就再发一次，东西没了而进度没变就 NEED_ITEM——不会重复消耗，所以不需要 v0 的消费预约。

**此刻能不能打断**：发出请求到收尾之间 UNSAFE_TO_STOP（一次动作，几秒钟）；其余 BETWEEN_ACTIONS。

### spi 与接缝

```text
ability.quest.spi.QuestBookOperations     能力只认这个接口，由联动入口实现，经登记表交来
  entry(quest, requirement 或 reward)      条目现在的样子：可见、能开始、要求完成没有、奖励领没领、是不是选择奖励、候选
  submit(quest, requirement)               发一次提交
  confirm(quest, requirement)              发一次勾选
  claim(quest, reward, choice)             发一次领取
compat.ftbquests                           联动入口（知识检索会话的同一个），实现 QuestBookOperations：
                                           读用 QuestBook（知识检索定义），发包用 QuestBookActions（本规格定义，实现放读写端旁边）
neoforge.compat.ftbquests                  读写端：直接调 FTB Quests 的客户端任务书与网络包（经 Architectury 的网络入口），不用反射
```

`ability` 看不到 `compat`，所以能力只认 `ability.quest.spi` 里的接口；联动登记表要为它加一个槽（公共部分，交审查会话统一加）。FTB Quests 没装时能力不登记（`requiredMods`），按名字下达回 `unknown_ability` 并说缺哪个模组。

## 4 能力说明

| 参数 | 必填 | 说明 |
| --- | :---: | --- |
| `operation` | ✅ | `submit` 交物品 / `confirm` 手动勾选 / `claim` 领奖 |
| `quest` | ✅ | 任务书里任务的编号（`lookup` 的任务书资料里给的） |
| `requirement` | | 任务里那条要求的编号；`submit` / `confirm` 必填 |
| `reward` | | 本任务的根奖励编号；`claim` 必填 |
| `choice` | | 领选择奖励时选哪个候选（资料页里给的候选编号） |

不带 `target`：任务书不在世界里。

能力说明：

> 对 FTB 任务书里的一个条目做一次动作：submit 把身上的东西交给一条"提交物品"的要求，confirm 勾选一条手动完成的要求，claim 领取一个任务的奖励（选择奖励要用 choice 指明选哪个）。编号从 lookup 的任务书资料里拿。只做一次、不自动推进、不替你选奖励；发出去了但任务书没反应会如实告诉你，不会连点。要看任务书的内容用 lookup。

结果细节：`entry`（动作前后这个条目的样子：进度、领取状态）、`sent`（发没发出去）。`changes` 用 `ITEM_CONSUMED`、`ITEM_GAINED`。

## 7 游戏事实的新归属

| 事实 | 新位置 |
| --- | --- |
| FTB 的任务、要求、奖励编号是 64 位、16 位十六进制 | `ParamSpecs` |
| 提交、勾选、领取各是一个客户端发给服务端的包；FTB 没有专门的回应，结果只能从任务书同步与背包看 | `compat.ftbquests` 的 `QuestBookActions` 与第 6 步 |
| 只有消耗物品的要求和带按钮的自定义要求有提交按钮；奖池子节点不是可领的奖励；选择奖励要先选 | 读取接缝 `QuestBook`（知识检索）给出，能力第 4 步判 |
| 只读自己队伍；未同步时队伍数据是占位 | 读取接缝 |
| 发包占用本刻的交互机会 | M3 交互机会 |

## 9 验收

**离线**：参数校验一次报全；已完成 / 已领过 → 已满足；自动完成的要求 → NOT_POSSIBLE_HERE；选择奖励缺 choice → CHOOSE_ONE 列候选；发出后窗口内无变化 → partial + unconfirmed，不重发；背包变了进度没变 → partial 并写明；没装 FTB Quests → 能力不登记。

**实机**（要一个装了 FTB Quests 的实例，见需求总表 Q1）：交 8 块铁锭的要求 → 铁锭少了、进度满了；勾选一条手动要求；领一个普通奖励与一个选择奖励；对已完成的再做一次 → 直接"已完成"；重启后恢复一个没发出的 `quest` 目标 → 重新读现场后只发一次。
