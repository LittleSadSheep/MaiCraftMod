# 世界刻速与失焦限流：任务变慢先查刻速，再谈停滞

## 规则

- 单机模式下内置服务端与客户端共用主循环：游戏窗口失焦时操作系统限流后台进程，世界刻速可降到 0.1~1tps；窗口回前台即恢复满速。这是运行环境特性，不是任务故障。
- 判断「任务停滞」前先读 situation 的 `tick_rate` 段：`recent_tps` 是两次观察之间的实测刻率；`rate_available=false` 时间隔一小会儿再查一次即可还原。
- 慢放与停滞的区分：任务 running、角色坐标未动、而 `recent_tps` 明显低于 20——是世界慢放，等待即可；`recent_tps` 接近满刻而进度持续不动，才是真停滞。
- task_progress 事件自带 `game_time`：把两条事件的 game_time 差与真实时间差对照，可以自行还原刻速。

## 这个规则会怎么坑你

- 失焦挂机期任务长时间角色未动，实际只走了几十刻：直接取消重提会重付寻路/观察成本，且重提后仍在限流。
- 把限流期描述成「世界冻结」：用户看画面时是满速，双方各自为真；结论要先带上刻率数字。
- 把动作确认失败归因于「刻速冻结」：先查动作自身的失败原因（如模式拦截、站位不符），刻速只是背景条件。

## 边界

- `tick_rate` 是两次 MCP 观察之间的平均刻率，不反映两次观察之间的瞬时波动；观察间隔过短、过长或世界时间回退时不给刻率，如实在 `reason` 说明。
